# 内容生产规范（M1）

> 本文件约束 `web/scripts/content/` 中所有对学员可见的内容，以及 `docs/content-specs/` 中的课时规格。它回答三个问题：写成什么样、题目怎么出、什么时候允许进入下一批。

## 0. 权威顺序

出现冲突时按以下顺序裁决，不靠个人偏好：

1. **目录与边界**：`docs/curriculum-plan.md` 决定课时 ID、标题、时长、先修与模块归属。
2. **数据形态**：`docs/content-schema.md` 决定字段、块类型、ID 规则与清单口径。
3. **写作与题目**：本文件决定语气、结构、题型、测试、Python、事实与评审规则。
4. **模块执行**：`docs/implementation/*` 的模块 brief 决定本模块讲什么、不做什么。

模块 brief 与本文件冲突时，先停下来改文档并记录原因，不带着冲突写正文。课时 ID、时长与清单不允许在正文阶段改动。

执行原则：

- 先规格，后正文；没有通过自检的 `docs/content-specs/<lesson-id>.md`，不允许写该讲。
- 内容生产按 M1–M4、E1、B 大块组织和收口；“阶段”一词可保留在教学过程语义中，但不再表示 S0→S7 的线性必修目录。
- 一次只写一讲；一批 2 讲（附录 2-3 讲），一批未通过校验不进入下一批。
- 事实先登记，测试先于文案；没有可验证证据的结论不写成事实。
- M9/G8 之前不发布，站点保持私有。

## 1. 读者与语气

### 1.1 读者画像

读者是有前端基础、后端经验偏弱的工程师，目标是在 AI 时代成为能独立交付、能定位故障、能讲清取舍的资深全栈。默认读者：

- 熟悉 JavaScript、浏览器、HTTP 的基本使用，但没系统处理过并发、持久化、容量与线上故障；
- 能读代码，但容易被“框架用法”掩盖对机制的理解；
- 需要能直接迁移到工作的判断，而不是名词解释。

### 1.2 语气规则

- 对读者说“你”，用具体场景开场：谁在什么情况下遇到了什么失败。
- 先给问题和代价，再给概念；先解释为什么，再解释怎么做。
- 不写营销话术：禁止“颠覆”“神器”“一文精通”“全网最全”。
- 不写“众所周知”“显然”“简单来说”来跳过推导。
- 不把框架当答案；框架只是实现，机制与边界必须讲清。
- 允许说“取决于版本”“需要实测”，不允许编造确定结论。
- 术语首次出现时用「中文（English）」标注，后文统一使用一个说法。

反例与正例：

| 反例 | 正例 |
| --- | --- |
| 众所周知，事件循环是 Node 的核心。 | 一段同步 JSON 解析卡住 2 秒时，这个进程里所有请求都会一起排队；先看事件循环被谁占住了。 |
| 使用连接池可以提升性能。 | 每次请求新建 TCP + TLS 连接，冷启动会多出几个 RTT；连接池把复用成本摊到多次请求上，但会占用服务端连接数。 |
| 这里显然应该用 302。 | 如果目标 URL 会变，301 可能被浏览器长期缓存；LinkHub 的短码目标可修改，因此默认用 302，并说明例外。 |

### 1.3 一次讲解的最小闭环

每个重要概念至少完成四步：

1. **现象**：读者能观察到什么（报错、延迟、状态码、日志、监控）。
2. **机制**：系统内部发生了什么，为什么会导致这个现象。
3. **取舍**：至少两个可选方案，各自的代价与适用边界。
4. **验证**：用什么命令、测试或指标证明判断成立。

只有名词与定义的段落不合格。

## 2. 段落与信息密度

- 一个 `html` 块只表达一个中心思想；不要把三个主题塞进同一段。
- 单个 `html` 块的纯文本不超过 **900 字符**；目标是 300-700 字符。超过就拆成两个块，或改成 `list` / `steps` / `table`。
- 每段 2-4 句；长句拆开，避免一个句子同时承担条件、结论和例外。
- 列表项保持平行结构；每项以动词或名词短语开头，不写完整的长段落。
- 不使用连续三层以上嵌套列表；需要层级时改用 `steps` 或表格。
- 代码、表格、流程、坑块之间要有过渡句，说明“为什么现在看这个”，不堆砌孤立素材。
- 正文不重复课时标题与副标题；第一段直接进入问题。
- 课时结束前给一个可执行的检查动作：一条命令、一个测试或一个自检问题。

## 3. HTML 白名单

`html` 字段只允许以下标签：

| 标签 | 允许用途 |
| --- | --- |
| `<code>` | 行内代码、命令、字段名、错误码 |
| `<strong>` | 关键结论、风险词 |
| `<em>` | 需要强调但非结论的词 |
| `<br>` | 极少量换行；优先拆段 |
| `<ul>` / `<ol>` / `<li>` | 并列项或步骤列表 |
| `<pre>` | 必须保留空白的短片段；长代码用 `code` 块 |

禁止：

- `<script>`、`<style>`、`<iframe>`、`<img>`、外链图片、Markdown 图片；
- 内联 `style`、`class`、`id`、`on*` 事件属性；
- `<h1>`-`<h6>`、`<table>`、`<div>`、`<span>` 等结构标签；
- `<a>` 链接；跨讲引用写课时标题，导航交给站点路由；
- TODO、待补充、占位、Lorem ipsum 等占位词；
- 任何需要联网才能显示的内容。

约束：

- 表格必须用 `table` 块，不写在 `html` 里。
- 代码必须用 `code` 块；`<pre>` 只用于极短、无法用代码块表达的内容。
- HTML 实体按需使用；不要用实体拼接代码。
- 所有可见文本必须能在无网络环境下完整呈现。

## 4. 内容块规则

每讲 8-14 个块；`ready` 课时必须至少包含 1 个 `analogy`、1 个 `code`、1 个 `pitfall` 或 `tip`、1 个 `table` / `compare` / `flow` / `steps`，以及 1 个深挖 `text`。

| 块类型 | 职责 | 硬限制 |
| --- | --- | --- |
| `analogy` | 用前端经验建立第一层直觉 | 必须指出类比在哪里失效 |
| `flow` | 展示阶段、状态转换或故障路径 | 3-7 个节点，每个节点有职责与失败表现 |
| `text` | 解释机制、取舍、边界 | 单块 ≤900 字符；深挖块 ≥200 字符 |
| `code` | 最小可运行实现或可执行片段 | 20-60 行；零第三方依赖；关键行注释 |
| `table` | 对比多个对象的同一组维度 | 4-6 列、4-8 行；单元格不塞长段落 |
| `compare` | 两到三个方案的并列对比 | 维度对称，不能只列好处 |
| `pitfall` | 线上常见错误的完整复盘 | 现象、原因、发现方式、修复、预防至少写 4 项 |
| `tip` | 可立即采用的实践建议 | 必须给出验证方式或判断标准 |
| `note` | 补充说明、版本差异、面试延伸 | 不承载必学主线；面试延伸 1-2 个问题 |
| `list` | 并列清单 | 3-7 项，结构平行 |
| `steps` | 有顺序的操作流程 | 3-7 步，每步有可观察结果 |
| `case` | 事故或决策复盘 | 六个必填字段齐全；`metric` 可选但有数据更好 |

### 4.1 类比块

- 至少 1 个/讲，优先使用浏览器、DevTools、前端构建、请求生命周期等读者熟悉的经验。
- 类比必须能映射到后端的真实约束：并发、持久化、失败、容量、共享状态。
- 必须写一句“这个类比在哪里不成立”，防止读者把直觉当机制。
- 不使用与主题无关的娱乐化类比。

### 4.2 深挖块

- 每讲至少 1 个 `text` 块承担深挖职责，纯文本不少于 **200 字符**（审计按去标签后的字符数计算）。
- 深挖必须包含以下至少两类：机制细节、数量级/预算、失败模式、边界条件、版本差异。
- 深挖不重复正文结论；它回答“再往下追问一层会怎样”。
- 不写没有来源的性能数字；确需数字时先登记事实，或明确写“取决于环境，需实测”。

### 4.3 坑块

每个 `pitfall` 至少覆盖五要素中的四项：

1. **现象**：用户、监控、日志分别看到什么；
2. **原因**：机制层面的根因，不是“代码写错了”；
3. **发现方式**：用什么命令、指标或测试定位；
4. **修复**：止损与根治的区别；
5. **预防**：测试、告警、约束或评审如何避免复发。

只列现象或只写“注意不要……”的坑块不合格。

### 4.4 面试延伸

- 每讲最后用 1-2 个 `note` 或 `tip` 问题收尾，问题要能检验取舍与边界。
- 给出参考要点与判断路径，不给“标准答案”式长文。
- 问题必须来自本讲内容，不引入下一讲才讲的概念。
- S6/S7 的面试延伸必须包含跨层验证、评估或成本边界。

### 4.5 表格、对比、流程与步骤

- 表格列必须有明确语义，不能出现“其他”“杂项”这类兜底列。
- 对比必须使用同一组维度；不允许 A 方案列 5 点、B 方案列 2 点。
- 流程节点写清输入、职责、输出与失败表现；只画顺序不写失败的流程不合格。
- 步骤必须可执行，每步有判断标准或可观察结果。

### 4.6 案例复盘

`case` 块六个字段必填：`title`、`context`、`symptom`、`cause`、`fix`、`prevention`。`metric` 可选，但推荐写可观察的指标变化。

- 案例可以是真实事故的脱敏重构，不编造具体公司、用户与金额。
- `cause` 必须写到机制层，不能停在“配置错误”。
- `fix` 区分止损与根治；`prevention` 必须包含可执行的测试、告警或约束。
- 不把案例写成故事会；每个字段都要服务于本讲的一个 objective。

## 5. 代码规范

### 5.1 正文代码块

- 20-60 行；只保留理解机制所需的最少代码。
- 零第三方依赖；需要运行时使用标准库或课程已有依赖。
- 必须可运行或可直接在站点判题器中执行；不写伪代码冒充可运行代码。
- 关键行用注释解释“为什么”，不解释“这行在赋值”。
- 一段代码只演示一个机制；需要多个机制时拆成多个 `code` 块。
- 错误处理必须显式：不要让示例默认网络、文件或权限永远成功。
- JS 代码块默认 `lang: 'javascript'`；需要 Python 对照的关键代码块必须在 `python.js` 中提供 `PYTHON_BLOCKS` 映射与 `pythonNote`。

### 5.2 练习题代码

- 题目必须是纯函数或无副作用的小模块，输入输出契约在题面中写清。
- 不使用网络、真实时间、随机数、文件系统、环境变量或第三方包；测试必须确定性。
- `starter` 保留结构但缺少关键逻辑，至少失败 1 条测试；`solution` 必须全部通过。
- `tests` 至少 4 条，覆盖正常路径、边界、失败路径；推荐 5-6 条。
- 测试名用中文，能直接看出失败含义，例如“并发峰值不超过上限”。
- 测试设计要能区分“理解机制”与“背答案”：至少一条测试针对常见错误实现。
- 单题 JS 超时 3 秒，Python 超时 5 秒；不要用长延时制造并发测试，优先用计数器与微任务/短延时。

### 5.3 测试断言

- JS 测试使用运行器提供的 `assert`、`assert.equal`、`assert.deepEqual`、`assert.throws`；异步测试必须 `await`。
- JS 测试沙箱只提供 `assert`、静默 `console`、`setTimeout/clearTimeout`、`setInterval/clearInterval`、`queueMicrotask`；不能使用 `process`、`require`、`fs`、`setImmediate`、`fetch`。需要等待事件循环时用 `setTimeout(0)` 或微任务。
- Python 测试使用 `assert_eq` 与 `assert`；异步测试标记 `async: true`，由运行器用 `asyncio.run` 执行。
- 测试代码不能依赖执行顺序；每条测试独立构造输入。
- 错误断言要校验错误类型或消息中的稳定片段，不校验完整堆栈。
- 浮点数比较使用明确的舍入规则或误差范围，不直接比较未定义的尾数。

## 6. 题型规则

### 6.1 概念检查（每讲 3 题）

- 3 题/讲；至少 1 道多选题。
- 单选题恰好 1 个正确项；多选题至少 2 个正确项。
- 每题 4 个选项（多选题可 4-6 个），至少 2 个干扰项；干扰项要像“真会犯错的人”会选的答案。
- 解析必须逐项解释错误选项为什么错，不能只重复正确项。
- 考决策、边界、故障判断与取舍，不考名词复述。
- 不使用“以上都对/都不对”、双重否定、文字游戏。
- 每题标注对应的 objective；三道题覆盖至少两个 objective。

### 6.2 代码题

- 按模块课时表配置：代码讲 1 道/讲；SQL 讲以 SQL 题验收；方案讲允许代码 + 方案双练习。
- 所有代码题 Node/Python 双轨；SQL 题不强制 Python 轨。
- 题面必须写清：业务场景、函数签名、输入输出、错误语义、边界条件。
- 测试至少 4 条；必须覆盖正常、边界、失败；starter 至少失败 1 条。
- 题解不能依赖框架或外部服务；需要并发时用可控制的 Promise/任务函数，不用真实网络。
- 常见错误实现要在规格中列出，并对应到会失败的测试。

### 6.3 SQL 题

- 只使用迷你 SQL 引擎支持的语法；不确定时先读 `web/scripts/engine/sql.js`。
- 数据量小但能区分正确/错误查询；至少包含 NULL、重复值、边界行中的两类。
- `expected` 必须与 `solution` 的执行结果精确一致；列顺序与行顺序按引擎结果定义。
- 题面说明排序、去重、NULL 处理与聚合口径，避免“碰巧对”。
- 不强制 Python 轨；但题解思路必须能迁移到真实数据库。

### 6.4 方案题

- 每个阶段至少 1 道；架构型课时额外增加。
- 自检清单 6-8 条，每条是学员能自己判断“做了/没做”的可观察项。
- 参考要点必须包含：约束、备选方案、代价、反悔条件；不能只列好处。
- 场景要包含至少一个冲突目标（例如一致性 vs 可用性、延迟 vs 成本）。
- 常见浅答案要写出来，并说明为什么不够。
- 方案题不要求唯一答案，但要求能自证取舍。

### 6.5 题目与目标对齐

规格中必须有一张对齐表：

| objective | 检查题 | 练习题 | 可观察证据 |
| --- | --- | --- | --- |
| O1 | C1 | — | 能判断失败层 |
| O2 | C2 | EX1 | 测试通过 |
| O3 | C3 | EX2 | 自检清单完成 |

没有题目覆盖的 objective 不允许进入正文；一道题覆盖不了任何 objective 也不允许保留。

## 7. Python 轨道规则

### 7.1 覆盖范围

- 每个 `kind: 'code'` 练习必须有 Python track；键为练习 ID，放在阶段 `python.js` 的 `PYTHON_TRACKS`。
- 每个关键 JS `code` 块应有 `PYTHON_BLOCKS` 对照；数组索引与该讲 JS 代码块顺序一致。
- SQL 题不强制 Python 轨；方案题不强制代码实现。

### 7.2 实现要求

- 使用 Python 习惯：`snake_case`、标准库、`asyncio`、明确的异常类型。
- 不逐行翻译 JS；按 Python 的运行时模型重写。
- 必须写 `pythonNote`，解释至少一个真实差异：
  - 事件循环与 GIL；
  - 异步 vs 线程/进程；
  - 数据结构与可变性；
  - 异常模型；
  - 标准库选择与边界。
- 不使用第三方包、网络、文件系统；兼容 Python 3.11+ 与浏览器 Pyodide 3.13。
- 浮点舍入、排序稳定性、字典顺序等行为差异要在题面或测试中固定。
- Python 测试数量必须与 Node 测试一致；异步测试标记 `async: true`。

### 7.3 反例

- 把 `Promise.all` 直接改成 `asyncio.gather` 却不讲并发上限与异常传播差异；
- 用 `ThreadPoolExecutor` 冒充异步，回避 GIL 与事件循环的讨论；
- 只改函数名与缩进，测试仍按 JS 语义写；
- Python 测试少于 Node 测试，导致边界未覆盖。

## 8. 事实登记

### 8.1 必须登记的内容

以下内容在写入正文或规格前，必须先登记到 `docs/facts/registry.md`：

- 版本号、发布日期、支持周期；
- 默认值、默认行为、默认配置；
- 价格、配额、速率限制；
- 性能数字、延迟预算、吞吐量、内存占用；
- 协议行为、状态码语义、标准条款；
- AI 模型能力、上下文长度、价格与限制。

### 8.2 登记格式

每行必须包含事实、日期与来源，日期格式 `YYYY-MM-DD`：

```text
- TLS 1.3 完整握手 1-RTT，TLS 1.2 为 2-RTT — 2026-11-09 — RFC 8446 / RFC 5246
```

- 来源优先官方文档、RFC、标准或本机实测；社区文章只能作为线索。
- 无法确认时写“取决于版本/环境”，不写绝对数字。
- 事实变化时更新日期；不删除旧结论，改为标注失效日期或替代条目。
- `tools/check-facts.mjs` 会扫描内容中的版本/数字模式；未登记即失败。
- AI 内容不写死模型名与价格；必须写机制、可替换接口、评估与降级。

### 8.3 事实与正文的一致性

- 规格中的事实表必须能在 `registry.md` 找到对应行。
- 正文引用的数字必须与登记值一致；不把“约”“可能”当成免责声明。
- 性能数字必须带环境与测量方法；没有环境说明的数字不写。
- 面试延伸中的结论也要受本规则约束。

## 9. AI 内容与 AI Coding

### 9.1 AI 应用内容

每讲 AI 应用内容必须覆盖：

- **机制**：请求如何进入模型、上下文如何组织、结果如何被验证；
- **可替换接口**：provider、模型、向量库、评估器都通过接口隔离，不把某家服务写死；
- **评估**：离线评估集、指标、通过门槛、回归方式；
- **降级**：超时、限流、内容拒绝、模型不可用时的产品行为；
- **成本与延迟**：预算、缓存、批处理、截断策略；
- **安全与隐私**：注入边界、数据脱敏、租户隔离、日志保留。

禁止：

- 把模型名、上下文长度、价格写成长期事实；
- 用“效果很好”代替评估；
- 示例依赖付费 API 或真实密钥；
- 把提示词技巧当成系统设计。

AI 练习使用 mock provider，必须离线可跑、无付费密钥、无仓库内密钥。

### 9.2 AI Coding 五层模型

AI Coding 内容按五层组织，不写提示词大全或工具评测：

| 层 | 要解决的问题 | 必须产出的可验证物 |
| --- | --- | --- |
| 任务 | 这次改动属于什么类型、风险与歧义在哪 | 任务分类、验收标准、非目标 |
| 上下文 | 模型需要哪些代码、约束、样例与历史 | 上下文清单、仓库地图、边界说明 |
| 执行 | 如何把任务拆成可审查的小步 | 分步计划、每步 diff 与回滚点 |
| 验证 | 如何证明改动正确，而不是看起来正确 | 测试、静态检查、运行时证据、review 记录 |
| 系统 | 如何让协作可复用、可度量、可改进 | 规则/模板、失败复盘、度量指标、团队规范 |

每讲 AI Coding 必须包含：

- 一个真实任务切片，能在一讲内完成；
- 一个可执行的验证步骤与失败判据；
- 一个失败模式复盘（模型幻觉、上下文缺失、测试假绿、范围蔓延等）；
- 一个可复用的检查清单或模板。

## 10. 课时规格流程

### 10.1 规格位置与命名

- 位置：`docs/content-specs/<lesson-id>.md`；每个课时一份。
- 模板：`docs/implementation/templates/lesson-spec.md`。
- 规格头部必须标注：课时 ID、标题、阶段、时长、先修、对应项目里程碑、能力层级、规格状态（草案/已评审/已冻结）。
- 规格不写正文；它写“正文要讲什么、怎么验证”。

### 10.2 规格必填内容

1. 元数据与能力层级；
2. 3-4 条可验证 objectives；
3. 学习者起点与常见误解；
4. 范围边界（本讲讲什么、不讲什么、交给哪一讲）；
5. 8-14 个内容块大纲，含类型、标题、核心论点、素材要点；
6. 3 道概念检查，含选项、正确项、解析要点、对应 objective；
7. 代码题：契约、starter/solution 要点、≥4 条测试、测试设计说明、Python 差异、常见错误；
8. 方案题（按阶段要求）：场景、自检清单、参考要点、常见浅答案；
9. 事实清单，逐条对应 `registry.md`；
10. 项目联动：本讲如何为阶段项目提供能力与证据；
11. 自检表，全部勾选后才允许写正文。

### 10.3 流程

```text
读大纲与模块 brief
  → 写规格
  → 规格自检（范围/目标/块/题/事实）
  → 独立评审（10 维预评分，<18/20 退回）
  → 写正文（一次一讲）
  → 单讲审计 + JS/Python/SQL 测试
  → 浏览器检查（渲染、控制台、移动端）
  → 批次收尾评审
```

- 规格与正文不一致时，以已评审规格为准；如果规格本身有问题，先改规格并记录原因，再改正文。
- 未通过规格评审的课时，不允许以“先写一点看看”为理由开始正文。
- 首批规格为 `s0-l1`、`s0-l2`；它们通过评审后，M2 的 B2.1 才能开始写正文。

## 12. 批次与评审协议

### 12.1 批次

- 核心阶段每批 2 讲，最多 3 讲；S6/S7 每批 2 讲；附录每批 2-3 讲。
- 每批先写规格，再逐讲写正文；一次只写一讲。
- 每讲完成即跑单讲审计与对应测试，不积压到批次结束。
- 一批未通过自动校验，不开始下一批。

### 12.2 任务卡

每个可执行任务使用 `docs/implementation/templates/batch-task.md`，写清类型、依赖、输入、产出、约束、验收、证据、回滚、批量与停止条件。

### 12.3 评审

- 每批结束写 `docs/reviews/<module>/<batch>.md`，包含命令输出摘要、问题与修复、残余风险。
- 每模块结束按 `docs/implementation/templates/review-report.md` 做独立评审。
- 内容评审使用 10 维评分表：范围纪律、问题先行、前端类比、事实准确、最小实现、坑与边界、练习对齐、Python 等价、深度、结构与可读性。
- 单讲 ≥18/20，且无 0 分项；S6 加“是否跨层”，S7 加“评估/成本/安全”，AI Coding 加“可验证/可复盘”。附加项不过，整讲不通过。
- 评审不通过，不进入下一模块；修复后重新评审，不带着问题累计。
- 任何跨讲改动先改边界矩阵，再改内容。

### 12.4 门禁命名

- 本文件的 M1 规范门评审写入 `docs/reviews/g1-standards.md`。
- 总纲中 M2 完成后的 S0-S1 内容门仍为 `docs/reviews/g1-s0-s1.md`，两者不是同一道门；不得互相替代。
- 发布门为 G8；M1 及后续内容生产阶段不执行发布，站点保持私有。
