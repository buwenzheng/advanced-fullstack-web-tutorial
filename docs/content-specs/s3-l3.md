## 1. 出口能力

1. 比较令牌桶、漏桶、固定窗口与滑动窗口的精度、突发与内存成本。
2. 选择限流维度与层次（IP/用户/API Key/租户/全局），并说明 NAT、共享出口与白名单的影响。
3. 实现令牌桶、429/Retry-After 与容量算术，能解释参数如何从流量与成本推导。
4. 设计过载丢弃与优先级保护，写清哪些请求先失败。

## 2. 学习者起点与常见误解

- 已经知道：前端 `debounce`/`throttle`；HTTP 429 与 `Retry-After` 的基本含义；API Key 与用户身份的区别。
- 常见误解：
  - 「限流就是每秒只放 N 个请求。」——还要区分突发容量、并发连接数与配额周期。
  - 「前端已经防抖了，服务端不用限流。」——客户端可被绕过，服务端保护的是自身与下游。
  - 「按 IP 限流最公平。」——办公室 NAT 与移动网络会让大量用户共享出口，容易误伤。
  - 「先限流再认证更省资源。」——匿名维度太粗会误伤；认证后按用户/租户限流更准确，但认证本身也要限流。
  - 「Retry-After 写 1 秒就行。」——要让客户端等到真正可能成功的时刻，并加抖动。
  - 「限流能替代扩容。」——限流是止损与保护，长期容量问题仍要扩容或降本。

## 5. 概念检查（3 题）

### C1

- ID：`s3-l3-check-1`
- 类型：单选
- 考点：突发流量适合令牌桶还是漏桶
- 正确项：令牌桶允许在容量内突发；漏桶把输出整形为恒定速率
- 解析要点：固定窗口边界会双倍突发；滑动窗口更平滑但成本高；选择取决于是否允许突发。

### C2

- ID：`s3-l3-check-2`
- 类型：多选
- 考点：限流维度与 NAT/租户
- 正确项：按 IP 会误伤 NAT 后的多用户；按用户/API Key 更精确；租户维度防单租户吃满；全局保护兜底
- 解析要点：维度越细成本越高；先认证再按用户限流；匿名入口单独限 IP。

### C3

- ID：`s3-l3-check-3`
- 类型：单选
- 考点：429 与 Retry-After
- 正确项：429 + 稳定错误码 + Retry-After（按令牌补充时间计算）
- 解析要点：Retry-After 为 0 或过小会引发重试风暴；过大浪费恢复时间；需加抖动。

## 6. 代码题：令牌桶

- 契约：`createTokenBucket({ capacity, refillPerSecond, now = Date.now } = {})`
  - `tryConsume(tokens = 1)` → `{ allowed, remaining, retryAfterMs }`；
  - 初始满桶；按时间补充，补充后不超过 capacity；
  - 支持小数 token 与小数补充速率；
  - 允许时 `retryAfterMs` 为 0；拒绝时按缺口与速率计算向上取整的等待毫秒；
  - 注入 `now`，测试不使用真实时间。
- 测试（≥6）：
  1. 初始满桶可一次消耗完；
  2. 小数 token 消耗与剩余；
  3. 时间推进后按速率补充；
  4. 突发耗尽后拒绝并给出 retryAfterMs；
  5. 补充不超过容量上限；
  6. 非法参数或非正 token 抛错；
  7. 拒绝后等待足够时间可成功。
- 测试设计说明：用 `clock` 变量推进时间；浮点比较使用误差范围；retryAfterMs 用精确整数；第 5 条长时间推进后一次消耗 capacity，断言仍允许、再消耗一个被拒绝。
- Python 差异：毫秒整数时钟；`min(capacity, tokens + elapsed / 1000 * rate)`；返回 dict；浮点与整数除法差异写进 note。
- 常见错误：补充不封顶；用 `Date.now` 导致测试不稳定；retryAfter 算成 0；真实 Redis 中非原子读改写。

## 7. 方案题：LinkHub 限流策略

场景：跳转、创建、登录三类接口共享数据库；营销活动会带来突发；部分企业客户走固定出口 IP。

参考要点：创建按用户/API Key，跳转按 IP + 全局保护，登录按 IP + 账号；企业固定出口用 API Key 或白名单避免 NAT 误伤；过载时保跳转、丢分析类请求；用压测校准容量，保留开关。
