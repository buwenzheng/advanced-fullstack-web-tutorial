## 1. 出口能力

1. 把部分失败、超时与「未知结果」当成常态，不用二值思维写调用代码。
2. 设计跨服务超时预算与重试预算，避免重试放大与重试风暴。
3. 用租约 + fencing token 处理锁过期后的旧写入。
4. 解释时钟偏移、乱序与「看起来的先后」如何制造错误。

## 2. 学习者起点与常见误解

- 已经知道：单服务内的超时、重试、退避、熔断、幂等键（m3-resilience）；消息至少一次投递与幂等消费（m3-queue、e1-consistency）。
- 常见误解：
  - 「调用超时就是失败，可以放心重试。」——超时只说明结果未知，可能已经成功。
  - 「重试是安全的，多试几次总能成功。」——调用链每层都重试会指数放大，打垮下游。
  - 「锁没过期就是安全的。」——GC 停顿、网络延迟会让持有者「以为自己还持锁」，实际已被别人拿走。
  - 「拿到锁之后写数据就安全。」——锁保护的是「同一时刻只有一个持有者」，不保护「旧持有者迟到写入」。
  - 「时间戳能决定先后。」——不同机器时钟有偏移，时间戳只能当参考，不能当因果。

## 3. 范围边界

- 本讲只讲：部分失败与未知结果、超时/重试预算、租约与 fencing token、时钟与顺序的工程直觉。
- 本讲不讲：CRDT 与共识算法（Raft/Paxos）的内部推导；也不重复 m3-resilience 的退避公式与熔断器实现。
- 与相邻讲的分工：m3-resilience 讲单个服务如何扛住依赖故障；本讲把同一批问题放大到跨服务，重点是「未知结果」与「旧持有者」；CAP/PACELC 只讲取舍直觉，不背定理。

## 6. 代码题：Fencing Token 锁

契约：`createFencedLock({ store, now })`。

- store 提供 `get(key)`、`set(key, record)` 与一个单调递增的 token 源（`nextToken()`）。
- `acquire(key, ttlMs)`：当前锁未过期则返回 `null`；否则生成新 token（全局单调递增），写入 `{ token, owner, expiresAt: now() + ttlMs }`，返回 `{ token, expiresAt }`。
- `renew(key, token, ttlMs)`：锁不存在、已过期或 token 不匹配返回 `false`，否则延长 `expiresAt` 并返回 `true`。
- `release(key, token)`：token 匹配且未过期时删除锁，返回 `true`；否则 `false`。
- `write(key, token, value)`：token 必须等于当前锁 token 且锁未过期，才写入 `store.data[key]`，返回 `{ ok: true }`；否则返回 `{ ok: false, reason: 'STALE_TOKEN' }`。
- 新持有者获取锁后 token 必然大于旧 token；旧 token 的写入与续租都被拒绝。

测试（7）：首次获取；续租延长过期；过期后可被新锁获取；旧 token 写入被拒；新 token 写入成功；续租过期锁失败；释放后新持有者获取。

Python 差异：`time` 注入（`now` 可调用）；token 用整数单调递增；返回 `dict`；错误用 `{'ok': False, 'reason': ...}`。
