## 1. 出口能力

1. 解释主从复制、复制延迟与 read-your-writes，能选合适的补救手段。
2. 选择分片键，识别热点、跨分片查询与重分片代价。
3. 设计分布式 ID 与一致性哈希环，并解释增删节点时的最小迁移。
4. 对读写分离与分片做取舍，知道什么时候不该分片。

## 2. 学习者起点与常见误解

- 已经知道：索引、查询计划（m2-schema）；读模型与最终一致（e1-consistency）；缓存与失效（m3-cache）。
- 常见误解：
  - 「主从复制是实时的。」——异步复制有延迟窗口，读从库可能读到旧值。
  - 「读写分离就是配置一下连接。」——写后立刻读需要额外机制（粘主、版本号、会话一致性）。
  - 「分片后性能自然变好。」——分片键选错会产生热点与跨分片查询，反而更慢。
  - 「分布式 ID 只要不重复就行。」——趋势递增影响索引与范围查询效率，随机 ID 会放大写放大。
  - 「一致性哈希能保证负载绝对均衡。」——虚拟节点太少会倾斜，增删节点仍有迁移。

## 3. 范围边界

- 本讲只讲：复制与延迟、read-your-writes、分片键与热点、一致性哈希、分布式 ID 的结构与取舍。
- 本讲不讲：B+tree/LSM 的内部结构（b-btree）、数据库产品参数调优、跨分片事务的完整协议。
- 与相邻讲的分工：b-btree 讲存储引擎内部；本讲只讲「扩数据」的方案与代价；e1-consistency 讲读模型一致性，本讲讲副本与分片带来的可见性问题。

## 6. 代码题：一致性哈希环

契约：`createHashRing(nodes, { virtualNodes = 100, hash = fnv1a })`。

- `hash` 默认固定为 FNV-1a 32-bit（与 m3-cicd 同一实现，对 UTF-8 字节计算）。
- 环上位置 = `hash(node + '#' + replicaIndex) % 2^32`；每个物理节点映射 `virtualNodes` 个虚拟节点。
- 返回 `{ getNode, addNode, removeNode, nodes, size }`：
  - `getNode(key)`：`hash(key)` 后二分查找第一个 ≥ 该位置的虚拟节点，回绕到环首；空环抛 `EMPTY_RING`。
  - `addNode(node)` / `removeNode(node)`：增量更新环，不重建其余节点的映射；重复添加/删除不抛错（幂等）。
- 测试（7）：同一 key 多次调用结果一致；固定 5 节点 1000 个 key 时每节点份额在 10%–30%；增加节点后仍映射到旧节点的 key 保持不变；删除节点后其 key 迁移到后继；空环抛 `EMPTY_RING`；虚拟节点从 1 增到 100 时最大份额下降；重复 add/remove 幂等。

Python 差异：同一 FNV-1a 实现；环用排序 `list` + `bisect`；返回 `dict`；空环抛 `ValueError('EMPTY_RING')`。

## 8. 事实清单

| 事实 | registry 对应 |
| --- | --- |
| 异步复制存在复制延迟，读从库可能读到旧值 | 通用复制模型，不绑定产品版本；registry 无版本型事实，check-facts 不涉及 |
| 一致性哈希通过虚拟节点改善均衡 | 通用算法机制，不绑定实现；registry 无版本型事实 |
| Snowflake 类 ID = 时间戳 + 节点 + 序列 | 通用结构，不绑定实现；registry 无版本型事实 |
