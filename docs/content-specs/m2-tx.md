## 1. 出口能力

1. 用 LinkHub 场景解释 ACID，并区分脏读、不可重复读、幻读与丢失更新，能判断一个现象属于哪一类。
2. 为标准隔离级别建立正确的预期，知道 PostgreSQL 与 MySQL InnoDB 的默认级别不同，并能说明默认值不等于业务正确性。
3. 为「创建短链 + 写审计」「点击跳转 + 写点击事件」「更新链接 + 写审计」选择事务边界，说明哪些必须同事务、哪些应移出事务异步执行。
4. 用版本列 + 比较并交换（compare-and-set）实现乐观并发更新与有上限的重试，避免丢失更新；并能诊断长事务与连接池耗尽，用容量算术说明池大小的依据。

## 2. 学习者起点与常见误解

- 已经知道：JavaScript 的异步、Promise、事件循环；HTTP 请求的生命周期；SQL 的基本增删改查；索引能加速查询。
- 常见误解：
  - 「用了数据库就有 ACID，业务代码不需要关心事务边界。」——事务边界由应用决定，跨两次独立请求的写操作不会被自动包在一个事务里。
  - 「隔离级别越高越安全，直接上 SERIALIZABLE。」——更高隔离会带来更多冲突、重试与锁等待，需要与业务冲突率和吞吐一起权衡。
  - 「REPEATABLE READ 下不会发生丢失更新。」——应用层「读出来、改一改、写回去」仍可能覆盖别人的写入；需要锁、版本号或串行化冲突检测。
  - 「MVCC 就是完全不加锁。」——普通读走快照，写操作仍要加锁并写新版本；写写冲突、唯一约束冲突仍然存在。
  - 「长事务只影响开启它的那个请求。」——它会占住连接、持有快照与锁，拖慢清理与其他事务，最终把连接池耗尽。
  - 「连接池越大越好，调到数据库上限就行。」——连接数由所有实例、后台任务和副本共同占用，过多的连接会加剧数据库上下文切换与内存压力。
  - 「把外部副作用放在事务里更安全。」——外部操作会拉长事务；事务尚未提交时执行副作用，失败后还可能留下无法回滚的痕迹。

## 3. 范围边界

- 本讲只讲：
  - ACID 的四个保证与它们在并发下的失效方式；
  - 脏读、不可重复读、幻读、丢失更新的定义与判别；
  - SQL 标准的四种隔离级别与 PostgreSQL/MySQL InnoDB 的默认值差异；
  - MVCC 的快照读、当前读、版本链与可见性直觉；
  - 乐观并发控制（版本列 + CAS + 重试）与悲观锁的取舍；
  - LinkHub 的事务边界、幂等与重试上限；
  - 长事务、连接池等待与容量算术。
- 本讲不讲：
  - 分布式事务、两阶段提交与跨服务一致性（S5）；
  - 缓存一致性策略与失效模式（S3）；
  - 数据库存储引擎、undo/redo 日志的内部实现（b-btree）；
  - 复制、主从延迟与故障切换（S5/S6）；
  - 具体 ORM 的事务 API（实现细节，不是机制）。
- 与相邻讲的分工：
  - `m2-sql` 建立查询正确性，`m2-index` 解释查询性能；本讲解释并发写入为什么会互相覆盖，以及如何证明修复有效。
  - `m2-schema` 讲约束与迁移；本讲的锁与长事务是迁移风险的输入，但不在本讲展开迁移步骤。

## 5. 概念检查（3 题）

### C1

- ID：`m2-tx-check-1`
- 类型：single
- 标签：异常分类
- 题干：两个会话都读到 `links.clicks = 10`，会话 A 写回 11 并提交，会话 B 仍按自己读到的 10 写回 11 并提交，最终值是 11 而不是 12。这属于哪类异常？
- 选项：
  - A. 脏读：B 读到了 A 未提交的数据（错误）
  - B. 不可重复读：同一事务内两次读到不同值（错误）
  - C. 丢失更新：B 的写入覆盖了 A 已提交的更新（正确）
  - D. 幻读：同一范围查询返回了新的行（错误）
- 解析要点：脏读是读到未提交数据；不可重复读是同一事务内同一行被别的事务改动；幻读是同一范围查询的行集合变化；这里的核心是两次基于旧值的写回导致一次更新消失。提高隔离级别不一定自动消除应用层读改写造成的丢失更新，需要锁、版本号或串行化冲突检测。
- 对应 objective：O1。

### C2

- ID：`m2-tx-check-2`
- 类型：multi
- 标签：MVCC 与隔离级别
- 题干：关于隔离级别与 MVCC，以下哪些说法正确？
- 选项：
  - A. PostgreSQL 默认隔离级别是 READ COMMITTED（正确）
  - B. MySQL InnoDB 默认隔离级别是 REPEATABLE READ（正确）
  - C. 普通 SELECT 在 MVCC 下读取快照，UPDATE 需要读取当前最新版本并加锁（正确）
  - D. 所有数据库的 MVCC 实现与快照时机完全相同（错误）
  - E. 只要使用 READ COMMITTED，就不会发生丢失更新（错误）
- 解析要点：默认级别是两个数据库的已知差异；MVCC 的读路径与写路径不同，写操作仍要处理并发；不同数据库的版本链、快照时机与清理机制不同；丢失更新取决于应用是否做了读改写与冲突检测，不是单靠隔离级别名称就能消除。
- 对应 objective：O2。

### C3

- ID：`m2-tx-check-3`
- 类型：single
- 标签：长事务诊断
- 题干：接口 P99 从 200ms 升到 3s，连接池等待数持续升高，监控显示部分事务里在调用第三方 HTTP 接口。第一步应该做什么？
- 选项：
  - A. 立刻把连接池上限调到数据库最大连接数（错误）
  - B. 定位并缩短持有连接的事务，把外部调用移出事务，再根据事务时长与并发量重新评估池大小（正确）
  - C. 把隔离级别改成 SERIALIZABLE（错误）
  - D. 直接重启数据库实例释放连接（错误）
- 解析要点：池等待高是症状，根因是连接被长事务长期占用；先缩短持有时长，再谈容量。直接加连接会把压力转移到数据库，可能更慢；SERIALIZABLE 增加冲突与重试；重启只能短暂清空会话，不能改变事务持有时长。
- 对应 objective：O4。

## 6. 代码题（1 题）

- 题号：`m2-tx-ex-1`
- 标题：乐观并发更新与重试
- 业务场景：LinkHub 的运营后台可以同时修改同一条短链的目标地址。两个编辑者同时打开表单时，后提交的人不能悄悄覆盖先提交的修改；冲突时应基于最新版本重试，超过上限则明确报错。
- 契约：
  - `updateWithRetry(store, id, mutate, { maxRetries = 3 } = {})`，返回最终记录（包含递增后的 `version`）。
  - `store.get(id)`：返回当前记录的浅拷贝；不存在时返回 `null`。
  - `store.compareAndSet(id, expectedVersion, next)`：原子操作；当前 `version === expectedVersion` 时写入 `next` 并返回 `true`，否则返回 `false`，不得部分写入。
  - `mutate(snapshot)`：接收最新快照，返回下一版本的字段；`id` 与 `version` 由函数维护，`mutate` 不需要返回它们。
  - `maxRetries`：首次尝试失败后的重试次数，总尝试次数为 `1 + maxRetries`。
  - 冲突耗尽后抛 `ConflictError`，错误对象包含 `id` 与 `attempts`。
  - 记录不存在抛 `NotFoundError`。
  - `mutate` 抛出的业务错误立即向上传播，不能当成冲突重试，也不能写入。
- starter 要点：只读一次、调用一次 `mutate`、只做一次 CAS；失败后直接抛普通 `Error`，不重试；版本递增依赖 `mutate` 自己返回。
- solution 要点：每次尝试重新 `get`；`mutate` 基于最新快照；把 `{ ...next, id, version: snapshot.version + 1 }` 交给 CAS；CAS 失败则重试；捕获 `ConflictError` 之外不吞错误；重试上限用尽后抛出带 `attempts` 的 `ConflictError`。
- 测试（6 条）：
  1. 无冲突时一次成功，版本从 1 递增到 2；
  2. 第一次 CAS 冲突，第二次基于最新版本成功，`mutate` 被调用两次；
  3. `maxRetries: 2` 且持续冲突时共尝试 3 次，抛 `ConflictError` 且 `attempts === 3`；
  4. 两个并发更新（共享一个把 `get`/`compareAndSet` 变成异步的 store）最终两个修改都生效，计数从 0 变 2，版本递增两次；
  5. `mutate` 抛错时错误原样传播，store 的写入次数为 0；
  6. 记录不存在时抛 `NotFoundError`，不调用 `mutate`。
- 测试设计说明：第 2、3 条区分「只写一次」与「有上限重试」；第 4 条专门抓「读取后直接写」的丢失更新；第 5 条抓「把业务错误当冲突重试」；第 6 条固定失败语义。并发测试用微任务让两个调用都先读到旧版本，再让 CAS 依次执行，避免依赖真实计时。
- Python 差异：函数为 `async def update_with_retry(store, id, mutate, max_retries=3)`；store 方法为 `async def get` 与 `async def compare_and_set`；`mutate` 可以是普通函数或协程函数，统一用 `await` 调用；自定义 `ConflictError` 与 `NotFoundError`；用 `asyncio.sleep(0)` 让出事件循环即可制造交错，不需要真实延时。Python 测试同样 6 条，标记异步。
- 常见错误：
  - 读取后直接写，完全不做版本比较；
  - CAS 失败后不重新读取，拿旧快照再次写；
  - 版本号由 `mutate` 维护或忘记递增；
  - 重试没有上限，冲突时无限循环；
  - 把 `mutate` 的业务异常当成冲突重试；
  - 并发测试用真实 `setTimeout` 延迟，既慢又不稳定。

## 7. 方案题（1 题）

- 题号：`m2-tx-ex-2`
- 场景：LinkHub 要同时处理三类写入：创建短链并写审计记录；点击跳转并记录点击事件；编辑链接并写审计记录。当前实现把三类操作都塞进同一个长事务，第三方统计接口也在事务里调用，导致 P99 升高、连接池等待增加。请给出事务边界、隔离级别、失败重试、幂等与监控方案，并说明哪些操作应移出事务异步执行。
- 自检清单（9 条）：
  1. 明确「创建链接 + 审计」必须同事务，失败一起回滚；
  2. 明确点击事件在跳转链路上不能阻塞响应，改为异步/批量写入，并说明丢失与重复的取舍；
  3. 明确「更新链接 + 审计」必须放进同一事务边界，外部通知在提交后执行；
  4. 为三类写入选定隔离级别并说明理由，不默认使用最高级别；
  5. 为唯一键冲突、版本冲突与序列化失败分别给出重试上限、退避与最终失败行为；
  6. 为审计与点击事件设计幂等键或去重策略，保证重试不会写重复记录；
  7. 说明锁顺序或单行更新策略，避免死锁；
  8. 明确事务内不调用外部服务，并给出长事务的监控指标与超时；
  9. 给出可观察证据：事务时长、锁等待、连接池等待、重试次数、重复写入计数。
- 参考要点：创建 + 审计同事务；点击事件异步批量写入，跳转先返回，写入侧幂等；外部通知在提交后执行，失败进入有界重试；创建用唯一约束兜底并有限重试，更新用版本列 CAS；隔离级别按业务选择 READ COMMITTED 并显式处理冲突，只有在跨多行不变量无法用约束/锁表达时才考虑 SERIALIZABLE；重试只针对可重试错误，业务校验错误不重试；监控事务时长分布、`idle in transaction`、锁等待与池等待，而不只看平均耗时。
- 常见浅答案：把所有操作放进一个事务「保证一致」；在事务里调用第三方接口；用无限重试解决冲突；认为提高隔离级别就能消除丢失更新；只调大连接池，不缩短事务持有时长。
