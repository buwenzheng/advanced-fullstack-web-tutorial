## 1. 出口能力

1. 把 LinkHub 的业务能力拆成资源树，为每个端点写出方法、路径、成功状态码与主要错误码。
2. 判断一个 HTTP 方法是否安全、是否幂等，据此决定能否缓存、能否自动重试。
3. 为公开 API 选择版本化与弃用策略，区分破坏性变更与兼容性变更。
4. 实现路由匹配器，正确处理静态段、参数段、方法不匹配、URL 解码与重复参数名。

## 2. 学习者起点与常见误解

- 已经知道：在浏览器里发过 `fetch` 请求；用过 REST 风格的接口；知道 GET 与 POST 的大致区别；写过前端路由。
- 常见误解：
  - 「REST 就是 URL 里不要出现动词。」——资源建模是为了稳定标识与可组合，不是为了满足一条形式规则；确实没有合适名词的动作型操作可以是显式例外。
  - 「GET 和 POST 的区别就是参数在 URL 还是 body。」——更关键的是语义：是否安全、是否幂等、能否被缓存与自动重试。
  - 「接口返回 200，里面放 `{success:false}` 也算 REST。」——这会让网关、监控、SDK 与重试策略全部失效；错误应使用对应状态码。
  - 「给响应加字段一定会破坏客户端。」——兼容性取决于客户端是否忽略未知字段；真正危险的是删除字段、改类型、改含义和新增必填请求字段。
  - 「版本号放进 URL 就万事大吉。」——版本化只给你并行维护的窗口，不替代兼容性设计、弃用通知与迁移文档。
  - 「路由匹配就是从前往后遍历第一个匹配。」——静态段与参数段的优先级、方法不匹配与路径不存在是两种错误，需要分别处理。

## 3. 范围边界

- 本讲只讲：
  - 资源、集合、子资源与动作型端点的建模；
  - HTTP 方法的安全性、幂等性与状态码选择；
  - LinkHub 的资源树与公开端点表；
  - 版本化（URL/Header）与弃用策略；
  - 契约稳定性：兼容变更与破坏性变更；
  - 路由匹配器的最小实现。
- 本讲不讲：
  - 输入校验与错误信封（m2-errors）；
  - 认证、授权与多租户（m2-auth）；
  - 分页、幂等键、限流契约与 OpenAPI（m2-contract）；
  - HTTP/2、HTTP/3 的连接细节（S0）；
  - 具体框架的路由 API 与网关配置（项目与附录）。
- 与相邻讲的分工：本讲决定「有哪些端点、用什么方法和状态码」；下一讲决定「请求内容不合法时怎么拒、错误长什么样」。

## 5. 概念检查（3 题）

### C1

- ID：`m2-resource-check-1`
- 类型：single
- 标签：资源建模
- 题干：运营需要「把一批链接一次性归档」。以下哪种端点设计最符合资源建模与可演进性？
- 选项：
  - A. `POST /v1/archiveLinks`，body 里放 id 数组（错误）
  - B. `POST /v1/links/bulk-archive`，把批量动作显式建模为动作端点（可接受的例外，但不是首选）（错误）
  - C. `PATCH /v1/links`，body 里放 id 数组与 `status`（正确）
  - D. `GET /v1/links?action=archive&ids=...`（错误）
- 解析要点：归档改变的是每个链接的 `status` 字段，`PATCH /links` 以资源集合为目标、幂等且可重试；A 把动词塞进路径且非幂等；B 是动作型端点的合法例外，但能表达为资源状态变更时优先用资源；D 用 GET 产生副作用，违反安全方法语义。批量操作在真实系统中还要考虑逐条结果与部分失败，这属于后续工程化内容。
- 对应 objective：O1。

### C2

- ID：`m2-resource-check-2`
- 类型：multi
- 标签：方法语义
- 题干：关于 HTTP 方法的安全性与幂等性，以下哪些说法正确？
- 选项：
  - A. GET 是安全方法，不应产生业务副作用（正确）
  - B. PUT 是幂等方法，重复发送同一个请求的结果与发送一次相同（正确）
  - C. POST 既不安全也不幂等，重复提交可能创建多条记录（正确）
  - D. DELETE 是幂等方法，因此重复删除必须始终返回 200（错误）
  - E. PATCH 一定是幂等的，所以可以无条件自动重试（错误）
- 解析要点：安全指不改变服务端状态；幂等指多次执行的效果与一次相同，不代表响应码相同。DELETE 第二次可能返回 404 或 204，取决于契约，但资源状态一致；PATCH 是否幂等取决于补丁语义（例如「追加」不幂等）。POST 非幂等正是创建接口需要幂等键的原因。
- 对应 objective：O2。

### C3

- ID：`m2-resource-check-3`
- 类型：single
- 标签：契约变更
- 题干：LinkHub 的 `POST /v1/links` 已在第三方使用。以下哪项最可能构成破坏性变更？
- 选项：
  - A. 在响应里新增一个 `lastVisitedAt` 字段（错误）
  - B. 新增一个可选的查询参数 `fields`（错误）
  - C. 把请求体中的 `url` 从可选改为必填（正确）
  - D. 给响应中的 `status` 枚举新增一个 `archived` 值（错误）
- 解析要点：新增响应字段与可选参数通常兼容（客户端应忽略未知字段）；枚举新增值对「穷举所有值」的客户端有风险，但通常可接受并需要通知；把可选请求字段改为必填会让现有合法请求立刻失败，是最典型的破坏性变更。删除字段、改类型、改字段含义同属破坏性变更。
- 对应 objective：O3。

## 6. 代码题（1 题）

- 题号：`m2-resource-ex-1`
- 标题：路由匹配器
- 业务场景：LinkHub 的 API 路由表需要一个小型匹配器，用于网关与契约测试共用。它要能区分「路径不存在」与「路径存在但方法不允许」，并把参数段解码后交给处理函数。
- 契约：
  - `matchRoute(routes, method, path)`，`routes` 是 `{ method, path }` 数组，`path` 形如 `/v1/links/:id/clicks`。
  - 命中返回 `{ route, params }`，`params` 只包含参数段，值为 `decodeURIComponent` 后的字符串。
  - 路径能匹配但方法不匹配时返回 `{ error: 'method_not_allowed', allowed: [...] }`，`allowed` 去重后按字母序排列。
  - 路径不存在返回 `{ error: 'not_found' }`。
  - 方法比较不区分大小写；路径按 `/` 分段，忽略末尾单个斜杠（根路径除外）；段数必须相等。
  - 参数段必须非空；同一路由内参数名重复时抛出 `Error`，消息包含 `duplicate param`。
  - 百分号编码非法导致解码失败时返回 `{ error: 'bad_request' }`。
- starter 要点：只做字符串全等与第一个参数段替换；405 合并进 not_found；不处理尾斜杠和解码。
- solution 要点：先按段数与静态/参数逐段匹配收集候选；路径命中集合为空返回 not_found；再在命中集合里找方法；方法不存在时汇总 allowed；解码失败捕获 `URIError`。
- 测试（6 条）：
  1. 静态路径命中，`params` 为空对象；
  2. 参数路径命中，`id` 被解码（`a%20b` → `a b`）；
  3. 路径存在但方法不匹配，返回 `method_not_allowed` 与去重排序后的 `allowed`；
  4. 路径不存在返回 `not_found`，不得误报 405；
  5. 尾斜杠与大小写方法可命中；
  6. 同一路由重复参数名抛错，非法百分号编码返回 `bad_request`。
- 测试设计说明：第 3、4 条抓「所有失败都当 404」；第 5 条抓「实现只支持精确字符串」；第 6 条固定错误语义。测试全部纯函数，无网络与时间依赖。
- Python 差异：函数为 `match_route(routes, method, path)`；使用 `urllib.parse.unquote`，它默认不抛异常，遇到非法编码需要先检查 `%` 后是否跟两位十六进制，再决定返回 `bad_request`；`allowed` 用 `sorted(set(...))`；重复参数抛 `ValueError`。测试同样 6 条。
- 常见错误：
  - 先遍历方法再匹配路径，导致路径不存在时误报 405；
  - 参数段允许为空，`/links//clicks` 被错误命中；
  - 不解码或重复解码；
  - 405 不返回 `allowed`，调用方无法自助修复；
  - 尾斜杠处理不一致，`/links/` 与 `/links` 行为漂移；
  - 重复参数名静默覆盖。

## 7. 方案题（1 题）

- 题号：`m2-resource-ex-2`
- 场景：LinkHub 要从内部脚本升级为第三方可用的公开 API。现有端点包括创建短链、跳转、列表、编辑、删除、查看点击统计；内部实现有 `POST /createLink`、`GET /getLinks`、`POST /deleteLink` 这类风格。请给出资源树、方法、状态码、版本化与弃用方案。
- 自检清单（8 条）：
  1. 列出资源树，集合与单体路径成对出现；
  2. 每个端点标注方法、成功状态码与至少两个错误码；
  3. 区分安全方法与幂等方法的缓存/重试策略；
  4. 跳转端点说明为什么用 302 而不是 301；
  5. 说明版本化位置（URL 前缀/Header）与并行维护窗口；
  6. 给出弃用通知方式（响应头/文档/邮件）与移除条件；
  7. 列出至少三项兼容变更与三项破坏性变更；
  8. 给出契约测试要覆盖的公开字段与错误码。
- 参考要点：资源树以 `/v1/links` 为中心，`/v1/links/:id/clicks` 作为子资源；创建 201 + Location，删除 204，校验失败 400/422，未认证 401，无权限 403，不存在 404，方法不允许 405 + Allow；跳转目标可修改，默认 302；版本放 URL 前缀便于网关与文档分流，代价是路径冗余；弃用先双写/双读再发通知，观察调用方迁移后再移除；兼容变更包括新增响应字段、新增可选参数、新增错误码；破坏性变更包括删除字段、改类型、改含义、新增必填请求字段。
- 常见浅答案：只把 URL 改成名词就算 REST；所有响应都 200；版本化等于复制一份代码永不删除；弃用只在文档里写一句。
