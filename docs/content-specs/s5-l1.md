## 2. 学习者起点与常见误解

- 已经知道：分层目录、`import` 依赖、API 契约。
- 常见误解：
  - 「微服务一定比单体先进。」——服务化把函数调用换成网络调用，引入部分失败与数据一致性问题。
  - 「按 controller/service/repository 分层就是模块化。」——技术层不是业务边界，改一个功能仍要跨层修改。
  - 「目录分开就没有循环依赖。」——运行时调用与数据共享仍可能成环。
  - 「拆得越细越好。」——团队规模、发布频率与一致性要求决定粒度。
  - 「共享数据库只是暂时的。」——共享数据库通常是边界没画清的信号。

## 3. 范围边界

## 6. 代码题：依赖方向与环检测

契约：`analyzeGraph(graph, rules)`。

- `graph`：`{ module: [dependency, ...] }`，允许依赖未在键中出现的模块（视为叶子）。
- `rules`：`[{ id?, name, forbid: [module, ...] }]`，表示 `name` 不允许直接依赖 `forbid` 中的模块。
- 返回 `{ cycles, violations }`：
  - `cycles`：环路径数组，首尾模块相同（如 `['a','b','a']`）；自依赖为 `['a','a']`；同一环只报告一次；按路径字典序排序。
  - `violations`：`[{ from, to, rule }]`，按规则顺序与依赖顺序稳定输出。
- 环检测用 DFS 三色标记；不要把「已访问」当成「已完成」。

测试（7）：无环；直接环；间接环；自依赖；分层违规；未知模块与未知规则不崩溃；多环只报一次且顺序稳定。

Python 差异：用 `dict`/`list`，DFS 三色；环路径为 `list`，排序用 `sorted`；不依赖第三方库。

## 7. 方案题：LinkHub 模块边界

自检清单（9）：业务能力；数据归属；依赖方向；同步/异步；共享内核；拆分收益；拆分代价；迁移路径；不拆的理由。

参考要点：先模块化单体；统计服务可以独立（p5），API 与 Web 不一定要拆；共享数据库是边界没画清的信号；拆分前先用依赖图与变更频率找证据。
