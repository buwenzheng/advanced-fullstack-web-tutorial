## 1. 出口能力

1. 解释 at-most-once、at-least-once 与「精确一次」的工程含义，判断一条链路需要哪种保证。
2. 实现 ack、可见性超时、重试退避、死信与幂等消费，并说明每个机制的失败表现。
3. 诊断积压、毒消息与消费者不足，给出扩容、限流与重放的处理顺序。
4. 为 LinkHub 点击事件设计一条可恢复的异步链路，并写清与 p-e1-stats Outbox/RabbitMQ 的升级边界。

## 2. 学习者起点与常见误解

- 已经知道：前端事件循环、`setTimeout`、Promise 队列；HTTP 请求失败会重试；数据库事务的基本概念。
- 常见误解：
  - 「消息队列保证消息只处理一次。」——多数队列提供至少一次投递；「只处理一次」要靠消费端幂等。
  - 「先 ack 再处理，失败了重试就行。」——ack 后进程崩溃，消息不会再投递，副作用直接丢失。
  - 「重试次数越多越可靠。」——毒消息会无限占用消费者；重试必须有上限、退避与死信。
  - 「队列积压就加消费者。」——先看入队速率、出队速率、单条处理耗时与毒消息；盲目扩容可能打垮下游数据库。
  - 「消息顺序一定和发送顺序一致。」——并发消费者、重试与分区都会影响顺序；需要顺序时要说清范围与代价。
  - 「用 BullMQ 就等于解决了双写一致性。」——入队与业务提交仍是两次写；Outbox 在 e1-consistency，p-e1-stats 才升级。

## 3. 范围边界

- 本讲只讲：
  - 生产者/队列/消费者模型、ack、可见性超时、重试、死信；
  - 至少一次投递与幂等消费；
  - 积压诊断与消费者扩容；
  - BullMQ、RabbitMQ、Kafka 的概念差异（不写产品教程）；
  - LinkHub 点击事件链路与 p-m3-ship 的实现范围。
- 本讲不讲：
  - Outbox、Saga 与最终一致（e1-consistency）；
  - 分布式事务与跨服务一致性协议（s5）；
  - Kafka 分区、副本与运维参数（基础设施附录）；
  - 具体产品的安装、配置与 Dashboard 教程。
- 与相邻讲的分工：本讲用应用内队列把「慢活」移出请求链路；e1-consistency 解决「入队与业务提交两次写」的窗口；p-e1-stats 才把队列升级为独立服务。

## 5. 概念检查（3 题）

### C1

- ID：`m3-queue-check-1`
- 类型：单选
- 考点：消费者处理成功但 ack 前崩溃
- 正确项：消息在可见性超时后重新投递，消费者可能再次执行同一事件
- 解析要点：ack 是「处理完成」的确认；未 ack 就有重投；再次执行需要幂等；ack 后崩溃则副作用丢失。

### C2

- ID：`m3-queue-check-2`
- 类型：多选
- 考点：幂等消费需要哪些条件
- 正确项：稳定的事件 ID；持久化的去重记录；处理与记录在同一事务或可补偿；数据库唯一约束兜底
- 解析要点：只靠内存 Set 在重启后失效；用 payload 哈希可能因字段顺序不稳定；先 ack 后记录会丢。

### C3

- ID：`m3-queue-check-3`
- 类型：单选
- 考点：队列积压且消费速率低，先看什么
- 正确项：入队速率、出队速率、单条处理耗时与毒消息，再决定扩容或限流
- 解析要点：盲目加消费者可能压垮下游；毒消息会占满重试；先止损再扩容，最后重放。

## 6. 代码题：可见性超时队列 + 幂等消费者

- 契约：
  - `createQueue({ visibilityTimeout = 1000, maxAttempts = 3, now = () => Date.now() } = {})`
    - `enqueue(payload)` → 返回消息 id；
    - `reserve()` → `{ id, payload, attempt }` 或 `null`；只返回可见消息；超时未 ack 的消息重新可见；
    - `ack(id)` → 成功确认；
    - `nack(id)` → 立即重新可见；attempt 已达 `maxAttempts` 时进入死信；
    - 超时重投时 attempt 也递增，达到上限进入死信；
    - `deadLetters()` → 死信数组副本。
  - `consume(queue, handler, processed)`：异步；`processed` 是去重 Set；以 `payload.eventId` 为幂等键；重复事件直接 ack 并返回 `{ duplicate: true }`；handler 成功后写入 processed 并 ack；失败 nack，不写入 processed。
- 测试（≥7）：
  1. 正常 ack 后不再投递；
  2. 未 ack 超过可见性超时后重投，attempt 递增；
  3. nack 后立即重投；
  4. 达到 maxAttempts 进入死信，reserve 返回 null；
  5. 相同 eventId 重复投递只执行一次副作用；
  6. 空队列 reserve 返回 null；
  7. handler 失败不 ack，消息可再次 reserve。
- 测试设计说明：注入 `now` 变量推进时间；第 5 条用两次 `enqueue` 同一 eventId 模拟重复投递；第 7 条断言 `processed` 未写入且消息可重投；第 4 条同时断言 `deadLetters()` 含消息。
- Python 差异：同步版本即可；用 `time` 注入毫秒整数；`consume` 用 `async def`，handler 可为普通函数或协程（用 `inspect.isawaitable` 兼容）；去重使用 `set` 或持久化存储接口；`None` 表示空队列。
- 常见错误：ack 在 handler 之前；重投不递增 attempt；去重键用不稳定的 payload 哈希；DLQ 只能写不能读；失败也写入 processed。

## 7. 方案题：LinkHub 点击事件链路

场景：跳转接口要在 50ms 内返回重定向；点击统计允许秒级延迟，但不能丢；消费者随 API 进程部署，后续可能独立扩容。

自检清单（≥6）：

- [ ] 事件 ID 的生成位置与稳定性；
- [ ] 幂等键与去重存储（内存/数据库/Redis）；
- [ ] ack 时机与失败处理；
- [ ] 重试次数、退避与抖动；
- [ ] 死信、告警与重放工具；
- [ ] 顺序要求与范围；
- [ ] 消费者扩容与下游保护；
- [ ] 监控指标（积压、处理耗时、失败率、DLQ）；
- [ ] 与 p-e1-stats Outbox/RabbitMQ 的升级边界。

参考要点：p-m3-ship 用 BullMQ 把点击写入移出请求链路；事件在 API 侧生成稳定 `eventId`；消费者以 `eventId` 去重并落库；成功后才 ack；失败指数退避，超过次数进 DLQ 并告警；重放工具从 DLQ 读回；入队与业务提交仍是两次写，p-e1-stats 用 Outbox 消除双写窗口，不重复实现。
