## 1. 出口能力

1. 用唯一、CHECK、外键与部分唯一索引表达业务不变量，解释每条约束在防哪种非法状态。
2. 写出带版本、校验和、可逆 down 的迁移，并说明为什么「已应用的迁移不能改写」。
3. 设计 expand-contract 的零停机变更：加可空列、分批回填、双写、收紧约束、清理旧路径，每一步都能独立回滚。
4. 从空库与旧版库各跑一次迁移并验证结果，能识别会锁表、长时间回填或不可逆的破坏性迁移。

## 2. 学习者起点与常见误解

- 已经知道：TypeScript 类型、JSON 对象、SQL 的建表与约束、索引的基本作用、事务的提交与回滚。
- 常见误解：
  - 「TypeScript 类型已经保证了数据正确。」——类型只在编译期与进程内生效，数据库会被多个服务、脚本与并发请求写入。
  - 「软删除后 slug 还能唯一，直接给 slug 建唯一索引就行。」——唯一索引会把已删除行也算进去，导致 slug 不能复用；需要只约束未删除行的部分唯一索引或等价方案。
  - 「迁移只要 up 能跑就行，down 以后再说。」——没有 down 与备份的迁移在出错时只能手工救火；已应用的迁移被改写会让不同环境的 schema 悄悄分叉。
  - 「加一个带默认值的 NOT NULL 列总是瞬间完成。」——是否重建表取决于数据库、版本与默认值类型；大表上仍可能长时间持锁。
  - 「迁移框架会自动保证零停机。」——框架只负责执行顺序与记录，锁级别、回填批次与双写窗口仍要设计。
  - 「种子数据只是测试数据，放点生产密钥方便联调。」——种子会进入仓库与所有环境，密钥必须由环境注入。
  - 「约束会影响写入性能，能少加就少加。」——约束是把不变量放在数据库层的最后防线，缺少约束会把数据修复成本推给未来。

## 3. 范围边界

- 本讲只讲：
  - 唯一、CHECK、外键、部分唯一索引与软删除下的唯一性；
  - LinkHub 三张表的约束清单与失败表现；
  - 版本化迁移的生命周期、校验和、重复版本与失败回滚；
  - expand-contract 零停机变更的步骤与回滚点；
  - 长事务回填、在线 DDL 与锁级别的直觉；
  - 种子数据的可重复执行与密钥边界。
- 本讲不讲：
  - 分库分表、跨库迁移与数据同步（S5）；
  - 数据库存储引擎与页结构（a3）；
  - 备份恢复、容灾演练（S6）；
  - 具体迁移框架的 API 细节（正文只给最小运行器与通用原则）。
- 与相邻讲的分工：
  - `s1-l1` 讲表与查询，`s1-l2` 讲索引，`s1-l3` 讲事务与锁；本讲把它们组合成「可演进、可回滚」的 schema 变更流程。
  - 迁移过程中的并发控制细节复用 `s1-l3`，不重复讲隔离级别。

## 5. 概念检查（3 题）

### C1

- ID：`s1-schema-check-1`
- 类型：single
- 标签：软删除唯一
- 题干：LinkHub 的 `links` 使用软删除（`deleted_at` 为空表示有效），要求有效链接的 slug 唯一，但删除后的 slug 可以复用。最直接的约束方案是什么？
- 选项：
  - A. 在 `slug` 上建普通唯一索引，删除时把 slug 改成随机值（错误）
  - B. 在 `(tenant_id, slug)` 上建部分唯一索引，条件为 `deleted_at IS NULL`（正确）
  - C. 在 `(slug, deleted_at)` 上建唯一索引，依赖 NULL 互不相等（错误）
  - D. 只在应用层查询是否存在同 slug 的有效链接，然后插入（错误）
- 解析要点：部分唯一索引只约束未删除行，允许删除后复用；改写 slug 会破坏历史可读性与外部引用；`(slug, deleted_at)` 在 `deleted_at` 为 NULL 时无法阻止多条有效行重复（PostgreSQL 中 NULL 互不相等），而 MySQL 等实现行为又不同；应用层先查后插存在并发窗口。其他数据库若不支持部分索引，需要生成列或独立活动表等等价方案。
- 对应 objective：O1。

### C2

- ID：`s1-schema-check-2`
- 类型：multi
- 标签：危险迁移
- 题干：以下哪些迁移属于高风险或破坏性操作？
- 选项：
  - A. 没有备份与回滚方案，直接删除正在使用的列（正确）
  - B. 在一个事务里对大表全量回填千万行（正确）
  - C. 迁移没有 down，且没有人工回滚脚本（正确）
  - D. 先把生产密钥写进 `seed.sql`，方便所有环境联调（正确）
  - E. 先加可空列、分批回填、再加约束（错误）
- 解析要点：删列会丢失数据且旧代码可能仍在读；长事务回填会持锁、放大日志并阻塞清理；没有 down 与回滚脚本会把恢复成本推给事故现场；种子进入仓库会泄露密钥；可空加列 + 分批回填 + 收紧约束是标准的兼容路径，不属于破坏性操作。
- 对应 objective：O4。

### C3

- ID：`s1-schema-check-3`
- 类型：single
- 标签：expand-contract
- 题干：给已有数据的 `links` 表新增 `tenant_id NOT NULL`，要求不停机。正确的顺序是什么？
- 选项：
  - A. 直接 `ALTER TABLE ... ADD COLUMN tenant_id NOT NULL DEFAULT ...`，然后上线新代码（错误）
  - B. 加可空列 → 分批回填 → 应用双写 → 加 NOT NULL/约束 → 删除旧路径（正确）
  - C. 先删除旧列 → 停机导入 → 再建新表（错误）
  - D. 在事务里一次回填全部数据，再提交（错误）
- 解析要点：直接加 NOT NULL 可能在大表上长时间持锁或依赖默认值行为；可空列 + 分批回填让旧代码继续工作；双写覆盖切换窗口；收紧约束前先验证数据；最后才清理旧路径。一次回填全部数据会形成长事务，阻塞写入与清理。
- 对应 objective：O3。

## 6. 代码题（1 题）

- 题号：`s1-schema-ex-1`
- 标题：可回滚迁移运行器
- 业务场景：LinkHub 的 schema 会持续演进，团队需要一个小型迁移运行器：按版本执行、跳过已应用、校验迁移内容未被改写、失败时回滚当前迁移、支持逆序回滚。
- 契约：
  - `createMigrator({ migrations, store })` 返回 `{ up, down }`。
  - `migration`：`{ version, name, sql, up, down }`；`version` 为正整数且唯一；`sql` 是用于校验和的稳定文本；`up(tx)` / `down(tx)` 为异步函数。
  - `store.applied()`：返回已应用记录 `[{ version, checksum }]`，按版本升序。
  - `store.transaction(fn)`：开启事务并调用 `fn(tx)`；成功提交，抛错回滚；`tx.record(version, checksum)` 记录版本，`tx.remove(version)` 删除记录。
  - `up()`：按版本升序执行未应用迁移；执行前校验已应用记录的 checksum；任一迁移失败则中止，当前事务回滚，后续迁移不执行。
  - `down()`：按已应用版本逆序执行 `down`；每步在事务中执行并删除记录；失败则中止并回滚当前事务。
  - 重复版本在创建 migrator 时抛 `DuplicateVersionError`；已应用记录找不到对应迁移抛 `UnknownMigrationError`；checksum 不匹配抛 `ChecksumMismatchError`。
  - Node 环境使用确定性字符串哈希（FNV-1a 32 位）做教学校验和；生产环境应使用 SHA-256 或迁移文件内容哈希。
- starter 要点：把 migrations 原样排序后全部执行；不读取 applied；不校验 checksum；不检测重复版本；失败后继续执行后续迁移。
- solution 要点：创建时按版本排序并检测重复；`up` 先读取 applied 并逐条校验 checksum；用 `Set` 跳过已应用；每个迁移包在 `store.transaction` 中；失败自然中止；`down` 取 applied 的版本逆序，调用 `down` 后 `remove`。
- 测试（6 条）：
  1. 空库按版本升序执行全部迁移，记录写入顺序正确；
  2. 已应用迁移 checksum 一致时跳过，第二次 `up()` 不重复执行；
  3. 已应用记录的 checksum 不匹配时拒绝执行，任何迁移都不运行；
  4. 创建 migrator 时重复版本立即抛 `DuplicateVersionError`；
  5. 第二个迁移 `up` 抛错时中止，当前事务回滚，记录只保留第一个迁移，第三个不执行；
  6. `down()` 按版本逆序执行；第三个迁移 `down` 抛错时停止，当前事务回滚，记录不丢失。
- 测试设计说明：第 2 条区分「每次全跑」与「按 applied 跳过」；第 3、4 条分别抓校验和与重复版本；第 5、6 条验证失败中止与事务回滚；测试用内存 store 快照实现事务，不依赖真实数据库。
- Python 差异：使用 `class Migrator` 与 `create_migrator(migrations, store)`；迁移为字典，`up`/`down` 为协程函数；`hashlib.sha256` 计算校验和；store 的 `transaction` 为异步上下文；测试同样 6 条并标记异步。
- 常见错误：
  - `down` 按升序执行，先删基础表导致后续回滚失败；
  - 迁移失败后仍写入版本记录，下一次启动误以为已应用；
  - checksum 只存在内存或完全不校验，环境之间 schema 悄悄分叉；
  - 不检测重复版本，`Map` 覆盖导致某个迁移永远不执行；
  - 把「已应用但找不到迁移文件」当成正常情况跳过。

## 7. 方案题（1 题）

- 题号：`s1-schema-ex-2`
- 场景：`links` 表已有数百万行数据，需要新增 `tenant_id NOT NULL` 并回填，要求不停机、可回滚，且旧版本应用在新 schema 上仍能工作。请给出完整变更方案，包括每一步的验证与回滚点。
- 自检清单（8 条）：
  1. 先加可空列，旧代码不需要修改即可继续读写；
  2. 回填按主键或时间分批，可重入、可断点续跑，不形成长事务；
  3. 应用层双写或默认值策略覆盖切换窗口；
  4. 约束收紧顺序明确：先校验数据，再 `NOT NULL` / 约束，必要时使用 `NOT VALID` 后验证；
  5. 索引创建方式考虑锁与写入影响，说明数据库差异；
  6. 给出每一步的回滚动作与旧代码兼容性；
  7. 给出监控指标：回填进度、锁等待、错误率、复制延迟（如适用）；
  8. 给出数据校验：行数、空值计数、抽样对比与最终一致性检查。
- 参考要点：加可空列 → 分批回填（带重试与进度记录）→ 应用双写 → 校验无空值 → 加 NOT NULL/约束（大表先用 `NOT VALID` 再 `VALIDATE`）→ 建索引（在线方式或低峰执行）→ 删除旧路径。每一步都能独立回滚；回填脚本必须幂等；不要在一个事务里更新全表；监控锁等待与回填进度，失败时暂停而不是回滚全部已完成批次。
- 常见浅答案：直接 `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...`；在一个事务里全量回填；先删旧列再迁移；不说明索引与约束的锁；没有回滚点与数据校验。
