## 1. 出口能力

1. 区分认证与授权，为 Web、移动端与服务端调用选择 Session、JWT、Refresh Token 或 API Key。
2. 设计 RBAC/ABAC 权限模型，写清 owner、admin、租户成员与跨租户访问的判断顺序。
3. 在数据访问层实施租户隔离，识别 IDOR 与「客户端传 tenantId」的漏洞。
4. 说明 token 存储、轮换、撤销与 CSRF/XSS 的边界，知道完整防护属于哪一讲。

## 2. 学习者起点与常见误解

- 已经知道：Cookie 与 localStorage 的基本用法；前端路由守卫；JWT 由三段字符串组成；HTTPS 能加密传输。
- 常见误解：
  - 「前端路由守卫拦住页面，接口就安全了。」——攻击者直接调用接口，不经过你的前端；服务端必须逐请求认证与授权。
  - 「JWT 自带用户信息，所以不用查库。」——JWT 只证明签发者与内容未被篡改，权限变更与封禁不会自动生效，需要短过期、版本号或撤销机制。
  - 「把 token 放 localStorage 最方便。」——任何 XSS 都能读走；HttpOnly Cookie 能降低读取风险，但需要处理 CSRF。
  - 「请求里带 tenantId，后端照着查就行。」——租户标识必须来自服务端认证上下文，客户端传入的 tenantId 只能用于校验，不能作为信任来源。
  - 「管理员什么都能做。」——跨租户读取与跨租户写入要分开授权；平台管理员与租户管理员不是同一个角色。
  - 「Refresh Token 长期有效，省得用户重新登录。」——长期不轮换的 refresh token 一旦泄漏就是长期访问权；轮换与重用检测是常见要求。

## 3. 范围边界

- 本讲只讲：
  - 认证（Authentication）与授权（Authorization）的区别；
  - Session、JWT、Refresh Token、API Key 的适用场景与撤销能力；
  - RBAC/ABAC/ReBAC 的取舍；
  - 租户隔离与 IDOR；
  - token 存储、轮换、重用检测与撤销边界；
  - 认证/授权测试矩阵。
- 本讲不讲：
  - 完整 CSP、CSRF token 实现与 XSS 防御清单（S6）；
  - OAuth 2.0/OpenID Connect 的完整授权码流程与具体身份提供商；
  - 密码哈希算法参数与账户体系产品设计；
  - 网关与服务网格的鉴权插件配置。
- 与相邻讲的分工：上一讲定义错误契约；本讲定义「谁在调用、能做什么、能看哪个租户的数据」，错误码沿用 401/403。

## 5. 概念检查（3 题）

### C1

- ID：`s2-l3-check-1`
- 类型：single
- 标签：401 与 403
- 题干：用户 A 已登录，携带有效 token 请求删除同租户用户 B 的链接。服务端应返回什么？
- 选项：
  - A. 401，因为没有权限（错误）
  - B. 403，因为已认证但无权执行该操作（正确）
  - C. 404，因为链接不属于 A（错误）
  - D. 200，但响应体里写 failed（错误）
- 解析要点：401 表示未认证或凭证无效；403 表示身份已确认但授权失败。404 可以用于隐藏资源存在性，但要在契约中统一；200 会破坏监控与 SDK。删除他人链接属于同租户内的权限问题，应 403。
- 对应 objective：O1、O2。

### C2

- ID：`s2-l3-check-2`
- 类型：multi
- 标签：凭证与撤销
- 题干：关于 Session、JWT、Refresh Token 与 API Key，以下哪些说法正确？
- 选项：
  - A. 服务端 Session 可以在服务端删除，从而立即失效（正确）
  - B. JWT 默认在过期前无法撤销，需要短过期或额外的撤销机制（正确）
  - C. Refresh Token 轮换后，旧 token 再次出现可以视为泄漏信号（正确）
  - D. API Key 应该与用户密码使用同一套登录流程（错误）
  - E. 把 JWT 放进 localStorage 后，XSS 也无法读取（错误）
- 解析要点：Session 的状态在服务端，删除即失效；JWT 是自包含凭证，签发后默认不可撤销；refresh token 轮换与重用检测是常见防护；API Key 是机器凭证，通常单独签发、撤销与限权；localStorage 可被同源 JS 读取，XSS 可直接窃取。
- 对应 objective：O1、O4。

### C3

- ID：`s2-l3-check-3`
- 类型：single
- 标签：租户隔离
- 题干：`GET /v1/links/:id` 的实现是 `SELECT * FROM links WHERE id = $1`，租户 ID 只用于页面展示。最可能的风险是什么？
- 选项：
  - A. 查询变慢，因为缺少索引（错误）
  - B. 跨租户读取（IDOR）：猜到 id 就能读到其他租户的数据（正确）
  - C. 只有管理员能利用，普通用户不受影响（错误）
  - D. 只要前端不显示 tenantId 就不会泄漏（错误）
- 解析要点：租户隔离必须进入数据访问条件，`WHERE tenant_id = $1 AND id = $2`；前端隐藏字段不构成安全边界；IDOR 是对象级授权缺失，任何能构造请求的调用方都可能利用；修复后还要补跨租户测试。
- 对应 objective：O3。

## 6. 代码题（1 题）

- 题号：`s2-l3-ex-1`
- 标题：授权决策函数
- 业务场景：LinkHub 的接口层需要一个纯函数，把「当前用户 + 动作 + 资源」映射为允许或拒绝，并给出稳定原因，供日志与测试使用。
- 契约：
  - `authorize({ user, action, resource })` 返回 `{ allowed, reason }`。
  - `user` 为 `null` 表示匿名；`action` 取 `read`、`write`、`delete`；`resource` 含 `{ id, ownerId, tenantId, visibility }`。
  - 未知 action 返回 `{ allowed: false, reason: 'unknown_action' }`。
  - 匿名只能读 `visibility === 'public'` 的资源，返回 `public_read`；否则 `authentication_required`。
  - 租户不一致时：`admin` 的 `read` 允许（`platform_read`）；其他动作或非 admin 一律拒绝 `tenant_mismatch`。
  - 同租户内：owner 可 read/write/delete（`owner`）；admin 可 read/write/delete（`admin`）；其他用户 read 允许（`member_read`），write/delete 拒绝 `not_owner`。
  - 资源缺失返回 `{ allowed: false, reason: 'not_found' }`。
- starter 要点：只判断 `user.role === 'admin'` 和 owner，忽略租户与 action，默认放行。
- solution 要点：按「资源存在 → action 合法 → 匿名 → 租户校验 → owner/admin/member」的顺序判断，保证每个分支返回稳定 reason。
- 测试（7 条）：
  1. 匿名读公开资源允许；
  2. 匿名读私有资源拒绝 `authentication_required`；
  3. owner 写自己的资源允许；
  4. admin 跨租户读允许 `platform_read`；
  5. admin 跨租户写拒绝 `tenant_mismatch`；
  6. 同租户非 owner 写拒绝 `not_owner`，读允许 `member_read`；
  7. 未知 action 与缺失资源分别拒绝。
- 测试设计说明：第 4、5 条抓「admin 全放行」；第 6 条抓「同租户就放行」；第 7 条固定兜底语义。纯函数，无时间与网络依赖。
- Python 差异：函数为 `authorize(user, action, resource)`，返回 dict；`user` 用 `None` 表示匿名；判断顺序一致；测试 7 条。
- 常见错误：先判断 owner 再判断租户；把 admin 当成跨租户可写；匿名直接拒绝所有读；未知 action 默认放行；reason 随分支漂移。

## 7. 方案题（1 题）

- 题号：`s2-l3-ex-2`
- 场景：LinkHub 要从单租户内部工具变成多租户 SaaS。现有接口只按 id 查询，token 放在 localStorage，JWT 有效期 30 天且没有刷新机制；管理员可以查看所有数据。请给出认证、授权、租户隔离、token 生命周期与测试方案。
- 自检清单（8 条）：
  1. 明确 Web、移动端、服务端集成分别用什么凭证；
  2. 写清登录、刷新、登出与撤销路径；
  3. 定义角色与权限矩阵，区分平台管理员与租户管理员；
  4. 规定 tenantId 只来自认证上下文；
  5. 规定数据访问层的强制过滤与唯一约束；
  6. 给出 token 存储位置与 CSRF/XSS 边界；
  7. 给出 refresh token 轮换、重用检测与全家族撤销策略；
  8. 给出测试矩阵：匿名、成员、owner、admin、跨租户、过期、撤销。
- 参考要点：Web 用 HttpOnly + Secure + SameSite Cookie 或短 JWT + refresh；移动端用安全存储；服务端用 API Key 并限权。JWT 短过期 + refresh 轮换；撤销用版本号或黑名单。授权按资源与动作判断，平台 admin 读跨租户但写仍受限。租户过滤在仓储层强制，数据库唯一约束带 tenant_id。测试覆盖 401/403 与跨租户 IDOR。
- 常见浅答案：JWT 放 localStorage；token 有效期一个月；admin 全放行；只在前端隐藏 tenantId；不做撤销与轮换。
