## 1. 出口能力

1. 把 LinkHub 的用户、短链、点击事件映射成带主键、外键与约束的表，并说明每个约束在防什么。
2. 写出 `INNER JOIN`、`LEFT JOIN`、分组聚合与时间窗口查询，能解释 `COUNT(*)` 与 `COUNT(column)` 的差异。
3. 在规范化、反规范化与 JSONB 之间做有理由的取舍，说明一致性、查询与写入的代价。
4. 解释 NULL 三值逻辑与 `NOT IN` 的陷阱，能用测试或查询结果证明判断。

## 2. 学习者起点与常见误解

- 已经知道：JavaScript 对象与数组、`Array.prototype.filter/map`、TypeScript 类型、localStorage 的基本使用。
- 常见误解：
  - 「数据库表就是 JSON 数组，字段想加就加。」——表结构、类型与约束在运行期生效，还会面对并发写入。
  - 「外键只是文档要求，应用里校验就够了。」——应用校验与并发写入之间有时间窗，约束是最后一道防线。
  - 「`COUNT(*)` 和 `COUNT(column)` 一样。」——前者数行，后者忽略 NULL；在 LEFT JOIN 下差异会直接改变统计口径。
  - 「把过滤条件写在 `WHERE` 里和写在 `ON` 里一样。」——写在 `WHERE` 可能把 LEFT JOIN 退化成 INNER JOIN。
  - 「字段全塞进 JSONB 最灵活。」——灵活意味着约束、索引与查询能力要自己补，且不同数据库的 JSON 类型行为不同。
  - 「NULL 等于空字符串或 0。」——NULL 表示未知，任何与 NULL 的比较都不成立，只能用 `IS NULL` 判断。

## 5. 概念检查（3 题）

### C1

- ID：`s1-l1-check-1`
- 类型：single
- 题干：`click_events` 表的主键与外键应该怎么选？
- 选项：
  - A. 主键用 `(link_id, clicked_at)` 复合主键，不需要额外列（错误）
  - B. 自增或 UUID 主键，`link_id` 外键引用 `links.id`，并为 `link_id`、`clicked_at` 建索引（正确）
  - C. 主键用 `user_id`，因为一个用户只产生一条点击（错误）
  - D. 不建外键，靠应用在写入前校验链接存在（错误）
- 解析要点：`(link_id, clicked_at)` 在同一毫秒可能重复，不能保证唯一；点击事件属于链接而不是用户；应用校验与写入之间存在并发窗口，外键是数据库层的完整性约束。
- 对应 objective：O1。

### C2

- ID：`s1-l1-check-2`
- 类型：multi
- 题干：关于 JOIN 与聚合，以下哪些说法正确？
- 选项：
  - A. `LEFT JOIN` 后使用 `COUNT(*)`，未匹配的右表空行也会被算成 1（正确）
  - B. `COUNT(c.id)` 忽略 NULL，适合统计右表的实际匹配行数（正确）
  - C. 把右表的过滤条件写在 `WHERE` 里，可能把 `LEFT JOIN` 退化成 `INNER JOIN`（正确）
  - D. `GROUP BY` 后可以随意选择未聚合、未分组的列，所有数据库都允许（错误）
  - E. `INNER JOIN` 会保留左表中没有匹配的行（错误）
- 解析要点：`COUNT(*)` 数行，`COUNT(column)` 数非 NULL；`WHERE` 在连接结果上过滤，右表为 NULL 的行不满足条件会被移除；标准 SQL 要求 SELECT 列出现在 GROUP BY 中或被聚合；INNER JOIN 只保留匹配行。
- 对应 objective：O2。

### C3

- ID：`s1-l1-check-3`
- 类型：single
- 题干：LinkHub 的标签应该用 JSONB 数组还是关联表，主要取决于什么？
- 选项：
  - A. 前端是否使用 TypeScript（错误）
  - B. 是否需要按标签反查链接、统计标签使用量，以及强制标签唯一（正确）
  - C. 数据库是否有自增主键（错误）
  - D. 标签数量是否超过 10 个（错误）
- 解析要点：需要反查、统计与唯一约束时，关联表与索引更直接；JSONB 适合读多写少、整体读取且不需要强约束的场景，但反查与唯一性要额外处理。标签数量不是决定因素。
- 对应 objective：O3。

## 6. SQL 题（1 题）

- 题号：`s1-l1-ex-1`
- 标题：七天内每个链接的点击数
- 业务场景：LinkHub 的运营面板要看到「每个用户的每条链接在最近 7 天有多少点击」，没有点击的链接也要显示 0，否则无法判断哪些链接需要下架。
- 数据：`users` 4 行、`links` 5 行、`click_events` 9 行；包含 0 点击链接、窗口外点击、起始边界、结束边界与 `clicked_at` 为 NULL 的事件。
- 时间窗口：`2026-11-02T00:00:00Z`（含）到 `2026-11-09T00:00:00Z`（不含）。
- 输出：`user_id, link_id, clicks`；按 `user_id` 升序、`clicks` 降序、`link_id` 升序。
- 判定口径：
  - 每个用户×链接一行，包括点击数 0 的行；
  - `clicks` 只统计窗口内、`clicked_at` 非 NULL 的事件；
  - 起始边界计入，结束边界不计入；
  - 结果集精确匹配，行顺序固定。
- 正确解要点：从 `users` LEFT JOIN `links`，再 LEFT JOIN `click_events`，把两个时间条件写在第二个 `ON` 里，`COUNT(c.id)`，按 `u.id, l.id` 分组。
- 常见错误：
  - 用 `INNER JOIN` 或把时间条件写在 `WHERE`，丢掉 0 点击行；
  - 用 `COUNT(*)`，把 LEFT JOIN 的空行算成 1；
  - 只写 `>=` 不写 `<`，把结束边界算进来；
  - 不按 `link_id` 做稳定排序，并列时结果顺序不确定。
- 口径说明（迷你引擎限制）：计划中的「每个用户点击最多的 3 条链接」需要窗口函数（如 `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY clicks DESC)`），当前迷你 SQL 引擎不支持窗口函数。正文用一段只读对照展示生产方式，并把可执行 SQL 题限定为「窗口内每个链接的点击数」。G1 报告记录这一偏差，不声称 top-3 已被自动测试覆盖。该偏差不影响 G1 要求的「SQL 题包含 LEFT JOIN 与时间边界」。

## 7. 方案题

- 题号：`s1-l1-ex-2`
- 场景：LinkHub 要支持「给链接打标签」，需要按标签筛选链接、显示标签使用量、支持标签重命名，并保证同一链接不会重复打同一个标签。请给出表结构、约束、索引、删除策略与迁移顺序，并说明 JSONB 备选方案的代价。
- 自检清单（8 条）：
  1. 标签与链接是多对多，使用关联表而不是在 `links` 里存数组；
  2. 关联表有复合主键或唯一约束，防止重复打标；
  3. `tags.name` 有唯一约束，重命名时考虑大小写与空白；
  4. 给出「按标签查链接」与「按链接查标签」两个方向的索引；
  5. 删除链接时说明关联行如何处理（级联或显式清理）；
  6. 说明标签重命名对历史数据与缓存的影响；
  7. 说明 JSONB 备选的适用条件与反查代价；
  8. 给出迁移顺序：建表 → 回填 → 加约束 → 切读写 → 清理旧字段。
- 参考要点：`link_tags(link_id, tag_id)` 复合主键；`tags(name)` 唯一；索引 `(tag_id, link_id)` 支持反查，`(link_id)` 通常由复合主键前缀覆盖；删除用 `ON DELETE CASCADE` 或事务内显式清理；不要把标签数组塞进 `links` 还指望高效反查；迁移要可回滚，先双写再切换。
- 常见浅答案：只画两张表没有关联表；用 JSONB 数组 + 应用层去重；不说明删除与重命名；不给出迁移顺序。
