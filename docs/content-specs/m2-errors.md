## 1. 出口能力

1. 区分语法、语义与业务三层校验，并把失败稳定映射到 4xx。
2. 实现零依赖的创建短链校验器，返回字段顺序稳定的错误列表。
3. 设计统一错误信封与可枚举错误码表，保证客户端可编程处理。
4. 区分 4xx 与 5xx，避免泄漏堆栈、SQL 与内部标识，并为校验写测试。

## 2. 学习者起点与常见误解

- 已经知道：TypeScript 的类型系统；前端表单校验；JSON 请求体；常见的状态码名词。
- 常见误解：
  - 「前端已经校验过了，后端不用再校验。」——请求可以绕过前端，类型只在编译期存在，服务端必须重新校验。
  - 「校验失败就返回 400 加一段错误字符串。」——客户端无法稳定解析；需要错误码、字段路径与 requestId。
  - 「所有错误都用 500 最省事。」——4xx 是调用方问题、5xx 是服务端问题，混用会让监控、重试与告警全部失真。
  - 「错误信息越详细越好，把 SQL 也返回给调用方。」——内部细节会帮助攻击者；对外只给稳定、可行动的信息。
  - 「未知字段直接忽略最兼容。」——静默丢弃会让调用方以为字段生效；公开 API 应显式拒绝或明确声明策略。
  - 「一次性返回所有错误会让客户端难处理，所以只返回第一个。」——公开契约应固定策略：要么全量、要么首个，不能随实现漂移。

## 3. 范围边界

- 本讲只讲：
  - 语法、语义、业务三层校验与状态码映射；
  - 创建短链的校验规则与零依赖实现；
  - 错误信封 `{ error: { code, message, requestId, details? } }`；
  - 可枚举错误码表与 4xx/5xx 边界；
  - 未知字段策略与错误顺序稳定性；
  - 校验测试的最小集合。
- 本讲不讲：
  - 认证与授权失败（m2-auth）；
  - 幂等键、限流错误与 OpenAPI 错误文档（m2-contract）；
  - 具体 schema 库（zod/Joi）的 API 与选型教程；
  - WAF、注入攻击与 CSP（S6）。
- 与相邻讲的分工：上一讲定义端点与方法；本讲定义「请求不合法时，响应长什么样、客户端怎么处理」。

## 5. 概念检查（3 题）

### C1

- ID：`m2-errors-check-1`
- 类型：single
- 标签：状态码边界
- 题干：创建短链时 `expiresAt` 是一个格式正确、但早于当前时间的 ISO 字符串。最合适的响应是什么？
- 选项：
  - A. 200，响应体 `{ success: false, message: '过期时间不能早于当前时间' }`（错误）
  - B. 400 或 422，错误码 `validation_error`，`details` 指出 `expiresAt` 字段（正确）
  - C. 500，因为服务端无法处理这个时间（错误）
  - D. 201，先创建再让定时任务清理（错误）
- 解析要点：格式正确但语义不满足要求，属于调用方输入错误，应是 4xx；用 200 会让监控与重试策略失效；500 把责任推给服务端并触发误告警；先创建再清理会产生不可见脏数据。400 与 422 的选择要在契约中固定，不能同一 API 内混用。
- 对应 objective：O1、O4。

### C2

- ID：`m2-errors-check-2`
- 类型：multi
- 标签：错误信封
- 题干：一个可供第三方编程处理的错误响应，应该满足哪些要求？
- 选项：
  - A. 有稳定的机器可读错误码（正确）
  - B. 有贯穿日志与响应的 requestId（正确）
  - C. 把数据库堆栈与 SQL 放进 message 便于排查（错误）
  - D. 校验错误能指出出错字段（正确）
  - E. 所有错误都返回 HTTP 200，靠 body 区分（错误）
- 解析要点：错误码让客户端分支稳定；requestId 把用户报障与服务端日志串起来；堆栈与 SQL 泄漏内部结构；字段级 details 让表单能定位；HTTP 状态码是网关、监控与 SDK 的共同语言，不能被 body 替代。
- 对应 objective：O3。

### C3

- ID：`m2-errors-check-3`
- 类型：single
- 标签：未知字段策略
- 题干：公开 API 的创建接口收到一个未定义的字段 `color`。以下哪种处理最符合「契约可验证」？
- 选项：
  - A. 静默忽略，保证向后兼容（错误）
  - B. 写入数据库的扩展字段，避免报错（错误）
  - C. 返回 4xx `validation_error`，`details` 指出 `color` 为未知字段，并在文档中写明该策略（正确）
  - D. 返回 500，因为这属于服务端未实现的字段（错误）
- 解析要点：静默忽略会让调用方误以为字段生效，是隐蔽的契约破坏；写入扩展字段绕过校验并污染数据；500 错误归因；显式拒绝并文档化，能让调用方在集成阶段就发现问题，也让契约测试可断言。若产品确实需要宽松策略，必须统一声明并测试，不能逐接口漂移。
- 对应 objective：O2、O3。

## 6. 代码题（1 题）

- 题号：`m2-errors-ex-1`
- 标题：创建短链的校验器
- 业务场景：第三方通过 `POST /v1/links` 创建短链。服务端要在进入业务逻辑前拒绝非法输入，并返回字段级错误，供 SDK 与表单直接定位。
- 契约：
  - `validateCreateLink(input, { now = Date.now() } = {})`。
  - 成功返回 `{ ok: true, value }`，`value` 只包含已知字段：`url`、`slug?`、`title?`、`expiresAt?`。
  - 失败返回 `{ ok: false, errors }`，每项 `{ field, code }`；`errors` 顺序固定：先按 `url`、`slug`、`title`、`expiresAt` 的规则顺序，再按字段名字典序追加未知字段错误。
  - `url` 必填、字符串、必须是带主机名的绝对 URL，协议只能是 `http` 或 `https`；缺失为 `required`，类型错为 `invalid_type`，结构不合法为 `invalid_url`，协议不对为 `invalid_protocol`。实现用正则解析，不依赖运行时的 `URL` 全局。
  - `slug` 可选；存在时必须是 4-32 位小写字母、数字或连字符；保留字 `api`、`admin`、`login`、`static`、`health` 不允许；错误码分别为 `invalid_format`、`reserved`。
  - `title` 可选；存在时 trim 后长度 1-120；错误码 `invalid_length`。
  - `expiresAt` 可选；存在时必须是可解析的 ISO 字符串，且严格晚于注入的 `now`；错误码 `invalid_datetime`、`expired`。
  - 未定义字段产生 `{ field, code: 'unknown_field' }`，不得进入 `value`。
  - 不做 trim 之外的隐式转换；数字、布尔、null 都按类型错误处理。
- starter 要点：只检查 `url` 是否存在；`expiresAt` 与当前真实时间比较；未知字段直接丢弃；错误按对象遍历顺序产生。
- solution 要点：先收集已知字段错误，再统一处理未知字段并排序；URL 用 `new URL` 加协议白名单；时间用 `Date.parse` 与注入的 `now` 比较；只把合法字段写入 `value`。
- 测试（7 条）：
  1. 合法输入返回 `ok: true`，`value` 不含未知字段；
  2. 缺 `url` 返回 `required`；
  3. `ftp://` 返回 `invalid_protocol`，不可解析字符串返回 `invalid_url`；
  4. 保留字 slug 返回 `reserved`，长度或字符不符返回 `invalid_format`；
  5. `expiresAt` 等于注入的 `now` 或更早返回 `expired`，格式错误返回 `invalid_datetime`；
  6. 未知字段被拒绝且错误按字段名字典序追加；
  7. 多个字段同时非法时错误顺序稳定（先已知字段规则顺序，再未知字段）。
- 测试设计说明：第 5 条必须注入 `now`，抓「用真实时间导致测试漂移」；第 6、7 条抓「静默忽略未知字段」与「错误顺序随对象键漂移」；第 3 条同时区分解析失败与协议失败。
- Python 差异：函数为 `validate_create_link(input_data, now=None)`，`now` 为毫秒整数或 `None` 时用 `time.time()*1000`；ISO 时间用 `datetime.fromisoformat`，需要把结尾 `Z` 替换为 `+00:00`；URL 用 `urllib.parse.urlsplit` 并检查 `scheme` 与 `netloc`；返回 `dict`，错误顺序由显式列表构造。测试同样 7 条，`now` 用固定毫秒值。
- 常见错误：
  - 用 `Date.now()` 直接比较，测试无法固定时间；
  - 只判断字符串前缀 `http`，把 `httpevil://` 当合法；
  - 保留字检查放在格式检查之后，错误码不稳定；
  - 未知字段静默丢弃；
  - 用对象键遍历产生错误，顺序随输入变化；
  - 把数字 `123` 自动转成字符串后通过校验。

## 7. 方案题（1 题）

- 题号：`m2-errors-ex-2`
- 场景：LinkHub 要发布第一版错误码表，供 Web、移动端与第三方 SDK 共用。当前每个接口各自返回 `{ message }`，有的接口校验失败返回 500，有的返回 200。请给出错误信封、错误码表、状态码映射、日志与测试方案。
- 自检清单（8 条）：
  1. 定义统一错误信封，字段含义与可选性写清；
  2. 错误码可枚举、命名稳定，不把 message 当判断依据；
  3. 为每个错误码标注 HTTP 状态码与是否可重试；
  4. 区分配置/校验/认证/权限/冲突/限流/内部错误；
  5. 规定未知字段、错误顺序与 details 形状；
  6. 规定 requestId 的生成、回传与日志关联方式；
  7. 规定对外 message 的信息边界，禁止堆栈/SQL/内部 ID；
  8. 给出契约测试：状态码、code、字段路径、无泄漏。
- 参考要点：信封固定四字段；错误码按域前缀或固定枚举；400 用于语法错误，422 用于语义错误（二选一并全站统一）；401/403/404/409/429 各归其位；未知字段显式拒绝；details 只放字段与原因，不放内部异常；requestId 由入口生成并透传；message 可本地化，code 不可变；测试断言 code 与状态码，不断言完整文案。
- 常见浅答案：只列状态码不列 code；把异常 message 直接透传；所有 4xx 都用一个 `bad_request`；details 里放原始请求体。
