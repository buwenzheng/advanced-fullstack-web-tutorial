## 1. 出口能力

1. 说出 Node 事件循环的六个阶段，解释微任务、`process.nextTick` 与宏任务的执行顺序，并说明哪些顺序不能死记。
2. 判断一段代码是阻塞事件循环、占用 libuv 线程池，还是只排队微任务，并能用 event loop lag 与线程池证据定位。
3. 写出带并发上限的调度器：结果顺序与输入一致、拒绝可传播、非法上限有确定行为。
4. 对比 Node 与 Python 的并发模型，为 I/O 密集与 CPU 密集任务选择 asyncio、线程、多进程或队列。

## 2. 学习者起点与常见误解

- 已经知道：`Promise`、`async/await`、`setTimeout`、`fetch`；写过 `await`，知道「异步不阻塞」，但多数时候只是把它当语法。
- 常见误解：
  - 「用了 `async` 就不会阻塞。」——CPU 密集的同步代码照样卡死事件循环。
  - 「异步读文件不占线程。」——`fs.readFile` 会占用 libuv 线程池，默认只有 4 个线程。
  - 「`Promise` 回调一定比 `process.nextTick` 先执行。」——Node 中 `nextTick` 队列优先。
  - 「顶层 `setTimeout(0)` 一定早于 `setImmediate`。」——顶层顺序取决于启动时机，不能背固定答案。
  - 「未处理的 Promise 拒绝只是警告。」——Node 15+ 默认以非零码退出。
  - 「`process.exit(1)` 是优雅退出。」——它会丢弃在途异步操作与未刷新的日志。
  - 「Python 有 GIL，所以线程完全没用。」——I/O 等待会释放 GIL；CPU 密集才需要多进程或原生扩展。
  - 「asyncio 会开很多线程。」——asyncio 是单线程协作式调度。
- 本讲要纠正的判断：
  - 异步的收益是「等待时不占主线程」，不是「所有工作都不占资源」。
  - 事件循环、线程池、微任务队列是三块独立资源，各有自己的天花板。
  - 并发上限是保护下游与自身线程池的契约，不是可选优化。

## 5. 概念检查（3 题）

### C1

- ID：`m1-runtime-check-1`
- 类型：single
- 题干：下面哪一段代码会直接阻塞 Node 事件循环，让同一进程内的其他请求一起等待？
- 选项与正确项：
  - A. `await fs.promises.readFile(path)`（错误）
  - B. `setTimeout(() => {}, 0)`（错误）
  - C. `fs.readFileSync(path)` 写在请求处理函数里（正确）
  - D. `Promise.resolve().then(() => {})`（错误）
- 解析要点：`readFileSync` 在主线程同步等待磁盘，期间无法处理其他回调；`fs.promises.readFile` 把读操作交给线程池，主线程可以继续调度；`setTimeout` 只是登记定时器；一个空的 Promise 回调是微任务，执行时间极短。错误选项分别对应「异步 API 也阻塞」「定时器阻塞」「微任务等于阻塞」三种混淆。
- 对应 objective：O2。

### C2

- ID：`m1-runtime-check-2`
- 类型：multi
- 题干：关于 Node 事件循环与未处理拒绝，以下哪些说法正确？
- 选项与正确项：
  - A. Node 中 `process.nextTick` 回调先于 Promise 微任务执行（正确）
  - B. 每个宏任务回调结束后，运行时会清空微任务队列（正确）
  - C. 在 I/O 回调内注册的 `setImmediate` 通常先于 `setTimeout(0)` 执行（正确）
  - D. 顶层 `setTimeout(0)` 与 `setImmediate` 的顺序在所有 Node 版本中固定（错误）
  - E. Node 15+ 未处理的 Promise 拒绝默认导致进程以非零码退出（正确）
- 解析要点：A、B 描述微任务清理规则；C 的前提是「在 I/O 回调内」，此时下一轮先进入 check 阶段；D 错误，顶层顺序取决于进程启动与定时器精度，不能背固定答案；E 正确，默认模式会抛出并使进程退出，但注册 `unhandledRejection` 监听会改变行为，正文需写清边界。错误选项对应「把顶层顺序当规范」。
- 对应 objective：O1。

### C3

- ID：`m1-runtime-check-3`
- 类型：single
- 题干：服务对 40 个文件各执行一次 `fs.readFile`，每次约 30ms，总耗时接近 300ms，但 event loop lag P99 只有 5ms。最可能的原因是什么？
- 选项与正确项：
  - A. 主线程被同步读文件阻塞（错误）
  - B. libuv 线程池默认 4 个线程，40 个读任务在队列中分批执行（正确）
  - C. DNS 解析拖慢了文件读取（错误）
  - D. 微任务队列饥饿导致 I/O 无法回调（错误）
- 解析要点：lag 低说明主线程仍在按时调度，排除 A；异步文件读取占用线程池，默认 4 个线程，40 个任务约分 10 批，每批 30ms，量级接近 300ms；文件读取不经过 DNS；微任务饥饿会推高 lag 并延迟 I/O 回调，与「lag 很低」矛盾。若 `UV_THREADPOOL_SIZE` 被修改，批次数会变化，正文要提醒先确认环境。
- 对应 objective：O2。

## 6. 代码题（1 题，Node/Python 双轨）

- 题号：`m1-runtime-ex-1`
- 标题：带并发上限的任务调度器
- 业务场景：p-m1-probe 探针需要同时检查多个 URL，但不能无限并发打满本机线程池或下游；调度器要保证输出顺序稳定，并在任一任务失败时让调用方拿到明确错误。
- 函数/接口契约：

```js
runWithLimit(tasks, limit)
```

- `tasks`：数组，元素是「无参函数」，调用后返回 Promise 或普通值；
- `limit`：并发上限；不是正整数时按 `1` 处理；
- 返回 Promise：
  - 全部成功时，按输入顺序返回结果数组；
  - 任一任务拒绝时，整体以该拒绝原因拒绝；
  - 空数组立即返回 `[]`；
  - 任意时刻在飞任务数不超过 `limit`；
  - 不修改 `tasks` 数组，不丢失其他任务的拒绝处理（不产生未处理拒绝）。
- 调度规则：按输入顺序启动任务；前一个任务结束后再启动下一个，直到所有任务完成。

- Node starter 要点：用 `Promise.all(tasks.map((task) => task()))` 一次性启动；结果顺序与拒绝传播能过，但峰值并发、`limit=0` 与 `limit` 大于任务数的边界不满足契约。
- Node solution 要点：维护 `next` 游标与 `active` 计数；用 worker 循环从游标领取任务；成功时写入对应下标并在全部完成时 resolve；失败时标记终止并 reject；每个任务都挂拒绝处理，避免其余任务产生未处理拒绝。
- 测试用例（6 条，全部用 deferred 手动控制，不依赖真实时间）：

| # | 场景 | 构造 | 期望 |
| --- | --- | --- | --- |
| 1 | 峰值并发不超过上限 | 4 个 deferred 任务，`limit=2`；启动后先让前两个进入 | 启动数最多为 2；逐个 resolve 后才启动后续任务；结果 `[0,1,2,3]` |
| 2 | 结果顺序与完成顺序解耦 | 3 个 deferred 任务，`limit=3`；先 resolve 第 2 个，再 resolve 第 3、1 个 | 结果仍为 `[a,b,c]` |
| 3 | 拒绝传播 | 3 个任务，第 2 个 reject `Error('boom')`，`limit=2`；其余两个在整体拒绝后 resolve | 整体以 `boom` 拒绝；其余任务能被正常完成，测试不遗留挂起任务 |
| 4 | `limit=0` 按 1 处理 | 3 个 deferred 任务，`limit=0` | 任意时刻只有 1 个在飞；结果顺序正确 |
| 5 | `limit` 大于任务数 | 2 个 deferred 任务，`limit=10` | 两个任务都启动，峰值并发为 2；结果顺序正确 |
| 6 | 空数组 | `runWithLimit([], 2)` | 立即 resolve `[]`，没有任务被调用 |

- 测试设计说明：用例 1 区分「一次性 `Promise.all`」的实现；用例 2 区分「按完成顺序收集结果」的实现；用例 3 区分「吞掉错误或永远 pending」的实现，沙箱无法直接观测未处理拒绝，该属性由实现契约（为每个已启动任务挂拒绝处理）与正文代码评审保证；用例 4 区分「把 0 当无限并发」或「直接抛错」的实现；用例 6 区分「对空数组仍启动 worker」的实现。测试名用中文，失败时能直接看出语义。
- Python 差异：
  - 函数名 `run_with_limit(tasks, limit)`，`tasks` 是返回 awaitable 的无参可调用对象列表；
  - 用 `asyncio.gather` 启动 `limit` 个 worker，`nonlocal cursor` 领取下标；
  - 任一任务抛异常时，取消其余 worker 并 `await` 它们的取消结果，再向上抛出原异常，避免遗留任务；
  - 不使用 `ThreadPoolExecutor` 冒充异步；GIL 与 asyncio 的 I/O 并发无关；
  - 测试使用 `assert_eq`，异步测试标 `async: true`；用 `asyncio.Future` 或 `asyncio.Event` 控制完成顺序，不用 `sleep`。
- 常见错误实现与对应失败用例：
  - `Promise.all` 全量启动 → 用例 1/4 失败；
  - 用 `results.push(value)` 按完成顺序收集 → 用例 2 失败；
  - 失败后吞掉异常或永远 pending → 用例 3 失败或超时；
  - `limit=0` 时直接抛错或当无限并发 → 用例 4 失败；
  - 空数组仍创建 worker → 用例 6 超时或产生多余调用。

## 7. 方案题

- 题号：`m1-runtime-ex-2`
- 场景：下面是一段「支付回调后扣款」的服务代码。它在本机测试通过，上线后出现 P99 抖动、偶发重复扣款、进程重启时订单状态不一致。请做一次运行时视角的代码审查，给出问题、线上现象、修复顺序与验证方式。

```js
import fs from 'node:fs';
import express from 'express';

const app = express();
app.use(express.json());

app.post('/pay', async (req, res) => {
  const rules = JSON.parse(fs.readFileSync('./rules.json', 'utf8'));
  const result = await charge(req.body.orderId, req.body.amount);
  res.json({ ok: true, result, rulesVersion: rules.version });
});

process.on('uncaughtException', () => process.exit(1));

app.listen(3000);
```

- 需要产出的决策/设计：
  - 哪些代码阻塞事件循环，哪些占用线程池；
  - 规则文件的读取与解析应该放在哪里；
  - `charge()` 失败时的错误处理与幂等键；
  - `uncaughtException` 后直接 `process.exit(1)` 的代价；
  - 外部调用的超时、重试与并发限制；
  - 入参校验与错误响应；
  - 修复的优先级与每一步的验证方式。
- 自检清单（8 条）：
  1. 指出 `readFileSync` 在请求路径中阻塞事件循环，并写出线上现象（lag 上升、吞吐下降、P99 抖动）；
  2. 规则文件改为启动时读取一次或带失效策略的缓存，不在每请求同步解析；
  3. 指出 `charge()` 没有错误处理，异步失败会变成未处理拒绝；
  4. 指出没有幂等键，客户端或网关重试会重复扣款；
  5. 指出 `process.exit(1)` 会硬切在途请求、丢日志缓冲、跳过连接关闭；
  6. 为外部调用设置超时，并说明重试必须建立在幂等前提上；
  7. 入口增加并发限制或背压，避免线程池与下游被打满；
  8. 给出修复优先级与验证方式（故障注入、压测、日志与指标对照）。
- 参考要点：
  - **约束**：支付回调可能重复投递；下游可能超时但已成功；进程随时可能被重启；日志是事后定位的主要证据。
  - **备选**：规则可在启动时加载并在版本变更时重载；幂等可用业务订单号 + 唯一约束或幂等表；超时可用 `AbortController` 或下游 SDK 的超时参数；并发限制可用本讲调度器，跨进程则用队列。
  - **代价**：启动时加载规则会牺牲「改文件立即生效」；幂等表增加一次写入与清理成本；重试会增加下游压力，必须配合退避与预算；优雅关闭需要等待在途请求，会延长发布窗口。
  - **反悔条件**：如果规则必须秒级生效，应改为带版本与原子替换的缓存，而不是回到每请求同步读；如果下游不支持幂等，不能盲目重试，需要先补幂等键或改为查询后补偿。
- 常见浅答案：
  - 「加个 `try/catch` 就好了」——没有覆盖未处理拒绝、重复扣款与硬退出；
  - 「用 `fs.promises.readFile` 替换」——只是把阻塞换成线程池排队，规则仍在每请求解析；
  - 「`process.exit` 前 `setTimeout` 一下」——仍在丢弃在途请求，且没有关闭服务器与刷新日志；
  - 「失败就重试三次」——没有幂等与超时预算，会把偶发失败放大成重复扣款。
