## 1. 出口能力

1. 设计游标分页、过滤与排序，保证稳定排序、白名单与分页上限。
2. 定义幂等键契约：作用域、TTL、同 body 重放、同键不同 body 的冲突语义（只讲契约，不写实现）。
3. 定义限流契约：429、Retry-After、配额响应头与客户端行为（只讲契约，不写算法）。
4. 设计 webhook 的签名、时间戳、重放窗口与重试策略，并用 OpenAPI 与契约测试守住文档漂移。

## 2. 学习者起点与常见误解

- 已经知道：offset/limit 分页；HTTP 请求头；JSON 与 HMAC 的基本概念；OpenAPI 这个名词。
- 常见误解：
  - 「offset 分页简单，永远够用。」——数据插入或删除会让页边界漂移，用户会看到重复或漏项；深 offset 还会越来越慢。
  - 「limit 由客户端传，想拉多少拉多少。」——无上限会让一次请求拖垮数据库与网关；服务端必须封顶并提供默认值。
  - 「幂等键就是去重表。」——本讲只定义契约；实现、存储与过期属于 S3 与项目。
  - 「限流就是返回 429。」——没有 Retry-After、配额头与文档，客户端只能盲目重试，反而放大压力；算法属于 S3。
  - 「webhook 发出去就行，失败了让对方重试。」——不签名、不校验时间戳、不去重，接收方无法区分伪造与重放。
  - 「有 OpenAPI 文件就等于契约一致。」——文件可能过期；需要用契约测试在 CI 里对比实现。

## 3. 范围边界

- 本讲只讲：
  - 游标分页、稳定排序、过滤/排序白名单；
  - 幂等键契约（请求头、作用域、TTL、冲突语义）；
  - 限流契约（429、Retry-After、配额头、客户端退避）；
  - webhook 签名、时间戳、重放窗口、重试与死信语义；
  - OpenAPI、契约测试与 CI 漂移检查；
  - SLA/SLO 与弃用策略的接口层表达。
- 本讲不讲：
  - 令牌桶/漏桶/固定窗口/滑动窗口算法与容量调参（m3-ratelimit）；
  - 幂等键的存储实现、分布式锁与重试预算（m3-resilience）；
  - 网关产品、CDN 与 OpenAPI 生成器的具体用法；
  - 计费与配额结算系统。
- 与相邻讲的分工：本讲定义「客户端能看到什么契约」；S3 讲「服务端怎么实现限流、幂等与异步」。

## 5. 概念检查（3 题）

### C1

- ID：`m2-contract-check-1`
- 类型：single
- 标签：分页
- 题干：第三方在翻页过程中不断有新链接创建，使用 offset/limit 分页时出现了重复项与漏项。最合适的修复方向是什么？
- 选项：
  - A. 把 limit 调大，减少翻页次数（错误）
  - B. 改用基于稳定排序键与 tie-breaker 的游标分页（正确）
  - C. 在每页请求前锁表，禁止写入（错误）
  - D. 让客户端自己去重，服务端不用改（错误）
- 解析要点：offset 基于行号，插入/删除会让边界漂移；游标用「上一页最后一条的排序键」定位，配合唯一 tie-breaker 保证稳定。调大 limit 只减少概率；锁表代价过高；客户端去重无法找回漏项。
- 对应 objective：O1。

### C2

- ID：`m2-contract-check-2`
- 类型：multi
- 标签：幂等键契约
- 题干：关于创建接口的 `Idempotency-Key` 契约，以下哪些说法正确？
- 选项：
  - A. 同一个键与同一个请求体重放，应返回首次结果而不是再创建一条（正确）
  - B. 同一个键配不同请求体，应返回冲突而不是静默执行（正确）
  - C. 幂等键应绑定租户或用户作用域，不能全局共享（正确）
  - D. 幂等键永久保存最安全，不需要 TTL（错误）
  - E. 只要客户端重试，服务端就一定会去重（错误）
- 解析要点：幂等键的核心是「同键同 body 重放返回首次结果」「同键不同 body 冲突」；作用域避免跨租户碰撞；TTL 控制存储成本并定义重放窗口；没有实现与存储时，重试仍可能创建重复记录，这正是 S3 要补的。
- 对应 objective：O2。

### C3

- ID：`m2-contract-check-3`
- 类型：single
- 标签：限流契约
- 题干：服务端对超限请求返回 429。为了让客户端能正确退避，响应至少还应包含什么？
- 选项：
  - A. 只返回 429，客户端自己猜（错误）
  - B. `Retry-After` 与稳定的限流错误码，并在文档中说明配额窗口（正确）
  - C. 返回 500，让客户端按服务端错误重试（错误）
  - D. 返回 200，把限流信息放在 body 里（错误）
- 解析要点：429 表示请求过多，客户端需要知道何时可以再试；`Retry-After` 给出秒数或 HTTP 日期；稳定错误码让 SDK 分支；文档说明窗口与配额。500 错误归因；200 会绕过监控与 SDK 的限流处理。具体限流算法不在本讲。
- 对应 objective：O3。

## 6. 代码题（1 题）

- 题号：`m2-contract-ex-1`
- 标题：游标分页
- 业务场景：LinkHub 的列表接口要支持第三方稳定翻页，数据会持续插入，不能用 offset。游标对客户端不透明，排序键为 `createdAt` 降序、`id` 降序。
- 契约：
  - `paginate(items, { limit = 20, cursor } = {})` 返回 `{ data, nextCursor }`。
  - `limit` 必须是正整数；超过 100 按 100 处理；默认 20。
  - 排序：`createdAt` 降序；相同 `createdAt` 按 `id` 降序。
  - `cursor` 是 base64url 编码的 JSON `{ createdAt, id }`；缺省表示第一页。
  - `nextCursor` 在还有下一页时返回字符串，否则为 `null`。
  - 游标无法解码、结构不对或对应记录不存在时抛 `InvalidCursorError`。
- starter 要点：用 slice(offset) 按索引翻页；游标直接用明文 JSON；不校验 limit。
- solution 要点：先稳定排序，再按游标值找到位置，从下一条开始取；base64url 编解码手写，避免依赖运行时；下一页游标取本页最后一条。
- 测试（7 条）：
  1. 第一页按 createdAt 降序返回，`nextCursor` 非空；
  2. 用上一页游标取到下一页，不重复；
  3. 最后一页 `nextCursor === null`；
  4. 非法游标（乱码/结构错误/记录不存在）抛 `InvalidCursorError`；
  5. 默认 limit 20，超过 100 封顶 100；
  6. 相同 createdAt 按 id 降序，翻页不重复；
  7. 空列表返回空数组与 null。
- 测试设计说明：第 4 条抓「解析失败静默当第一页」；第 5 条抓无界查询；第 6 条抓缺少 tie-breaker 导致翻页重复。
- Python 差异：函数为 `paginate(items, limit=20, cursor=None)`；用 `base64.urlsafe_b64encode`/`b64decode` 与 `json`；排序用 `sorted(key=lambda item: (item['createdAt'], item['id']), reverse=True)`；自定义 `InvalidCursorError`；测试 7 条。
- 常见错误：用 offset 而非游标值；排序不唯一；游标明文暴露内部字段；limit 不封顶；最后一页仍返回游标；解码失败静默从头开始。

## 7. 方案题（1 题）

- 题号：`m2-contract-ex-2`
- 场景：LinkHub 要发布面向第三方的 v1 API，包含列表、创建、点击统计与 webhook 回调。当前没有分页上限、没有幂等键、限流只有一句文档、webhook 不签名。请给出对外契约与验收方案。
- 自检清单（8 条）：
  1. 分页采用游标并定义稳定排序与上限；
  2. 过滤与排序字段使用白名单，非法字段返回 4xx；
  3. 幂等键的请求头、作用域、TTL、重放与冲突语义写清；
  4. 限流契约包含 429、Retry-After、配额头与客户端退避；
  5. webhook 有签名、时间戳、重放窗口与幂等建议；
  6. webhook 重试有上限与死信/停用策略；
  7. OpenAPI 覆盖公开字段、状态码与错误码；
  8. 契约测试在 CI 中检查文档与实现漂移。
- 参考要点：游标含 createdAt 与 id；limit 默认 20、上限 100；过滤/排序白名单；幂等键作用域到租户，同键不同 body 返回 409；429 带 Retry-After 与稳定 code；webhook 用 HMAC 签名覆盖 timestamp+body，接收方校验时间窗并去重；重试指数退避，超过次数进死信并告警；OpenAPI 由测试校验，CI 失败阻断发布。
- 常见浅答案：offset 分页加一个很大的 max limit；幂等键全局去重且永不过期；限流只返回 429；webhook 不签名靠 HTTPS；OpenAPI 手写后从不校验。
