## 0. 问题诊断

当前目录是「边写边长」出来的，不是从能力模型推导出来的，因此出现了六类问题：

1. **课时边界重叠**：`s2-l4` 与 `s3-l3` 都在讲令牌桶、429、幂等键，但两讲的定位没有写清楚谁讲契约、谁讲实现。
2. **项目主线断裂**：阶段 1-4 的项目是任务管理器，阶段 5 突然变成「按链接聚合」的统计服务，毕业项目又是 LinkHub，产品域在最后两跳才接上。
3. **前后因果矛盾**：阶段 3 的项目已经把点击计数改成 BullMQ 异步，阶段 5 的项目却说「把点击统计从同步写库改成事件驱动」，同一件事做了两遍，且第二遍的起点是错的。
4. **目标覆盖不均**：目标是性能优化、基础设施、大厂面试，但目录里没有独立的性能压测与瓶颈定位课，也没有数据库复制/分片课；附录只有数据结构。
5. **全栈层缺失**：课程止步于「后端服务 + 一个管理后台」，没有 BFF、渲染架构、实时链路、边缘部署与前端可观测性；也没有教「怎么写出能说服人的技术方案」「怎么组织测试与代码质量」「怎么做故障复盘」。按这个目录学完，能成为合格的后端工程师，但离「资深全栈」还差三层：产品端到端闭环、架构判断力、工程影响力。
6. **AI 层缺失，且 AI Coding 经验零散**：目录没有 LLM 应用、RAG/向量检索、评估与安全、AI 基础设施素养；也没有把 AI Coding 当成工程系统来讲。很多人已经在用 vibe coding，但经验来自个人试错：不知道为什么有效、什么时候会失败、如何验证、如何度量、如何让团队复用。AI 功能正在成为产品默认需求，资深全栈既要能判断「该不该用模型、怎么评估、怎么控成本、怎么防注入」，也要能把 AI 协作从个人技巧升级为可复用的工程系统。

根因不是某一讲写得不好，而是前置的目录没有定义清楚：每个阶段出口能力是什么、每讲只负责哪一层、项目如何逐阶段演进。先修目录。

「资深」不是多学几个中间件，而是能在信息不全时做判断，并为判断负责。课程里每个阶段至少有一次方案取舍训练，答案不唯一，但必须给出约束、备选与代价。

## 3. 设计原则

1. **能力驱动，而不是知识点驱动**：每个阶段先定义出口能力，再倒推课时。
2. **单一产品主线**：从阶段 1 起，所有阶段项目都围绕同一个产品 LinkHub 演进；不再中途换域。
3. **一次只引入一个新复杂度**：先能跑，再能交付，再能扛住，再谈拆分、数据扩展、全栈集成与 AI。
4. **每讲必须可验证**：3 道概念检查 + 至少 1 道可验证练习（代码/SQL/方案）；代码题 Node/Python 双轨，SQL 题按分阶段目录，每个阶段至少 1 道方案题。分阶段目录的「练习」列是最低要求，实施计划可加题但不能减题。
5. **事实可追溯**：版本、数字、行为都以官方文档为准；内容生产阶段逐条核对。
6. **双语言等价**：同一机制在 Node 与 Python 下都要有可运行实现，差异用注释讲清，而不是只翻译语法。
7. **面试不是独立轨道**：每讲带「面试延伸」，附录用系统设计案例收口，而不是背八股。
8. **深度优先**：核心讲机制与取舍，附录讲深水区；宁可少讲一个名词，也不留一个讲不透的课时。
9. **端到端闭环**：每个后端能力都要落到产品可见的路径上（契约 → UI → 观测），不做「只在后端自嗨」的练习。
10. **资深 = 判断力**：方案题不追求标准答案，追求约束、备选、代价与反悔条件都写清楚。
11. **AI 是应用能力，不是模型训练**：只讲把模型接进产品所需的应用层与基础设施素养；每个 AI 功能必须有评估集、成本上限与安全边界。
12. **AI Coding 是工程系统，不是提示词技巧**：以任务分类、上下文工程、独立验证、失败模式、度量与团队规范为骨架；个人经验必须能被复盘、复用和改进。

## 5. 项目主线：LinkHub

从阶段 1 开始，所有项目都在同一个产品上迭代。阶段 0 的 CLI 是工具，不属于 LinkHub。

| 项目 | 产品能力 | 技术重点 | 与上一跳的关系 |
| --- | --- | --- | --- |
| p0 HTTP 探针 CLI | 请求耗时探针 | DNS/TCP/TLS/TTFB、超时、错误处理 | 独立工具 |
| p1 LinkHub 数据层 | 用户、短链、点击事件落库 | PostgreSQL、索引、事务、迁移 | 从零建业务库 |
| p2 LinkHub 对外 API | 创建短链、跳转、管理 | REST、JWT、校验、错误契约、OpenAPI | 在 p1 的数据层上加契约 |
| p3 LinkHub 缓存与异步 | 热点跳转、点击事件、限流 | Redis、BullMQ、令牌桶、幂等键 | 在 p2 的 API 上加保护 |
| p4 LinkHub 生产化 | 可观测、可发布、可回滚 | 日志/指标/追踪、压测、Docker、CI/CD | 在 p3 的服务上加运营能力 |
| p5 LinkHub 统计服务 | 点击统计独立服务 | Outbox、RabbitMQ、幂等消费、死信、读模型 | 把 p3 的应用内异步升级为独立服务 |
| p6 LinkHub Web 与 BFF | 登录、创建/管理短链、实时点击看板 | 契约驱动、类型客户端、BFF、SSR/流式、实时、边缘、RUM | 在 p2-p5 的能力前加产品层 |
| p7 LinkHub AI 助手 | 链接摘要/标签、语义搜索、自然语言问数 | LLM 网关、流式、结构化输出、RAG、pgvector、工具调用、评估、注入防护、成本控制 | 在 p6 的产品上加模型能力 |
| 毕业项目 LinkHub | 完整短链产品 + 管理后台 + 多租户 + AI 助手 | 全部能力的集成与答辩 | 集成 p1-p7，补故障演练、ADR 与质量门槛 |

**关键因果**：p3 的 BullMQ 解决「把慢活挪出请求链路」，但入队与业务提交仍是两次写，消费者也随 API 进程部署；p5 用 Outbox 消除双写窗口，换 RabbitMQ 让发布器与消费者真正独立部署；p6 不重写后端，它在 p2-p5 的能力之上加产品层——契约生成的类型客户端、BFF 聚合、SSR/流式渲染、实时看板、边缘缓存与 RUM；p7 不新建系统，也不绕过 p2-p5：摘要/标签走 p3/p5 的异步链路，语义检索复用 Postgres/pgvector，问数只调用 p5 的受限工具。四跳各解决一个问题，不重复。

## 7. 分阶段目录

### S0 地基：请求、运行时与排障（3 讲 / 170 min）

**阶段目标**：在写业务代码之前，先能看见一次请求的完整路径，理解运行时为什么会被一行同步代码卡死，并掌握最基本的排障工具。

| ID | 课时 | 时长 | 核心内容 | 练习 | 先修 |
| --- | --- | --- | --- | --- | --- |
| s0-l1 | 从 URL 到响应：请求的四段旅程 | 55 | DNS、TCP、TLS、HTTP；每段的耗时与典型故障；curl/DevTools 对照 | 3 检查 + 代码：请求分段计时 | — |
| s0-l2 | Node.js/Python 运行时：事件循环与并发模型 | 60 | 事件循环阶段、微任务/宏任务、阻塞调用；Python GIL 与 asyncio 的差异 | 3 检查 + 代码：事件循环输出顺序 | s0-l1 |
| s0-cli | 命令行与排障：进程、端口、日志与 curl | 55 | 进程/信号、端口占用、环境变量、DNS/hosts、curl、日志检索、git 基本操作 | 3 检查 + 代码：端口/进程排障脚本 | s0-l1 |

**阶段项目 p0：HTTP 探针 CLI**
- 输出 DNS、TCP、TLS、TTFB、总耗时、状态码、重定向链。
- 支持超时、失败分段、JSON 输出；对 3 个不同站点跑通。
- 验收：任一段耗时翻倍时，输出能定位到段；错误不吞掉。

**出口标准**：能口述一次慢请求的排查顺序；能解释同步代码为什么会阻塞事件循环；能用 CLI 定位端口、进程与 DNS 问题。

### S1 数据与持久化：从对象到可信任的数据（4 讲 / 320 min）

**阶段目标**：把前端的对象变成能活过进程重启、并发写入和 schema 演进的数据。

| ID | 课时 | 时长 | 核心内容 | 练习 | 先修 |
| --- | --- | --- | --- | --- | --- |
| s1-l1 | 关系模型与 SQL：从对象到表 | 80 | 表/主键/外键、范式与反范式、JOIN、聚合、JSONB 的取舍；LinkHub 三张表 | 3 检查 + SQL 题 | S0 |
| s1-l2 | 索引与查询计划：为什么查询会突然变慢 | 85 | B+tree、复合索引最左前缀、覆盖索引、N+1、`EXPLAIN (ANALYZE, BUFFERS)` | 3 检查 + 代码/SQL：索引前后对比 | s1-l1 |
| s1-l3 | 事务、隔离级别与 MVCC | 80 | ACID、四类异常、隔离级别、MVCC 快照、行锁/间隙锁、连接池上限 | 3 检查 + 代码：并发更新与连接池 | s1-l1 |
| s1-schema | 数据建模、约束与迁移 | 75 | 唯一/CHECK/外键、规范化与反规范化、版本化迁移、种子脚本、零停机变更预览 | 3 检查 + 代码：可回滚迁移脚本 | s1-l1/s1-l3 |

**阶段项目 p1：LinkHub 数据层**
- 表：`users`、`links`、`click_events`；slug 唯一、过期时间、软删除、外键与 CHECK。
- 索引：slug 唯一索引、`(user_id, created_at)`、`click_events(link_id, clicked_at)`。
- 事务：创建短链与审计记录同事务；slug 冲突可重试；并发更新不丢更新。
- 交付：`schema.sql`、`seed.sql`、可回滚迁移、集成测试。
- 验收：`EXPLAIN` 证明列表与跳转查询走索引；并发测试无重复 slug；迁移可从空库与旧版库各跑一次。

**出口标准**：能为一个业务域画出表与约束；能用查询计划证明索引生效；能解释隔离级别与 MVCC；能写出可回滚的迁移。

### S2 API 设计与契约：把实现藏起来（4 讲 / 300 min）

**阶段目标**：把接口从「能跑」变成「第三方敢依赖」。

| ID | 课时 | 时长 | 核心内容 | 练习 | 先修 |

**S7 的教学骨架：AI Coding 五层模型**

AI Coding 不按工具讲，按「控制回路」讲。两讲都落在这五层上：

| 层 | 核心问题 | 关键实践 | 典型失败 |
| --- | --- | --- | --- |
| 任务层 | 该不该交给 AI？ | 任务分类、可验证性、风险、拆分粒度 | 把架构决策交给 AI；任务过大 |
| 上下文层 | 模型需要知道什么？ | 仓库规则、相关文件、接口契约、验收测试、负向约束 | 上下文缺失/过期；堆太多噪声 |
| 执行层 | 怎么让 AI 动手？ | 计划、增量 diff、工具权限、沙箱、预算 | 大范围重写；越权；失控 |
| 验证层 | 怎么证明它对了？ | 测试、类型、lint、构建、运行时、diff review、回滚 | 相信模型自述；测试被删；回归 |
| 系统层 | 怎么让团队持续受益？ | 度量、review 政策、安全/许可、成本、复盘 | 个人技巧无法复用；事故重复 |

**七步循环**：规格（可验收）→ 上下文（最小充分）→ 计划（可回滚的增量）→ 执行（最小权限）→ 验证（独立证据）→ 集成（小步提交与 review）→ 复盘（记录失败与改进）。

**任务分类矩阵**：

| | 高可验证 | 低可验证 |
| --- | --- | --- |
| 低歧义 | 可代理执行：样板、测试、机械重构 | 人主导 + AI 辅助：性能调优、安全敏感 |
| 高歧义 | AI 辅助 + 人定方案：新功能、迁移 | 人主导：架构、产品取舍、事故指挥 |

风险越高，越往「人主导」降级；验证成本越高，越要先补验收标准。

**成熟度 M1-M5**：M1 内联补全 → M2 对话辅助 → M3 Agent 结对（读仓库、多文件修改、跑测试）→ M4 流水线编排（issue→PR、自动 review、多 Agent）→ M5 组织系统（度量、规范、知识回路）。课程目标是让学员从 M2/M3 的零散经验，走到能设计 M4/M5 的工程系统。

**失败 taxonomy**：需求误解、上下文缺失/过期、幻觉 API/依赖、静默行为变更、过度设计/范围蔓延、测试作弊/删除、安全/隐私泄漏、集成/回归。每个失败都要能回答：怎么发现、怎么复现、怎么防再次发生。

**度量**：任务成功率、首次通过率、review 轮次、缺陷逃逸率、返工率、回滚率、单任务成本、人工 review 时间。不用「生成行数」「提示词数量」这类虚荣指标。

**阶段项目 p7：LinkHub AI 助手**
- 摘要与标签：抓取链接标题/描述，LLM 生成结构化摘要与标签；走 p3/p5 的异步链路，失败降级为规则提取。
- 语义搜索：embedding + pgvector；关键词 + 向量混合检索；rerank；答案必须带引用。
- 自然语言问数：把「上周哪个链接点击最多」转成对 p5 统计服务的受限工具调用，不直连生产库、不生成任意 SQL；回答带口径说明。
- 流式输出：SSE；支持取消、超时、断线重连；token 预算与租户配额。
- 评估：离线评估集覆盖事实性、引用、拒答与注入；评估进 CI，回归即失败。
- 安全：间接提示注入（链接页面内容中的恶意指令）、PII 脱敏、输出审查、租户隔离；密钥只走环境变量。
- 可观测：每次调用的模型、token、延迟、成本、检索命中、降级原因进 trace；模型超时/限流时有降级路径。
- AI 协作记录：按五层模型记录任务分类、上下文、验证证据、失败与回滚；至少 3 个失败案例与改进。
- 验收：引用可追溯；注入用例不越权、不泄漏；单请求与单租户成本有上限；评估集达到预设阈值；模型不可用时功能降级而不是整站不可用；AI 协作记录完整，至少一次因验证发现问题而回滚或重做。

**出口标准**：能设计一个可上线、可评估、可控成本、可防注入的 AI 功能；能判断何时不该用模型；能把 AI Coding 拆成任务、上下文、执行、验证与系统五层，并用证据而不是模型自述来验收产出。

## 11. 内容生产流程

1. **锁定目录**：本文件定稿后，课时 ID、顺序、时长、项目归属不再随意改动。
2. **写课时规格**：每讲先写 objectives、先修、块大纲、关键事实/版本、练习题与测试、Python 差异点。
3. **写正文**：按现有 block 类型（analogy/text/code/table/compare/flow/steps/pitfall/tip/note/list）组织；`case` 是唯一新增类型，用于完整事故/案例复盘（context/symptom/cause/fix/prevention/metric）。先讲清问题，再给最小实现，再讲坑与边界。
4. **事实核对**：版本、数字、默认行为逐条查官方文档；无法确认的写「取决于版本」，不写死。AI 相关的模型名、价格、上下文长度与 SDK 行为变化快：优先写机制与取舍，版本/价格标注日期；练习默认使用可替换的 provider 接口与本地 mock，避免绑定单一厂商。AI Coding 课时按五层模型讲，不绑定具体工具；示例至少覆盖 IDE 内联、CLI Agent、CI Bot 三类中的两类，练习用学员自己的工具 + 固定仓库夹具与验收测试。
5. **自动校验**：结构审计、JS 语法、Python AST、Node/Python 题测试、浏览器渲染、搜索索引、链接检查。
6. **人工 review**：按「是否只讲本讲范围」「是否与前后讲重复」「是否能被练习验证」三条检查；S6 课时再加一条「是否跨层」；S7 课时再加「是否有评估、成本与安全边界」「AI Coding 是否可验证与复盘」两条。
7. **发布**：全部通过后统一构建、私有发布；不发布半成品。

**每讲 Definition of Done**：
- 3-4 个 objectives，且与练习一一对应；
- 至少 1 个前端类比、1 个最小实现、1 个坑/边界；
- 3 道检查 + 至少 1 道可验证练习（代码/SQL/方案）；代码题双轨；SQL/方案题按分阶段目录配置；测试覆盖正常、边界、失败；
- 关键事实有版本/来源；
- 没有与相邻讲重复的完整段落；
- 页面渲染无控制台错误，搜索能命中正文；
- S6 阶段必须有三处跨层验证：s6-l1（契约 → UI）、s6-l3（传输 → UI 状态）、s6-l4（浏览器 → 服务端 trace）；
- S7 的 s7-l1..l3 必须覆盖评估集、注入用例、成本估算中的至少两项，并给出降级路径；s7-l4/l5 必须覆盖任务分类、上下文、验证与失败模式；
- AI Coding 课时必须包含任务分类、上下文、验证与失败模式；练习要求独立验证并提交协作记录。

## 14. 关键决策（默认采用，可调整）

1. **目标定位：资深全栈 + AI 应用 + AI Coding（推荐）**。S6 与 S7 都是核心必修；S7 前半讲产品 AI，后半把 AI Coding 系统化；否则课程只能证明「会写后端」或「会调模型」，无法证明「能把产品交付出去，并能持续用 AI 提效」。备选是把 AI 放进附录，课程短约 8 小时，但「AI 时代」的目标落不了地。
2. **课程规模：45 讲 / 约 57 小时（推荐）**。核心 32 讲 + 附录 13 讲。备选是 44 讲 / 约 55 小时（AI 只讲产品应用，不讲 AI Coding 系统化）或 39 讲 / 约 49 小时（不含 AI 核心阶段），适合只补后端与全栈的人，不适合本目标。
3. **AI 深度：应用工程 + AI Coding 系统工程（推荐）**。S7 的 l1-l3 讲 LLM 网关、RAG、评估、安全与成本；l4-l5 讲 AI Coding 五层模型、任务分类、上下文、验证、失败模式、度量与团队落地；不训练模型、不推导深度学习数学、不做微调生产线，也不做工具评测或提示词大全。备选是加一门 ML 基础，但会挤占全栈与工程能力的时间。
4. **附录结构：单个附录阶段 13 讲（推荐）**，保持现有 UI 的「APPENDIX」入口；备选是拆成「数据结构」「性能与基础设施」「架构与工程」「AI 基础设施」四个附录阶段，导航更细但首页卡片会变多。
5. **附录 ID 迁移（推荐）**：附录阶段改名 `appendix`，数据结构课改为 `a1..a6`，新核心阶段占用 `s6` 与 `s7`；同时做 localStorage 进度映射。备选是把新核心阶段命名为 `s8`/`s9`，避免迁移，但阶段顺序与「先核心后附录」的叙事不一致，导航也会出现空位。
6. **发布策略：保持私有，复用现有项目**。全部内容与审计通过后统一发布，不在中间状态发布半成品；`DEMO_SECRET` 维持当前演示值，不改成生产密钥；AI 练习默认使用 mock provider，不要求学员自备付费密钥。

默认按推荐方案执行；如果其中任何一项要改，先改本文件，再动内容。

## 15. 风险与边界

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| S6 变成框架教程 | 课时滑向 Next.js/React 语法与组件库 | 只讲契约、渲染策略、实时、安全与可观测性；框架只作为实现载体，版本无关 |
| S7 变成模型训练课 | 滑向 Transformer 数学、微调、GPU 集群 | 明确边界：只讲应用工程与基础设施素养；模型训练与微调不在课程范围 |
| AI Coding 变成工具教程 | 工具名/版本变化快，学员已有基础却学不到体系 | 按五层模型讲；工具只做载体；示例覆盖 IDE/CLI/CI 三类中的两类；练习用固定仓库夹具与验收测试 |
| AI Coding 内容太浅 | 学员已会用 AI，重复讲基础会失去兴趣 | 从失败案例与度量切入；先做自评；练习要求独立验证与复盘，不要求背提示词 |
| 自动化偏见 | 学员信任 AI 自述，跳过验证 | 强制独立验证、红队用例、回滚演练；review 政策与协作记录 |
| 协作记录流于形式 | 只写「用了 AI」，没有证据 | 模板要求任务分类、上下文、验证证据、失败与改进；项目验收抽查 |
| AI 内容过时 | 模型名、价格、上下文长度、SDK 行为变化快 | 机制优先；版本/价格标注日期；provider 接口可替换；练习用本地 mock |
| AI 练习成本与密钥 | API 费用、密钥泄漏、供应商锁定 | 默认 mock/小模型；预算上限；密钥只走环境变量；不把密钥写进仓库 |
| AI 安全 | 直接/间接提示注入、PII 泄漏、越权检索 | 注入用例、租户过滤、输出审查、最小权限、引用可追溯 |
| 课程过长 | 57 小时让学员失去节奏 | 核心阶段必须按顺序；附录标注「按需查阅」；每阶段有明确出口，可阶段结业 |
| p6/p7 重复实现后端 | 又写一套 API、缓存、队列 | p6/p7 只做组装与产品层；后端能力直接复用 p2-p5，验收看端到端而非重复造轮子 |
| ID 迁移丢进度 | 老用户本地进度指向旧 `s6-l*` | P1 加一次性映射；迁移脚本与结构审计同时验收 |
| 事实漂移 | 版本、默认行为、性能数字过时 | 关键事实标注来源与版本；无法确认的写「取决于版本」，不写死 |
| 方案题无法评分 | 答案开放，学员不知道对错 | 给参考要点与反例；评分看约束、备选、代价、反悔条件四项是否齐全 |
