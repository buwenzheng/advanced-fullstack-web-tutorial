## 3. 本轮发现与修复

1. 一致性哈希的均衡断言最初用 `link-0000` 形式的连续 key，5 节点 100 虚拟节点下最大份额达到 42%，会误伤正确实现。改用 `link:<n>` 夹具后实测份额 16.1%–24.8%，并把增删节点断言改为「其余节点映射不变、只迁移该节点 key」，测试保持确定性且不依赖随机。
2. 哈希环 starter 故意不实现虚拟节点、不回绕、重复 add 不去重；7 条测试中有 5 条失败，solution 全过。Python 轨使用同一夹具与同一 FNV-1a，`bisect_left` 与 JS 二分行为一致。
3. s5-l3 的 token 源最初打算用本地时钟，可能在同毫秒产生重复 token，且无法保证「新 token 严格大于旧 token」。改为 store 的单调 `nextToken()`，并在测试中覆盖「旧 token 写入被拒 / 新 token 写入成功」。
4. s5-l3 的 Python 展示块包含 `asyncio`、`time`、`random` 三个导入，已补齐；四条新展示块全部通过 `python -m py_compile`。
5. 两份规格的事实表最初引用了不存在的 registry 条目名（「复制延迟」「一致性哈希」等）。已改为指向真实行或明确标注「通用机制，无版本型事实」，与 `check-facts` 的实际口径一致。
6. p5 第 1 步明确要求「保留 p3 的业务接口与返回结构，不增加同步调用」，里程碑与检查项都写死「跳转主链路不同步调用统计」，避免项目升级被误解为要重写 p3。

## 4. 边界与对齐检查

- s5-l3 与 s3-resilience：s3 讲单服务的超时、重试、退避与熔断实现；s5-l3 从「结果未知」出发讲跨服务重试预算、租约与 fencing token，没有重复退避公式，也不展开 CRDT/共识算法。
- s5-l3 与 s5-l2：s5-l2 负责事件不丢不重与读模型一致性；s5-l3 负责锁失效、旧写入与重试放大，两者的失败场景不重叠。
- s5-data-scale 与 a3：只讲复制、分片键、一致性哈希与分布式 ID 的结构与取舍，没有 B+tree/LSM 内部结构、页分裂或 compaction。
- s5-data-scale 与 s1-schema：复用索引与查询计划结论，不重讲 SQL 优化；分片前先优化索引与缓存的判断与 s1 一致。
- p5 与 p3：p5-m1 保留 p3 的跳转接口与 BullMQ 业务语义，只把事件发布替换为 Outbox + RabbitMQ；p5-m4 的读模型按「日期 + link_id」组织，与 s5-data-scale 的跨分片聚合建议一致。
- 未新增课程；S6/S7/附录保持 draft；未修改 `functions/`；站点保持私有。

## 6. 残余风险

- `s5-data-scale` 的均衡份额依赖固定 key 夹具，若未来替换默认哈希或修改节点名，需同步重算断言；测试已写明 10%–30% 的意图，避免变成魔法数字。
- 分布式 ID 展示块只演示结构，不包含完整的多线程/多进程序列分配器；生产实现还需处理序列耗尽后的等待策略。
- p5 的故障演练需要 RabbitMQ 与 PostgreSQL 环境，课程仓库只提供演练脚本设计，不包含可执行容器编排；这与 p4 的 k6/Docker 交付边界一致，留到项目实践完成。
- 两条 Python 展示块只做语法编译检查，不进入判题器；实际运行路径由 Python 轨的 7 条测试覆盖。
