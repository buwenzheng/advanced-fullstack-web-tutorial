## 3. 本轮发现与修复

1. s5-l1 的环检测初版只按 DFS 访问顺序记录环，未做旋转归一，`a→b→a` 在不同起点可能被报两次。现按环路径旋转到字典序最小形式去重，并统一排序，测试覆盖两个不相交环的稳定输出。
2. s5-l1 的 starter 只检查自依赖，并把规则方向写反；solution 使用三色标记与排序邻接表，7 条测试全部通过，starter 在直接环、间接环、分层违规、未知规则与多环测试上失败。
3. s5-l2 的 starter 故意「先 markSent 再 publish」「消费者先记 eventId 再 apply」，在发布失败累加 attempts、达到上限不再抢占、消费失败可重试三条测试上失败；solution 先把事件与业务写入放在同一 `transaction` 回调，成功后才标记。
4. s5-l2 的 Python 测试使用 `asyncio.Event` 控制发布器，验证两个发布器抢占互斥；不在测试中使用真实 sleep。Python 轨 8 条测试与 Node 题数量一致。
5. 两讲的规则边界均在正文中写明：s5-l1 不写 ADR 模板（a10）；s5-l2 不重复 BullMQ 的队列 API（s3-l2），只讲双写窗口与 Outbox 的部署方式。

## 4. 边界与对齐检查

- `s5-l1` 只讲边界判断、依赖图与迁移；不写 ADR 文档格式（a10），不展开服务网格与部署拓扑（a8）。
- `s5-l2` 与 `s3-l2` 的分工清晰：s3-l2 讲应用内队列与幂等消费者，本讲讲「业务提交与事件发布如何原子」以及「消费者如何跨部署幂等」；不重讲队列 API。
- `s5-l2` 与 `p5` 对齐：`p5-m1` 同事务写明细与 outbox，`p5-m2` SKIP LOCKED 发布器，`p5-m3` eventId 幂等与唯一索引兜底。
- `s5-l1` 的模块边界设计题明确「统计服务可以独立，API 与 Web 不必拆」，为 p5 的部署边界提供依据。
- 两讲均使用 `FOR UPDATE SKIP LOCKED` 作为 PostgreSQL 概念举例，正文与事实登记都注明它是数据库特性，不写成通用 SQL。
