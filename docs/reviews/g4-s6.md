s6-l2 的练习是「页面特征 → 渲染策略 → 性能预算」的单层纵向链路，不强行算跨层；跨层门槛由上述三道满足。

### 4.2 逐项证据

- **并发启动而非顺序等待（s6-l1）**：`loadDetail` 返回后立即断言三个上游均已启动，顺序 `await` 实现无法通过；总超时用例注入假 scheduler，推进到 `timeoutMs` 后断言 `stats === null` 且 `meta` 标为未完成，迟到结果 resolve 后再次断言仍未写入。
- **degraded 显式标记（s6-l1）**：stats 失败时 `degraded` 精确等于 `['stats']`，`stats` 为 `null`，其余字段保留；成功时 `degraded` 为空数组。
- **重复 / 乱序 / 缺口三态（s6-l3）**：同 id 重复事件只累加一次；seq2 先到、seq1 后到仍按 id 去重；seq4 跳号后 `gap` 粘性为 true，后续事件到达不自动清除，需补拉重置。Python 轨道 9 条测试与 Node 对齐。
- **traceId 合并与 incomplete（s6-l4）**：正常用例按 `startMs` 排序 span，以浏览器 LCP 为终点得到 `totalMs=4200`、`largestGap=3000`；traceId 缺失或不匹配时返回 `incomplete: true`，不伪造完整链路。
- **正文跨层标注**：三道代码题标题均含「跨层」；s6-l4 的 Python 展示块标题也标注「跨层：浏览器 → 服务端」。
- **p6 端到端还原**：p6-m6 验收要求「RUM 事件与服务端 trace 用同一 traceId 合并，缺失时标记 incomplete」；第 7 步要求「一个 traceId 能从浏览器 LCP 还原到服务端 span，并标出最大缺口」。

### 4.3 跨层测试的不可替代性

- s6-l1 的并发用例不是测「结果对不对」，而是测「启动顺序」：先 `await` 第一个上游再启动第二个的实现，在 `loadDetail` 返回前只能启动一个上游，测试直接失败。
- s6-l3 的三态用例使用真实传输顺序而非人为打乱数组：重复事件按到达顺序再次调用，乱序用例先送入 seq2 再送入 seq1，缺口用例从 seq1 跳到 seq4；实现必须维护已见 id 与期望 seq。
- s6-l4 的 trace 用例同时注入浏览器侧与 API 侧数据，排序与缺口计算跨越两层；只做单侧聚合无法得到 3000ms 的结尾等待缺口。

- **m4 可检查安全项**：Cookie 属性可检查、localStorage 无 token、CSRF 缺失时写操作被拒、越权 403、CORS 不通配 credentials。
- **m5 断线重连演示**：断网后自动重连并补拉、重复不重复计数、seq 缺口有标记、降级轮询可用且恢复后自动切回。
