## 3. 本轮发现与修复

1. JS 用 `Math.round`，Python 的 `round` 是银行家舍入；抖动的半值样本会出现不一致。Python 轨改为 `int(x + 0.5)`，测试用 0.5 与 1.0 两个边界固定行为。
2. 熔断器半开探测失败后如果只把状态改回 open、不重置 `openedAt`，下一次 `execute` 会立刻再次满足冷却条件，形成连续探测。实现改为失败时写入 `openedAt = now()`，并用测试验证冷却重新计时。
3. `state` getter 带 `refresh()` 会让读取状态本身触发转换。测试改为通过 `execute` 驱动 open → half-open → closed，避免依赖 getter 的副作用；getter 仍保留刷新以便观察。
4. 半开状态必须只允许一个探测：用 `probing` 标记挡住并发，探测结束在成功与失败两条路径都清理；否则恢复瞬间的并发会把尚未恢复的下游再次压垮。
5. `planRetries` 的 budget 只累计「延迟之和」，不包含每次尝试的耗时；正文与 note 明确真实系统要把尝试耗时计入调用方 deadline，避免把示例参数当成生产预算。
6. 令牌桶拒绝时的 `retryAfterMs` 在补充速率为 0 时为 `Infinity`；429 响应构造器对非有限值回退到 60 秒，避免序列化出非法头。测试覆盖了普通拒绝与耗尽后按时间恢复。
7. p3 旧文案只有 5 步、4 个里程碑，且没有写清与 p5 的因果；重写为 6 步 / 5 个里程碑，并在 brief 与清单中固定「p3 是应用内队列、p5 才升级」的边界。

## 5. 残余风险

- 令牌桶是单进程对象，多实例共享配额需要 Redis Lua 或等价原子操作；正文只讲机制，代码题不实现分布式版本。
- 熔断器没有给 `fn` 强制超时；如果被调用函数永远不返回，半开探测会一直挂起。生产实现需要 AbortController/超时包装，正文在 note 中提示。
- `planRetries` 只按延迟预算截断，不判断错误类型；可重试判定由调用方负责，代码题未实现 `isRetryable`。
- 幂等键的并发安全依赖唯一索引或原子写入，本讲在表格与方案题中要求，代码题未实现存储层。
- p3 的 BullMQ、压测与故障演练是项目文案，仓库内没有对应可执行代码；验收依赖项目实现时的脚本与报告。
