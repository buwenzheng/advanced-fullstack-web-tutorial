## 5. 项目检查

- **p2 LinkHub 对外 API**：6 步、5 个里程碑（p2-m1..m5）、5 项交付物、6 条清单。OpenAPI 字段、错误码表、幂等键与限流响应头、跨租户测试均写入步骤或验收标准；契约测试与 OpenAPI 漂移检查作为里程碑交付，文案完整。
- **p3 LinkHub 缓存与异步**：6 步、5 个里程碑（p3-m1..m5）、6 项交付物、6 条清单。缓存链路覆盖 Cache-Aside、主动失效、空值缓存与 single-flight；异步链路覆盖事件 ID、幂等消费、ack/重试/DLQ；压测要求正常与突发两个场景并至少定位一个真实瓶颈；故障演练覆盖消费者崩溃、Redis 不可用、队列积压；验收包含「重复点击只计一次」「超限 429」「关掉统计不影响跳转」。
- **执行边界**：p2/p3 是学习项目文案，仓库内不包含学员实现。契约测试、压测报告与故障演练的实际产物由学员按步骤产出；本次门禁核对的是步骤、里程碑、交付物与验收标准是否可执行、是否与 S2/S3 课程口径一致，不对未实现的项目代码做伪造验收。
- **p3 与 p5 边界**：brief、步骤与清单三处固定「p3 是随 API 进程部署的 BullMQ 应用内队列，p5 才升级 Outbox + RabbitMQ」，避免把应用内队列当成分布式消息系统。

## 8. 残余风险

- 教学实现与生产实现的差距已在正文 note 声明：单进程令牌桶、单实例 single-flight、单进程队列的 `reserve` 原子性、教学版熔断器不强制 `fn` 超时；分布式版本依赖 Redis Lua、broker 锁与超时包装，课程只讲机制不承诺代码可直接上线。
- Python 轨与 JS 轨存在语言差异：整数除法、银行家舍入、字典空值判断、async 模型。已用固定样本与对照 note 固化行为，但真实项目迁移仍需按语言习惯重写。
- 游标不签名、webhook 示例依赖服务端 runtime、租户仓储绑定占位符风格，这些都在批次报告中登记；对应项目实现时需按 p2 验收标准补齐。
- p2/p3 的可执行产物（契约测试、压测报告、故障演练记录）不在仓库内，属于学员任务；G2 只保证文案可执行且口径一致。
- 事实登记覆盖了 HTTP 语义、Redis 过期、AMQP/BullMQ/Kafka 投递语义、限流与韧性机制，但不锁定具体版本默认参数；这是刻意的「版本相关结论不写死」策略。
