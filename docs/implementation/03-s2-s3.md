# M3：S2-S3 内容模块（8 讲 + p2 + p3）

> 依赖：G1。产出：API 契约与保护机制两条主线，p2 对外 API、p3 缓存与异步。通过 G2 后进入 M4。

## 1. 模块目标

- S2 只回答「接口对第三方是否可依赖」：资源、方法、错误、认证、分页、幂等与限流**契约**。
- S3 只回答「系统在压力与故障下是否扛得住」：缓存、队列、限流、超时/重试/熔断/幂等的**实现**。
- p2 在 p1 数据层上加契约；p3 在 p2 API 上加保护，不重写 p2。
- 严守 `s2-l4` 与 `s3-l3`、`s2-l4` 与 `s3-resilience` 的边界，禁止同一机制讲两遍。

## 3. S2 课时 brief

### s2-l1 资源建模与 HTTP 语义（75 min）

**Objectives**

1. 把 LinkHub 的业务对象建模成资源树，而不是 RPC 动词堆。
2. 为每个端点选择正确的方法、状态码与幂等语义。
3. 设计版本化与弃用策略，保证向后兼容。
4. 解释「API 是契约」对前端、网关、监控和第三方的约束。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 组件 props 与公开 API | props 改坏影响一个页面；API 改坏影响所有调用方 |
| 2 | text | 资源 vs 动作 | 什么时候 REST 合适，什么时候 RPC 更清楚 |
| 3 | flow | 领域 → 资源树 → 端点 → 方法 → 状态码 | 先画关系，再定路径 |
| 4 | table | LinkHub 资源树 | `/links`、`/links/:id`、`/links/:id/clicks`、`/users/me`、`/auth/*` |
| 5 | table | 方法与幂等 | GET/POST/PUT/PATCH/DELETE；哪些可重试 |
| 6 | code | 路由匹配器 | 路径参数、方法不匹配 405、未知路径 404 |
| 7 | pitfall | URL 里塞动词、状态码乱用 | `/getLinks`、`200 {code:500}`、暴露内部 ID |
| 8 | steps | 从用户故事设计端点 | 用户故事 → 资源 → 方法 → 状态码 → 错误 |
| 9 | compare | 版本化策略 | 路径版本、Header、媒体类型；弃用与迁移窗口 |
| 10 | text（深挖） | 契约稳定性 | 加法兼容、破坏性变更、消费者驱动契约 |
| 11 | note | 面试延伸 | 为什么 API 设计比实现更难改；如何做弃用 |

**概念检查**

- C1 单选：给定「把链接归档」应建模成什么资源/方法。
- C2 多选：哪些方法应保证幂等；哪些状态码适合创建/冲突/删除。
- C3 单选：新增必填字段属于什么变更，应该怎么发布。

**代码题：路由匹配器**

- 契约：`matchRoute(routes, method, path)`，routes 为 `{ method, pattern }`，pattern 支持 `:param`；返回 `{ route, params }`；路径存在但方法不匹配返回 `{ error: 'method_not_allowed', allowed }`；未知路径 `{ error: 'not_found' }`。
- 测试（≥5）：静态路径；参数路径；方法不匹配；URL 解码；尾部斜杠；重复参数名报错。
- Python：dict 返回；`urllib.parse.unquote`；正则命名组。
- 常见错误：把 404 和 405 混用；参数未解码；路由顺序导致 `/links/:id` 吃掉 `/links/search`。

**方案题：LinkHub 资源树与版本化**

- 自检清单：资源命名；嵌套层级；分页/过滤放 query；版本策略；弃用窗口；错误码；幂等；保留路径。
- 参考要点：`/v1/links` 路径版本简单可路由；新增字段向后兼容；删除/改语义需要新版本或迁移期；不要暴露数据库自增 ID 作为公共标识。

**事实清单**：HTTP 方法幂等性（RFC 9110）；201/202/204/409/410/429 语义；版本化没有唯一标准，写取舍。

**边界**：认证在 s2-l3；限流契约在 s2-l4，算法在 s3-l3。

### s2-l2 输入校验与错误契约（75 min）

**Objectives**

1. 在边界做 schema 校验：类型、范围、格式、未知字段、跨字段。
2. 设计稳定的错误信封与可枚举错误码。
3. 区分 4xx/5xx，不泄漏堆栈、SQL、内部路径。
4. 用测试覆盖校验与错误映射。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | TS 类型在运行时消失 | 前端类型检查不等于服务端安全 |
| 2 | text | 三层校验 | 传输层、schema 层、业务层；fail fast |
| 3 | table | 校验规则 | required/type/range/format/cross-field/unknown keys |
| 4 | code | 零依赖校验器 | 返回结构化 errors，不抛裸异常 |
| 5 | code | 错误信封 | `{ error: { code, message, requestId, details? } }` |
| 6 | table | 错误码与 HTTP 映射 | validation_error/unauthorized/forbidden/not_found/conflict/rate_limited/internal |
| 7 | pitfall | 校验失败返回 500 | 泄漏栈/SQL；同一错误多种文案；接受未知字段 |
| 8 | steps | 校验 → 映射 → 记录 → 响应 | 错误日志带 requestId，不回传内部细节 |
| 9 | compare | 手写校验 vs schema 库 | 依赖、可读性、错误信息、性能 |
| 10 | text（深挖） | 错误契约演进 | 机器码稳定、文案可改；details 的结构；i18n |
| 11 | note | 面试延伸 | 为什么 422 和 400 都有人用；如何设计可观测的错误码 |

**概念检查**

- C1 单选：格式错误、业务冲突、未认证分别返回什么。
- C2 多选：错误信封应满足哪些约束。
- C3 单选：客户端多发了一个未知字段，应该接受还是拒绝，取决于什么。

**代码题：创建短链的校验器**

- 契约：`validateCreateLink(input, { now = Date.now() } = {})` 返回 `{ ok:true, value }` 或 `{ ok:false, errors:[{ field, code }] }`；`expiresAt` 与注入的 `now` 比较，测试不依赖真实时钟。
- 规则：`url` 必填且为 http/https；`slug` 可选，4-32 位字母数字/连字符，保留字拒绝；`expiresAt` 可选，必须是严格晚于 `now` 的 ISO 时间；未知字段拒绝；`title` 可选但 ≤120 字。
- 测试（≥6）：合法；缺 url；非法协议；slug 冲突保留字；`expiresAt` 等于或早于注入的 `now`；未知字段；错误顺序稳定。
- Python：返回 tuple/dict；`datetime.fromisoformat`；用注入的 `now`（带时区）比较。
- 常见错误：只校验类型不校验语义；把第一个错误抛异常；错误信息泄漏内部字段名。

**方案题：LinkHub 错误码表**

- 自检清单：错误码可枚举；HTTP 映射；用户文案与机器码分离；details 只放安全字段；requestId；日志级别；兼容策略。
- 参考要点：错误码是契约的一部分；新增码是加法兼容，改语义是破坏性变更；5xx 不暴露内部原因。

**事实清单**：HTTP 400/401/403/404/409/422/429 语义；JSON Schema 不是运行时本身；不同框架错误对象不同。

**边界**：认证/授权在 s2-l3；限流 429 的实现与策略在 s3-l3。

### s2-l3 认证、授权与多租户（75 min）

**Objectives**

1. 区分认证与授权，比较 Session/JWT/Refresh/API Key 的取舍。
2. 实现 RBAC/ABAC 判定与租户隔离。
3. 解释 token 存储、轮换、撤销与 CSRF/XSS 的关系。
4. 写出覆盖越权与跨租户的测试矩阵。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 前端路由守卫不是安全边界 | 守卫只影响体验；服务端必须再判一次 |
| 2 | text | 认证 vs 授权 | 你是谁 vs 你能做什么 |
| 3 | table | Session/JWT/Refresh/API Key | 存储、撤销、扩展、CSRF、适用场景 |
| 4 | flow | 登录 → 凭证 → 请求 → 认证 → 授权 → 租户过滤 | 每一步的失败码 |
| 5 | code | 授权判定器 | role/attribute/tenant；默认拒绝 |
| 6 | code | 租户作用域仓储 | 所有查询强制带 tenant_id |
| 7 | pitfall | 信任客户端角色 | 缺租户过滤、JWT 无法撤销、token 放 localStorage、IDOR |
| 8 | steps | 威胁建模与测试矩阵 | 匿名/本人/他人/管理员/跨租户/过期 |
| 9 | compare | RBAC vs ABAC vs ReBAC | 表达能力、复杂度、性能 |
| 10 | text（深挖） | Refresh 轮换与重用检测 | 会话固定、撤销列表、短生命周期 access token |
| 11 | note | 面试延伸 | 401 与 403 的边界；如何做多租户数据隔离 |

**概念检查**

- C1 单选：未登录、已登录但无权限分别返回什么。
- C2 多选：JWT/Session 的取舍。
- C3 单选：跨租户访问最可能漏在哪一层。

**代码题：授权判定器**

- 契约：`authorize({ user, action, resource })` 返回 `{ allowed, reason }`。
- 规则：匿名只能读公开链接；本人可读写自己的链接；管理员可读所有但跨租户写拒绝；租户不匹配默认拒绝；未知 action 默认拒绝。
- 测试（≥6）：本人读/写；他人读/写；管理员跨租户读/写；匿名；未知 action。
- Python：dataclass/dict；默认拒绝；返回原因码。
- 常见错误：先判管理员再判租户；把「不是本人」当成允许；未知 action 默认允许。

**方案题：LinkHub 认证与租户隔离**

- 自检清单：Session vs JWT；refresh 轮换；撤销；Cookie 属性；CSRF；API Key；RBAC 角色；租户过滤；越权测试；日志脱敏。
- 参考要点：浏览器端优先 HttpOnly Cookie + CSRF；API 客户端用 API Key；JWT 短生命周期 + refresh；租户过滤放在数据访问层而不是每个 handler。

**事实清单**：JWT 是签名令牌不是加密；HttpOnly/SameSite/Secure 语义；OAuth/OIDC 区别；不同框架 CSRF 默认行为不同。

**边界**：全栈会话/CSP/CSRF 的完整实现与实时链路在 s6-l3；本讲只讲 API 侧认证授权与租户隔离。

| # | type | 标题 | 要点 |

**概念检查**

- C1 单选：列表数据频繁插入时 offset 分页的问题。
- C2 多选：幂等键契约应包含哪些规则。
- C3 单选：限流响应应包含哪些信息（429/Retry-After/配额头）。

**代码题：游标分页**

- 契约：`paginate(items, { limit, cursor })`；items 已按 `createdAt desc, id desc` 排序；cursor 是 base64 的不透明串；返回 `{ data, nextCursor }`；非法 cursor 抛 `InvalidCursorError`；limit 上限 100，默认 20。
- 测试（≥6）：第一页；下一页；最后一页；非法 cursor；limit 上限；相同时间戳的 tie-breaker。
- Python：`base64.urlsafe_b64encode`；异常类；稳定排序。
- 常见错误：cursor 直接用 offset；没有 tie-breaker；limit 不设上限；返回内部自增 ID 作为 cursor 明文。

**方案题：LinkHub 对外 API 契约**

- 自检清单：分页；过滤/排序白名单；幂等键；限流头；Webhook 签名与重试；OpenAPI；契约测试；版本化；SLA。
- 参考要点：契约先于实现；错误码与字段稳定；限流只定义语义，算法在 s3-l3；幂等键的作用域要写清。

**事实清单**：429/Retry-After 语义；HMAC 签名；OpenAPI 版本；Webhook 重试没有统一标准。

**边界**：令牌桶/漏桶/滑动窗口实现、分布式限流、过载丢弃全部在 s3-l3；本讲不写算法。

## 4. S3 课时 brief

### s3-l1 缓存分层与失效策略（85 min）

**Objectives**

1. 为一条读路径选择浏览器/CDN/应用/数据库缓存层。
2. 实现 Cache-Aside、TTL、主动失效、空值缓存与 single-flight。
3. 解释穿透/击穿/雪崩的成因与防护。
4. 用命中率、DB QPS、P99 证明缓存收益。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 前端 memo 与分布式缓存 | 失效才是难点；缓存一致性是业务问题 |
| 2 | flow | 四层缓存与命中路径 | 浏览器 → CDN → 应用 → DB |
| 3 | table | 缓存模式 | cache-aside/read-through/write-through/write-behind |
| 4 | code | Cache-Aside | get → miss → load → set；TTL |
| 5 | code | 防护 | single-flight、空值缓存、TTL 抖动 |
| 6 | table | 穿透/击穿/雪崩 | 原因、现象、防护 |
| 7 | pitfall | 缓存错误与脏数据 | 缓存异常；更新顺序；TTL 全相同；热点 key |
| 8 | steps | 度量与失效 | 命中率、DB QPS、P99；提交后失效；重试 |
| 9 | text（深挖） | 一致性与热 key | TTL vs 主动失效；延迟双删的边界；本地缓存 |
| 10 | note | 面试延伸 | 先更新 DB 还是先删缓存；为什么缓存不能解决所有问题 |

**概念检查**

- C1 单选：热点跳转应选哪种缓存模式。
- C2 多选：穿透/击穿/雪崩的防护。
- C3 单选：更新链接后缓存失效的正确顺序与失败处理。

**代码题：带防护的缓存**

- 契约：`createCache({ ttl, max, now })` 提供 `get(key, loader)`、`set`、`delete`；同一 key 并发 miss 只调用一次 loader；loader 失败不缓存；支持负缓存（短 TTL）。
- 测试（≥6）：命中；过期；并发 single-flight；loader 失败；负缓存；delete。
- Python：async 版本；`asyncio.Lock`；字典 + 时间注入。
- 常见错误：缓存 Promise 但不清理；失败也缓存；TTL 没有抖动；并发 miss 打穿。

**方案题：LinkHub 缓存方案**

- 自检清单：缓存对象；key 设计；TTL；主动失效；穿透/击穿/雪崩；热点 key；一致性；监控指标；回滚。
- 参考要点：跳转读多写少，cache-aside 合适；更新/删除后失效；空值短 TTL；single-flight；命中率与 DB QPS 作为验收。

**事实清单**：Redis 过期策略、Cache-Aside 不是规范；TTL 抖动是实践；不同缓存的一致性模型不同。

**边界**：CDN/边缘缓存与 SWR 在 s6-l4；本讲只讲应用缓存；Redis 集群/持久化不在本讲。

### s3-l2 消息队列与异步任务（85 min）

**Objectives**

1. 解释 at-most-once/at-least-once 与「精确一次」的工程含义。
2. 实现 ack、可见性超时、重试退避、死信与幂等消费。
3. 诊断积压、毒消息与消费者不足。
4. 为 LinkHub 点击事件设计一条可恢复的异步链路。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 前端事件队列与服务器队列 | 重试、重复投递、顺序与背压 |
| 2 | text | 生产者/队列/消费者 | ack、可见性超时、投递语义 |
| 3 | flow | 入队 → 投递 → 处理 → ack | 失败重投；超时；死信 |
| 4 | code | 可见性超时队列 | reserve/ack/nack；超时重投 |
| 5 | code | 幂等消费者 | 去重键 + 处理结果；唯一约束兜底 |
| 6 | table | 重试/退避/DLQ | 次数、间隔、抖动、最大年龄 |
| 7 | pitfall | 先 ack 后处理 | 无限重试；毒消息；副作用不幂等 |
| 8 | steps | 积压排查 | 入队/出队速率、消费者数、毒消息、扩容、重放 |
| 9 | compare | BullMQ/RabbitMQ/Kafka | 概念差异；不写厂商教程 |
| 10 | text（深挖） | 投递语义 | exactly-once 是端到端效果，不是队列属性 |
| 11 | note | 面试延伸 | 重复消息怎么处理；消息顺序重要吗 |

**概念检查**

- C1 单选：消费者处理成功但 ack 前崩溃，会发生什么。
- C2 多选：幂等消费需要哪些条件。
- C3 单选：队列积压且消费速率低，先看什么。

**代码题：可见性超时队列 + 幂等消费者**

- 契约：`createQueue({ visibilityTimeout, maxAttempts, now })`；`enqueue(payload)`；`reserve()` 返回 `{ id, payload, attempt }` 或 null；`ack(id)`；`nack(id)`；超过次数进入 DLQ。
- 消费者：`consume(queue, handler, processed)`，`processed` 是去重 Set/Map；同一事件重复投递只执行一次副作用。
- 测试（≥7）：正常 ack；超时重投；nack 重试；超过次数进 DLQ；重复消息只处理一次；空队列；失败不 ack。
- Python：`asyncio` 或同步版本；时间注入；dict 去重。
- 常见错误：ack 在 handler 之前；重投没有 attempt；去重键只用 payload 且不稳定；DLQ 不可重放。

**方案题：LinkHub 点击事件链路**

- 自检清单：事件 ID；幂等键；ack 时机；重试/退避；DLQ；重放；顺序要求；监控；消费者扩容；与 p5 Outbox 的关系。
- 参考要点：p3 用 BullMQ 解决「慢活出请求链路」；入队与业务提交仍是两次写，p5 再用 Outbox 消除双写窗口；不要在 p3 把 p5 的事做完。

**事实清单**：at-least-once 与 ack 语义；BullMQ/RabbitMQ/Kafka 的投递模型差异；exactly-once 需要端到端幂等。

**边界**：Outbox/Saga/最终一致在 s5-l2；p5 会把 p3 的应用内队列升级为独立服务。

**代码题：令牌桶**

- 契约：`createTokenBucket({ capacity, refillPerSecond, now })`；`tryConsume(tokens)` 返回 `{ allowed, remaining, retryAfterMs }`；支持小数 token；时钟注入。
- 测试（≥6）：初始满桶；消耗；按时间补充；突发；耗尽后的 retryAfter；容量上限。

**事实清单**：令牌桶/漏桶/滑动窗口的算法行为；429/Retry-After 语义；Redis 原子操作需要 Lua/事务；不同网关限流实现不同。

**边界**：s2-l4 只定义契约；本讲实现算法与调参；不写具体网关产品教程。

**Objectives**

| 2 | text | 超时分层 | 客户端、网关、服务、下游；deadline 传递 |
| 3 | table | 重试策略 | 固定/指数/抖动/预算；哪些错误可重试 |
| 4 | code | 重试计划 | 预算、最大次数、抖动、可重试判定 |
| 5 | flow | 熔断器三态 | closed/open/half-open；阈值、冷却、探测 |
| 6 | code | 熔断器 | 状态转换、成功/失败计数、半开探测 |

| 12 | note | 面试延伸 | 重试次数越多越好吗；熔断和限流的区别 |

**概念检查**

- C1 单选：哪些错误适合重试；POST 重试的前提。
- C2 多选：熔断器状态与转换条件。
- C3 单选：幂等键相同但 body 不同，应该怎么处理。

**代码题：重试计划 + 熔断器**

- 契约 A：`planRetries({ maxAttempts, baseDelayMs, maxDelayMs, budget, random })` 返回每次重试的延迟数组；抖动在 `[0.5, 1.5]` 倍之间；超过预算停止。
- 契约 B：`createCircuitBreaker({ failureThreshold, cooldownMs, now })`；`execute(fn)`；closed 连续失败达到阈值 → open；冷却后 half-open；half-open 成功 → closed，失败 → open。
- 测试（≥8）：重试延迟递增；抖动边界；预算耗尽；熔断打开；冷却半开；半开成功/失败；成功重置计数。
- Python：同步版本；`random.Random(seed)` 保证确定性；时间注入。
- 常见错误：重试所有 4xx；抖动没有上下界；熔断打开后仍然放行；半开并发探测过多。

**方案题：LinkHub 韧性方案**

- 自检清单：超时分层；重试预算；可重试错误；熔断阈值；隔离舱；幂等键；分布式锁边界；降级；演练。
- 参考要点：跳转链路对统计服务失败要降级；创建接口用幂等键；不要对非幂等写盲目重试；锁不能保证「绝对不并发」，要用 fencing token/版本号。

**事实清单**：重试放大与 retry storm；熔断器常见实现；fencing token 的原理；分布式锁没有绝对安全，只有租约与版本。

**边界**：分布式一致性与 Outbox 在 s5-l2；本讲讲单服务韧性；不写服务网格/产品教程。
