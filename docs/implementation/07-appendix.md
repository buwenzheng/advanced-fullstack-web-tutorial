## 3. 课时 brief（a1-a6 数据结构线）

### a1 复杂度与测量：先能算，再能测（60 min）

**Objectives**

1. 用 Big-O 描述增长，而不是背结论；明确 n 与操作的定义。
2. 识别微基准的五个陷阱：预热、计时精度、GC、死代码消除、环境噪声。
3. 用分位数与变异系数判断数据是否稳定。
4. 从操作计数拟合增长阶，区分 O(1)/O(log n)/O(n)/O(n log n)/O(n²)。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 打包体积与时间复杂度 | 都关心「随规模怎么涨」 |
| 2 | text | Big-O 与 n 的定义 | 最坏/平均；操作是什么；常数因子 |
| 3 | table | 常见增长阶 | 典型算法与数据规模感受 |
| 4 | code | 从操作计数拟合增长 | 比值/对数斜率；噪声与未知 |
| 5 | text | 微基准五坑 | 预热、计时、GC、死代码、环境 |
| 6 | code | 压测数据汇总 | p50/p95/p99、均值、CV、稳定性 |
| 7 | case | 本地快 20%，线上慢 2 倍 | 数据规模与缓存状态不同；如何复测 |
| 8 | pitfall | 用平均值、忽略 GC、只测一次 | 结论不可复现 |
| 9 | steps | 设计一次可复现实验 | 规模梯度、重复次数、环境固定 |
| 10 | note | 面试延伸 | 为什么 O(n log n) 有时比 O(n) 快 |

**概念检查**

- C1 单选：n 的定义不清晰时，复杂度结论为什么无效。
- C2 多选：微基准必须控制哪些变量。
- C3 单选：p99 高、均值正常，说明什么。

**代码题：增长拟合 + 压测汇总**

- 契约：
  - `estimateGrowth(samples)`：`[{ n, ops }]` → `'O(1)' | 'O(log n)' | 'O(n)' | 'O(n log n)' | 'O(n^2)' | 'unknown'`；至少 3 个 `n` 互异且 `n > 0`、`ops > 0` 的点，否则 `unknown`。候选函数固定：`1`、`log2(n + 1)`、`n`、`n * log2(n + 1)`、`n^2`；对每个候选计算 `c_i = ops_i / f(n_i)`，取 `spread = (max(c) - min(c)) / max(c)`；最小 `spread <= 0.15` 即判定该复杂度，否则 `unknown`；并列按 `O(1) → O(log n) → O(n) → O(n log n) → O(n^2)` 取简单者。噪声阈值固定为 0.15，不随数据调整。
  - `summarizeBenchmark(samples)`：`[{ ms }]` → `{ count, mean, p50, p95, p99, cv, stable }`；最近秩分位；CV ≤ 0.1 视为稳定。
- 测试（≥8）：常数；线性；线性对数；平方；点数不足；噪声；空样本；分位边界。
- Python：排序 + 索引；`statistics`；返回 dict。
- 常见错误：用两个点就下结论；把 O(n log n) 判成 O(n)；CV 用总体/样本公式不一致。

**事实清单**：Big-O 是渐近上界；实际性能受常数、缓存、GC 影响；分位数算法有差异。

**边界**：性能压测与瓶颈定位在 `s4-perf`；容量建模在 `a7`；本讲只讲复杂度与测量方法。

### a2 哈希表：平均 O(1) 的代价与边界（65 min）

**Objectives**

1. 解释哈希函数、冲突、负载因子与扩容的关系。

3. 识别哈希洪水、最坏 O(n)、迭代顺序不稳定等边界。
4. 判断什么时候不该用哈希表（范围查询、排序、内存敏感）。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 快递柜与取件码 | 哈希 = 用钥匙直接找柜子 |
| 2 | text | 哈希函数与冲突 | 均匀性、确定性、冲突不可避免 |
| 3 | table | 链地址 vs 开放寻址 | 缓存友好、删除、负载因子、最坏情况 |
| 4 | code | 开放寻址哈希表 | 线性探测、墓碑、扩容、负载因子 |
| 5 | flow | put → 探测 → 冲突 → 扩容 → rehash | 每步的失败现象 |
| 6 | case | 哈希洪水打满 CPU | 恶意 key 制造冲突；修复与限制 |
| 7 | pitfall | 可变 key、删除不墓碑、扩容时机 | 数据丢失与无限探测 |
| 8 | text（深挖） | 最坏 O(n) 与语言实现 | 红黑树化、随机盐、迭代顺序 |
| 9 | steps | 为计数器选哈希表 | 规模、并发、内存、删除频率 |
| 10 | note | 面试延伸 | 为什么哈希表不保证顺序 |

**概念检查**

- C1 单选：负载因子升高时平均查找为什么变慢。
- C2 多选：开放寻址删除为什么需要墓碑。
- C3 单选：范围查询为什么不适合哈希表。

**代码题：开放寻址哈希表**

- 契约：`createHashMap({ initialCapacity = 8, maxLoad = 0.75 })`；方法 `set(key, value)`、`get(key)`、`has(key)`、`delete(key)`、`size()`、`loadFactor()`；字符串 key；线性探测；删除用墓碑；超过负载因子扩容 2 倍并 rehash；`get` 缺失返回 `undefined`。
- 测试（≥9）：基本读写；覆盖；冲突；删除；墓碑复用；扩容；负载因子；大量 key；缺失 key。
- Python：类 + list；`hash()` 结果取模；墓碑用哨兵对象；测试同样覆盖。
- 常见错误：删除直接置空导致探测链断裂；扩容后顺序错；负载因子用 size/capacity 但没算墓碑；key 可变。

**事实清单**：不同语言哈希表实现不同；哈希函数质量影响最坏情况；迭代顺序不保证稳定。

**边界**：B+tree/LSM 在 a3；Redis 哈希在 s3-l1；本讲只讲哈希表本身。

**代码题：简化 B+tree**

**代码题：环形缓冲 + LRU**

- 契约：
  - `createRingBuffer(capacity)`：`push(x)` 覆盖最旧；`read()` 按写入顺序返回未读；`available()`；`size()`；容量固定。

**事实清单**：Redis 使用近似 LRU 采样；LRU 对扫描型负载不友好；环形缓冲的丢弃策略取决于业务。

**内容块大纲**

| 1 | analogy | 门口保安的「好像见过」 | 误判有、漏判无 |
| 2 | text | 布隆过滤器 | 位数组、k 个哈希、误判率公式 |
| 3 | code | 布隆过滤器 | add/mightContain；误判率估算 |
| 4 | text | HyperLogLog | 分桶、前导零、调和平均、误差 |
| 5 | code | HyperLogLog | add/estimate；精度参数 |
| 6 | table | 精确 vs 概率 | 内存、误差、可删除性、适用 |
| 7 | case | 布隆过滤器说「可能存在」，DB 却没有 | 误判不是 bug；如何兜底 |
| 8 | pitfall | 用布隆做删除、忽略误判率、HLL 小基数误差 | 常见误用 |
| 9 | steps | 为短链去重选结构 | 规模、误判容忍、删除需求 |
| 10 | note | 面试延伸 | 布隆过滤器能不能删除元素 |

**概念检查**

- C1 单选：布隆过滤器返回 false 意味着什么。
- C2 多选：影响布隆误判率的因素。
- C3 单选：HLL 估算 100 万 UV，误差 2% 意味着什么。

**代码题：布隆过滤器 + HyperLogLog**

- 契约：
  - `createBloomFilter({ bits, hashes })`：`add(x)`、`mightContain(x)`、`falsePositiveRate()`；`hashes` 为注入的哈希函数数组；位数组长度固定。
  - `createHLL(precision)`：`add(x)`、`estimate()`；桶数 `2^precision`；用注入的 64 位哈希（可用两个 32 位拼接模拟）；小基数返回近似值。
- 测试（≥8）：布隆加入必命中；未加入可能误判；误判率估算；不同哈希数；HLL 空集；小基数；大基数误差范围；重复元素不重复计数。
- Python：位数组用 `bytearray`；哈希注入；HLL 用列表；测试同样覆盖。
- 常见错误：布隆删除置位；HLL 用平均值而不是调和平均；哈希分布不均；精度参数越界。

**方案题：短链去重与 UV 统计**

- 自检清单：数据规模；误判容忍；是否需要删除；内存预算；精确计数需求；降级；监控误差。
- 参考要点：布隆适合「可能存在」的前置过滤，不负责删除；UV 用 HLL 要接受误差；关键账务数据不能用概率结构。

**事实清单**：布隆过滤器不支持标准删除；计数布隆可删除但有代价；HLL 误差约 1.04/√m；不同实现哈希方式不同。

**边界**：Redis 缓存与淘汰在 `s3-l1`；分片与复制在 `s5-data-scale`；本讲只讲概率结构。

**代码题：测试组合审计 + flaky 检测**

- 契约：
  - `auditTestPortfolio({ unit, integration, e2e, contract, flaky })`：全部为非负整数计数；`total = unit + integration + e2e + contract`；返回 `{ total, flakyRate, findings: [{ code, severity, detail }] }`。
    - 规则：`total === 0` → `NO_TESTS`（high）；`unit === 0` → `NO_UNIT_TESTS`（high）；`integration === 0` → `NO_INTEGRATION_TESTS`（medium）；`contract === 0` → `NO_CONTRACT_TESTS`（medium）；`e2e / total > 0.2` → `E2E_TOO_HIGH`（medium）；`flaky / total > 0.01` → `FLAKY_RATE_HIGH`（high）。
    - 边界：e2e 占比恰好 0.2 不报；flaky 率恰好 0.01 不报；`total === 0` 时只报 `NO_TESTS`，不计算比例规则。
    - `detail` 包含相关计数与比例（比例保留 3 位小数）；findings 按 `severity` 降序（high → medium → low），同严重度按 `code` 升序。
  - `detectFlaky(history)`：`[{ name, results: boolean[] }]` → `[{ name, flips, flaky }]`；翻转次数 ≥ 2 视为 flaky；按翻转次数降序，同次数按 `name` 升序。
  - `detectFlaky(history)`：`[{ name, results: boolean[] }]` → `[{ name, flips, flaky }]`；翻转次数 ≥ 2 视为 flaky；按翻转次数降序。
- 测试（≥8）：健康组合；缺契约；端到端过多；flaky 率；无翻转；多次翻转；空历史；排序。
- Python：纯函数；比例；返回 dict。
- 常见错误：把重跑成功当修复；flaky 只看失败率不看翻转；契约测试只测一端。

**事实清单**：测试组合因系统而异；契约测试需要消费者与提供者配合；flaky 根因多样。

**边界**：CI/CD 流水线在 `s4-l4`；本讲只讲测试策略与工程质量。
