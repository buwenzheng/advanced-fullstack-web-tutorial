# M2：S0-S1 内容模块（7 讲 + p0 + p1）

> 依赖：G0。产出：S0 三讲、S1 四讲、p0 HTTP 探针 CLI、p1 LinkHub 数据层。通过 G1 后进入 M3。

## 1. 模块目标

- 建立「一次请求的完整路径」与「运行时并发模型」的心智模型；
- 把前端对象变成能持久化、能并发写、能演进的数据库结构；
- 让学员第一次用可验证的代码题证明自己理解了网络、事件循环、SQL、索引、事务与迁移；
- p0 是独立工具，p1 是 LinkHub 主线的起点。

## 3. S0 课时 brief

### s0-l1 从 URL 到响应：请求的四段旅程（55 min）

**Objectives**

1. 区分 DNS / TCP / TLS / HTTP 四阶段的职责与失败表现。
2. 用 `curl -w` 把一次请求拆成 5 个耗时，判断慢在哪一层。
3. 解释冷启动 RTT 预算、连接复用与 HTTP 版本对延迟的影响。
4. 为 LinkHub 跳转接口选择正确的 301/302/404/410 语义。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 浏览器帮你藏起了前四段 | DevTools 只看到 TTFB；后端要对整条链路负责 |
| 2 | flow | 四段旅程与典型故障 | DNS 失败、TCP 拒绝、TLS 证书、HTTP 5xx 各查什么 |
| 3 | text | 后端为什么多出三个问题 | 并发、持久化、失败；共享资源与容量上限 |
| 4 | code | 最小可运行的跳转服务 | `node:http` 返回 302 + Location，含 `/health` |
| 5 | table | 状态码分工 | 2xx/3xx/4xx/5xx；401 vs 403；410 的语义 |
| 6 | pitfall | 一切都塞进 200 | 网关无法重试、监控无法聚合、前端无法通用处理 |
| 7 | tip | `curl -v` 是显微镜 | 停在哪一行对应哪一层 |
| 8 | steps | 五步拆解请求耗时 | `time_namelookup/connect/appconnect/starttransfer/total` |
| 9 | text（深挖） | 冷启动的 4 个 RTT | TLS 1.2 vs 1.3；DNS 多层缓存；连接复用 |
| 10 | table | DNS 记录与 TTL | A/AAAA/CNAME/TXT/NS/SOA；迁移时的坑 |
| 11 | compare | HTTP/1.1 vs 2 vs 3 | 队头阻塞、多路复用、QUIC、0-RTT 重放风险 |
| 12 | note | 面试延伸 | 首请求为什么慢；如何减少 RTT；301 缓存的代价 |

**概念检查**

- C1 单选：`certificate has expired` 出现在哪一层；为什么「部分用户」失败。
- C2 多选：状态码语义（401/403/409/503/404）。
- C3 单选：切 A 记录后部分移动用户失败，`time_namelookup`/`time_connect` 正常，下一步查什么（AAAA 记录）。

**代码题：请求分段计时与归因**

- 契约：`analyzeTimings({ namelookup, connect, appconnect, starttransfer, total })`，单位秒，返回：

```js
{
  dns, tcp, tls, server, transfer, // 毫秒，非负
  total,
  slowest: 'dns' | 'tcp' | 'tls' | 'server' | 'transfer'
}
```

- 规则：`tcp = connect - namelookup`；`tls = appconnect - connect`；`server = starttransfer - appconnect`；`transfer = total - starttransfer`；任一阶段为负或总时长不单调时抛 `Error('invalid timings')`。
- 测试（≥5）：
  1. 正常 HTTPS 冷请求；
  2. 连接复用时 `connect=0`、`appconnect=0` 的 HTTP 请求；
  3. `server` 最大时 `slowest='server'`；
  4. 非单调输入抛错；
  5. 毫秒四舍五入到 1 位小数。
- Python 差异：返回 dict；浮点格式化用 `round(x, 1)`；异常用 `ValueError`。
- 常见错误：把 `namelookup` 当成 DNS 总耗时而忽略缓存；`total` 直接减各段导致负数；不校验单调性。

**方案题：LinkHub 跳转契约**

- 场景：`GET /:code` 跳转。有效、过期、封禁、不存在、保留字冲突。
- 自检清单：301/302 取舍；410 vs 404；是否暴露「存在但被封」；保留字校验；`Location` 编码；点击事件如何记录；错误体结构。
- 参考要点：302 优先（目标可变，避免 301 永久缓存）；过期用 410；封禁可 404 或 410，取决于是否愿意暴露存在性；保留字在创建时拒绝；跳转与统计解耦（为 S3 异步埋点）。

**事实清单**

| 声明 | 来源 | 备注 |
| --- | --- | --- |
| TLS 1.3 完整握手 1-RTT，1.2 为 2-RTT | RFC 8446 / RFC 5246 | 不写具体毫秒 |
| HTTP/2 多路复用，HTTP/3 基于 QUIC | RFC 9113 / RFC 9114 | 不写浏览器实现细节 |
| DNS TTL 不保证所有递归解析器严格遵守 | 运营商实践 | 写「可能」不写绝对 |
| 301 可被浏览器永久缓存 | RFC 9110 | 结合 LinkHub 说明风险 |

**边界**：不讲 TCP 拥塞控制、TLS 证书签发流程、Nginx 配置（a8）；不讲 CDN（S6）。

### s0-l2 Node.js/Python 运行时：事件循环与并发模型（60 min）

**Objectives**

1. 说出 Node 事件循环阶段与微任务/宏任务顺序。
2. 判断一段代码是否阻塞事件循环，解释 event loop lag 与线程池排队。
3. 写出带并发上限的调度器。
4. 对比 Node 事件循环与 Python GIL/asyncio 的并发模型。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 同一个厨房，两套排队规则 | 浏览器事件循环 vs Node libuv；同步代码卡死整个进程 |
| 2 | text | 六个阶段 | timers/pending/idle/poll/check/close；每个回调后清微任务 |
| 3 | table | 会阻塞与不会阻塞 | readFileSync、JSON.parse、while(true)、异步 fs |
| 4 | code | 观察执行顺序 | nextTick/Promise/setTimeout/setImmediate/IO 回调 |
| 5 | compare | Node vs Python | libuv 线程池 vs GIL；asyncio 单线程事件循环；multiprocessing |
| 6 | pitfall | 未处理拒绝与 process.exit | Node 15+ 退出；exit 丢在途请求与日志 |
| 7 | steps | 五步定位事件循环问题 | lag P99、CPU profile、线程池、微任务饥饿、复测 |
| 8 | text（深挖） | 三块并发与各自天花板 | 事件循环吞吐、4 线程池、微任务无配额、worker/cluster 内存 |
| 9 | table | 主线程/worker/cluster/队列 | 适用场景、成本、通信、隔离 |
| 10 | note | Python GIL 的边界 | CPU-bound 线程不并行；I/O-bound 用 asyncio；CPU-bound 用多进程 |
| 11 | tip | 面试延伸 | 为什么异步 fs 也会排队；如何证明是线程池而不是主线程 |

**概念检查**

- C1 单选：哪一句阻塞进程（readFileSync）。
- C2 多选：事件循环事实（微任务、nextTick 优先级、I/O 回调中的 setImmediate、顶层顺序不确定、unhandledRejection）。
- C3 单选：40 个 30ms 异步读文件约 300ms，lag 5ms，原因是什么（4 线程池排队）。

**代码题：带并发上限的调度器**

- 契约：`runWithLimit(tasks, limit)`，tasks 是返回 Promise 的函数数组；结果顺序与输入一致；任务 reject 时整体 reject；limit 非法时按 1 处理。
- 测试（≥5）：峰值并发 ≤ limit；结果顺序；reject 传播；limit=0；空数组。
- Python：`async def run_with_limit(tasks, limit)`；`asyncio.gather` + worker；`nonlocal cursor`。
- Python 差异：GIL 不影响 asyncio 的 I/O 并发；不要用 `ThreadPoolExecutor` 冒充异步。

**方案题：审查一段服务代码**

- 代码含 `readFileSync`、无 catch 的 `charge()`、无幂等、`process.on('uncaughtException')` 直接 `process.exit(1)`、无超时。
- 自检清单：阻塞、重复解析、未处理拒绝、重复扣款、在途请求被硬切、无超时、无并发限制。
- 参考要点：每项要写「线上现象」而不是只写名词。

**事实清单**：libuv 默认线程池 4（`UV_THREADPOOL_SIZE` 可调）；Node 15+ 未处理拒绝默认退出；Python GIL 使 CPU-bound 线程不能并行；asyncio 是单线程协作式调度。

**边界**：不讲 V8 GC 细节、Python 解释器实现、完整 asyncio 教程；进程/信号在 s0-cli 与 S4。

**概念检查**

- C1 单选：哪个命令能查端口占用与 PID。
- C2 多选：信号与退出码语义。
- C3 单选：`curl` 连接拒绝 vs 超时 vs DNS 失败，下一步分别查什么。

**代码题：解析监听端口**

- 契约：`parseListeners(output)` 解析 `ss -ltnp`/`lsof` 风格文本，返回 `[{ address, port, pid, process }]`。
- 输入示例：

```text
LISTEN 0 511 0.0.0.0:3000 0.0.0.0:* users:(("node",pid=1234,fd=23))
LISTEN 0 511 [::]:3000 [::]:* users:(("node",pid=1234,fd=24))
LISTEN 0 511 127.0.0.1:5432 0.0.0.0:* users:(("postgres",pid=99,fd=7))
```

- 测试（≥5）：IPv4；IPv6；同一进程多行；无 `users` 字段（权限不足）；畸形行跳过；端口按数字排序。
- Python 差异：返回 list[dict]；正则命名组；`int(port)`；排序稳定。
- 常见错误：把 `0.0.0.0:*` 当端口；IPv6 地址里的冒号切错；权限不足时丢整行。

**方案题：故障排查 runbook**

- 场景：本地 `npm run dev` 报 `EADDRINUSE`；部署后 `curl` 超时；域名解析到旧 IP。
- 自检清单：先确认现象（拒绝/超时/DNS/5xx）；再确认进程与端口；再确认配置与环境变量；再确认 DNS；最后才改代码；每步有验证命令；不直接 `kill -9`；记录时间线。
- 参考要点：症状 → 层 → 命令 → 判据 → 下一步；不要把所有问题都归因于「服务挂了」。

**事实清单**：`ss` 在 Linux、`lsof` 在 macOS 更常见；信号语义 POSIX；退出码 0/非 0 约定；不同 shell 的 `$?` 行为一致。

**边界**：不讲内核网络参数、eBPF、systemd 深入（a8）；不讲容器（S4）。

**代码题：解析 EXPLAIN**

- 契约：`summarizeExplain(plan)` 接收简化计划树 `{ node, rows, actualRows, actualTime, children }`，返回 `{ seqScans, indexScans, maxRowMisestimate, totalActualTime, warnings }`。
- 规则：递归遍历；`Seq Scan` 计数；行数估计偏差 = `max(actualRows/rows, rows/actualRows)`；偏差 > 10 产生 warning；时间单位毫秒。
- 测试（≥5）：纯索引计划；Seq Scan；嵌套循环；行数偏差；空计划。
- Python 差异：递归 dict 遍历；`max()` 默认值；浮点比较。

**SQL 题**

- 目标：用 `(user_id, created_at)` 索引写列表查询；结果按创建时间倒序；分页边界。
- 测试：结果集精确；空结果；相同时间戳的稳定排序。

**方案题：LinkHub 索引方案**

- 输入：5 条高频查询 + 写入量 + 数据增长预估。
- 自检清单：每条查询对应索引；最左前缀；覆盖索引；写入放大；冗余索引；迁移与并发创建；验证方式（EXPLAIN 证据）。
- 参考要点：索引服务查询而不是服务列；不要为每个列建索引；用真实数据量测试。

**事实清单**：PostgreSQL B-tree 默认索引；`EXPLAIN ANALYZE` 实际执行；`BUFFERS` 需开启；index-only scan 依赖可见性地图；具体页大小/扇出写「取决于实现」。

**边界**：B+tree/LSM 内部结构在 a3；不在本讲讲存储引擎实现。

### s1-l3 事务、隔离级别与 MVCC（80 min）

**Objectives**

1. 用例子解释 ACID 与四类并发异常。

**内容块大纲**

| # | type | 标题 | 要点 |

| 1 | analogy | 共享文档的同时编辑 | 快照、锁、冲突；读到的到底是哪个版本 |

| 4 | flow | MVCC 快照读与当前读 | 版本链、事务 ID、可见性；写锁与等待 |
| 5 | code | 创建短链 + 审计同事务 | BEGIN/COMMIT/ROLLBACK；失败重试 |

| 11 | note | 面试延伸 | 什么时候该用 SERIALIZABLE；死锁怎么排查 |

**概念检查**

- C1 单选：给定场景判断异常类型。
- C2 多选：MVCC/隔离级别事实。
- C3 单选：接口 P99 飙升、连接池等待高、事务里有外部调用，先查什么。

**代码题：乐观并发更新与重试**

- 契约：`updateWithRetry(store, id, mutate, { maxRetries })`；store 提供 `get(id)`、`compareAndSet(id, expectedVersion, next)`；冲突时重试；超过次数抛 `ConflictError`。
- 测试（≥5）：一次成功；冲突后重试成功；耗尽重试；并发两个更新不丢；mutate 抛错不写入。
- Python：`async def update_with_retry`；`asyncio.sleep` 退避；自定义异常。
- 常见错误：读取后直接写、版本号不递增、重试没有上限、把业务错误当冲突重试。

**方案题：LinkHub 事务边界**

- 场景：创建短链 + 写审计；点击跳转 + 写点击事件；更新链接 + 失效缓存。
- 自检清单：哪些操作必须同事务；哪些可以异步；隔离级别；失败重试；幂等；缓存一致性；锁顺序；长事务风险。
- 参考要点：创建 + 审计同事务；点击事件在 S3 异步；缓存失效在事务提交后；不要在事务里调用外部服务。

**事实清单**：PostgreSQL 默认 READ COMMITTED；MySQL InnoDB 默认 REPEATABLE READ；MVCC 实现因数据库而异；连接池上限不等于数据库最大连接数。

**边界**：分布式一致性在 S5；缓存失效在 S3；不在本讲讲数据库内部实现。
