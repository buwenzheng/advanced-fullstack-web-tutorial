# M4：S4-S5 内容模块（8 讲 + p4 + p5）

> 依赖：G2。产出：生产化与分布式两条主线，p4 生产化、p5 统计服务。通过 G3 后进入 M5。

## 1. 模块目标

- S4 让系统「查得到、说得清、发得出去、回得来」：日志/指标/追踪、压测/瓶颈、容器/进程、CI/CD/回滚。
- S5 让学员能判断「该不该拆」：模块边界、Outbox/最终一致、分布式失败、复制/分片。
- p4 在 p3 的服务上加运营能力；p5 把 p3 的应用内 BullMQ 升级为 Outbox + RabbitMQ 独立统计服务，不重做 p3。
- 明确 `s4-perf` 与 `a7`、`s5-data-scale` 与 `a3`、`s5-l1` 与 `a10`、`s4-l3` 与 `a8`、`s4-l4` 与 `a11` 的边界。

## 3. S4 课时 brief

### s4-l1 日志、指标与追踪（80 min）

**Objectives**

1. 用结构化日志与 requestId 还原一次请求。
2. 用 RED/USE 指标体系回答「系统现在怎么样」。
3. 用 OpenTelemetry 的 span 串起服务、数据库与队列。
4. 设计低噪声、可执行的告警。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | console.log 与生产可观测性 | 前端错误监控 vs 后端三支柱 |
| 2 | text | 日志/指标/追踪 | 各自回答什么问题；成本与采样 |
| 3 | code | 结构化日志 + requestId | JSON 日志；上下文传播；脱敏 |
| 4 | table | RED/USE | Rate/Errors/Duration；Utilization/Saturation/Errors |
| 5 | code | 指标注册表 | counter/gauge/histogram；P50/P95/P99 |
| 6 | flow | 请求 → span → 日志 → 指标 | traceId/spanId 关联 |
| 7 | pitfall | 高基数标签、PII、平均延迟、告警疲劳 | 现象与修复 |
| 8 | steps | 为跳转接口设计告警 | 症状指标、阈值、持续时间、runbook |
| 9 | text（深挖） | 采样与关联 | head/tail sampling；trace 与日志的取舍 |
| 10 | note | 面试延伸 | 线上 P99 升高，先看哪三个信号 |

**概念检查**

- C1 单选：判断 P99 升高应看哪类信号。
- C2 多选：高基数标签、PII、采样、平均值的陷阱。
- C3 单选：告警应该基于症状还是每个内部指标。

**代码题：指标注册表与分位数**

- 契约：`createMetrics()` 提供 `counter(name, labels)`、`gauge(name, value)`、`histogram(name, value)`、`snapshot()`；直方图返回 `count/sum/p50/p95/p99`；标签排序稳定；禁止修改已注册类型。
- 测试（≥6）：计数；标签区分；直方图分位数；空直方图；类型冲突；快照不可变。
- Python：类 + dict；`statistics.quantiles` 或手写排序；浮点边界。
- 常见错误：用平均值代替分位数；标签里放 userId/URL 导致高基数；直方图桶设计不合理。

**方案题：LinkHub 可观测性方案**

- 自检清单：日志字段；requestId 贯穿；RED 指标；关键 span；采样；告警；看板；PII 脱敏；保留期。
- 参考要点：跳转接口看 rate/errors/duration + 缓存命中；统计链路看队列深度/消费延迟；告警必须有 runbook，否则只是噪声。

**事实清单**：OpenTelemetry 语义约定会演进；RED/USE 是方法论不是标准；不同平台分位数算法不同。

**边界**：RUM 与前后端 trace 串联在 s6-l4；本讲只讲后端可观测性。

### s4-perf 性能压测与瓶颈定位（75 min）

**Objectives**

1. 设计可复现的压测基线：负载模型、并发、时长、环境。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 前端 Lighthouse vs 后端压测 | 实验室数据 vs 生产数据 |
| 2 | text | 四个核心指标 | 吞吐、延迟分位、错误率、饱和度 |
| 3 | flow | 基线 → 加压 → 观察 → profile → 假设 → 修复 → 复测 | 每步留档 |
| 4 | code | 压测结果汇总 | P50/P95/P99、吞吐、错误率、Little 定律 |
| 5 | table | k6/autocannon/ab | 开环/闭环；适用场景；不写产品教程 |
| 6 | steps | 跑一次基线压测 | 并发、时长、数据量、缓存状态 |
| 7 | pitfall | 平均值、协调遗漏、冷缓存、忽略错误率 | 数据看似好看但结论错误 |
| 8 | text（深挖） | 排队与尾延迟 | 利用率、队列、P99 放大；瓶颈分类 |
| 9 | table | 瓶颈指纹 | CPU 饱和、GC、IO 等待、锁竞争、连接池、下游慢 |
| 10 | note | 面试延伸 | 压测结果 P99 高但 CPU 不高，怎么查 |

**概念检查**

- C1 单选：P99 的含义与误读。
- C2 多选：一次有效压测必须固定哪些条件。
- C3 单选：给定 CPU/延迟/队列指标，判断瓶颈类别。

**代码题：压测结果汇总**

- 契约：`summarizeLoadTest(samples, { durationSec })`，samples 为 `{ latencyMs, ok }`；返回 `{ count, throughput, errorRate, p50, p95, p99, avgConcurrency }`；分位数用最近秩；Little 定律 `L = λ × W`。
- 测试（≥6）：空样本；全成功；含错误；分位数边界；吞吐计算；并发估算。
- Python：排序 + 索引；浮点；返回 dict。
- 常见错误：用平均延迟算 Little 定律；分位数索引差一；把错误请求算进延迟；吞吐单位错。

**方案题：LinkHub 容量估算**

- 自检清单：峰值 QPS；读写比；缓存命中；单实例容量；冗余；增长；成本；压测验证；瓶颈假设。
- 参考要点：先有基线再谈容量；区分平均与峰值；给 2-3 倍冗余；用压测验证而不是拍脑袋；容量估算的假设要写出来。

**事实清单**：Little 定律适用条件；分位数算法差异；k6/autocannon 的模型不同；压测数字依赖环境，不写死。

**边界**：排队论与容量建模的深水区在 a7；本讲讲「怎么测、怎么定位」。

| # | type | 标题 | 要点 |

| 1 | analogy | 关闭浏览器标签 vs 服务 SIGTERM | 先停止接新活，再清理在途 |

| 3 | code | 优雅退出协调器 | 停止接收 → 排空 → 超时 → 强制 |
| 4 | flow | 构建 → 镜像 → 容器 → 探针 → 重启 | 每一步的失败现象 |

| 6 | table | 配置来源与优先级 | 环境变量、文件、命令行；密钥管理 |

**概念检查**

- C1 单选：SIGTERM 与 SIGKILL 的区别。
- C2 多选：Dockerfile 最佳实践。
- C3 单选：配置优先级与密钥管理。

**代码题：优雅退出协调器**

- 契约：`createShutdown({ server, timeoutMs, onDrain, scheduler })`；`scheduler` 注入 `{ setTimeout, clearTimeout }`（默认用全局定时器），测试用假定时器手动推进；`shutdown()` 返回 Promise；状态 `running → draining → closed`；重复调用幂等并返回同一结果；`server.close` 后进入 draining，`onDrain` 完成则 closed，超过 `timeoutMs` 强制关闭并返回 `{ forced:true, reason:'TIMEOUT' }`。
- 测试（≥6）：正常排空；重复调用返回同一 Promise；用假定时器推进到超时强制关闭；`onDrain` 抛错进入 closed 且标记失败；新请求在 draining 阶段被拒绝；状态不可逆。
- Python：`asyncio` + signal；状态机；超时用 `asyncio.wait_for`；测试用可控 `Event` 而不是真实 `sleep`。
- 常见错误：先关闭数据库再排空 HTTP；没有超时；重复注册信号处理器；`process.exit` 直接退出。

**方案题：部署配置审查**

- 自检清单：多阶段构建；非 root；只读文件系统；健康检查；资源限制；配置优先级；密钥；日志输出；退出码；回滚。
- 参考要点：镜像不可变；配置外置；密钥不落盘；探针区分 liveness/readiness；关闭顺序：停止接新请求 → 排空 → 关闭依赖。

**事实清单**：POSIX 信号；Docker 多阶段构建；Kubernetes 探针语义（概念）；不同运行时 PID 1 行为不同。

**边界**：Linux IO/反向代理在 a8；本讲只讲进程/容器/配置。

**Objectives**

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 前端 preview deploy vs 后端灰度 | 爆炸半径与回滚速度 |
| 2 | text | 流水线关卡 | lint/type/unit/integration/contract/security |
| 3 | table | 测试分层 | 单元/集成/契约/E2E；运行时间与稳定性 |
| 4 | flow | build → test → deploy → verify → promote/rollback | 每步的失败处理 |
| 5 | code | 特性开关 | 百分比、租户白名单、kill switch、确定性哈希 |
| 6 | compare | 蓝绿/金丝雀/滚动 | 成本、风险、回滚速度 |
| 7 | pitfall | 没有回滚 | 迁移不兼容；开关债务；手工步骤；只测 happy path |
| 8 | steps | 发布计划 | 指标、观察窗口、回滚阈值、负责人 |
| 9 | text（深挖） | expand-contract 与 dark launch | 向后兼容 schema；双写；读切换 |
| 10 | note | 面试延伸 | 一次高风险发布怎么做；回滚失败怎么办 |

**概念检查**

- C1 单选：高风险变更选哪种发布策略。
- C2 多选：流水线必须有哪些关卡。
- C3 单选：什么指标触发自动回滚。

**代码题：特性开关判定**

- 契约：`evaluateFlag(flag, context)`；`context = { userId? }`；flag 支持 `enabled`、`percentage`、`allowlist`、`denylist`、`killSwitch`；返回 `{ enabled: boolean, reason: string }`。
- 判定优先级固定：`flag == null` → `UNKNOWN_FLAG` 关；`killSwitch` → `KILL_SWITCH` 关；命中 `denylist` → `DENY_LIST` 关；命中 `allowlist` → `ALLOW_LIST` 开；`enabled === false` → `DISABLED` 关；`percentage === 100` → `FULL_ROLLOUT` 开；`percentage` 为 0/缺省 → `NOT_IN_ROLLOUT` 关；无 `userId` → `NO_IDENTITY` 关；否则算桶，命中 → `IN_ROLLOUT`，未命中 → `OUT_OF_ROLLOUT`。
- 哈希统一为 FNV-1a 32-bit（对 UTF-8 字节）：`h = 2166136261; 每个字节 b：h ^= b; h = (h * 16777619) mod 2^32`；JS 用 `Math.imul`，Python 用 `& 0xFFFFFFFF`；桶 = `hash(flagKey + ':' + userId) % 100`，`桶 < percentage` 即命中。两端必须使用同一算法与同一拼接格式。
- 测试（≥7）：全开/全关；白名单；黑名单；百分比对同一 `userId` 稳定且落在 `[0,100)`；kill switch 覆盖其他规则；匿名用户百分比关；未知 flag 默认关；reason 与优先级匹配。
- Python：`hashlib` 不用于此约定（会与 JS 不一致）；按上式手写 FNV-1a；返回 dict。
- 常见错误：用 `Math.random()` 导致同一用户每次不同；kill switch 优先级错；百分比按请求而不是用户。

**方案题：LinkHub 发布与回滚预案**

- 自检清单：发布策略；灰度比例；观察指标；回滚阈值；数据库兼容；开关；负责人；沟通；演练。
- 参考要点：先 expand 后 contract；灰度看错误率/P99/业务指标；回滚要能在分钟级完成；开关不是永久方案。

**事实清单**：蓝绿/金丝雀/滚动是通用模式；CI 产品能力不同；特性开关实现各异。

**边界**：测试策略与工程效能在 a11；本讲只讲流水线与发布。

| 7 | pitfall | 事务内发消息 | 先标记后 ack；重复消费；读不到自己的写 |
| 8 | steps | 从 p3 BullMQ 升级到 Outbox + RabbitMQ | 保留 p3 业务路径，替换发布方式 |
| 9 | text（深挖） | exactly-once 是端到端效果 | at-least-once + 幂等；读模型延迟 |
| 10 | note | 面试延伸 | 为什么不用 2PC；如何保证消息不丢 |

**概念检查**

- C1 单选：业务提交成功但消息发送失败，会发生什么。
- C2 多选：Outbox 的关键步骤。
- C3 单选：统计看板应标注什么一致性级别。

**代码题：Outbox 发布器 + 幂等消费**

- 契约：`createOutbox({ store, publisher, now })`；`add(event)` 与业务写入同事务（用 store 模拟）；`publishBatch(limit)` 用 `SKIP LOCKED` 语义抢占；发布成功标记 `sentAt`；失败累加 attempts；消费者 `consume(event, processed)` 用 eventId 去重。
- 测试（≥8）：同事务写入；抢占互斥；发布成功标记；发布失败重试；发布后崩溃重复投递只消费一次；attempts 上限；空批次。
- Python：`asyncio` 或同步；dict 模拟；唯一约束用 set。
- 常见错误：先标记 sent 再发布；消费者先写业务再记 eventId；没有唯一索引兜底；publisher 和业务不在同一事务。

**方案题：LinkHub 统计一致性**

- 自检清单：事件产生；outbox；发布器；MQ；消费者；读模型；一致性级别；延迟上界；重放；监控；降级。
- 参考要点：跳转主链路只写事件，统计异步；看板标注「最终一致，延迟 ≤ N 秒」；重复投递只累加一次；关掉统计不影响跳转。

**事实清单**：Outbox 模式；`FOR UPDATE SKIP LOCKED` 是 PostgreSQL 特性；RabbitMQ 投递语义；exactly-once 需要端到端幂等。

**边界**：分布式锁与部分失败在 s5-l3；本讲讲一致性方案与 Outbox。

| # | type | 标题 | 要点 |

| 1 | analogy | 网络不是函数调用 | 前端离线/重试；后端未知结果 |

| 9 | text（深挖） | CAP/PACELC 的直觉 | 不背定理，讲取舍 |
| 10 | note | 面试延伸 | 超时后到底成功没有；分布式锁真的安全吗 |

**概念检查**

- C1 单选：调用超时后应该假设什么。
- C2 多选：fencing token 能防什么、不能防什么。
- C3 单选：重试风暴的根因与修复。

**代码题：Fencing Token 锁**

- 契约：`createFencedLock({ store, now })`；`acquire(key, ttlMs)` 返回 `{ token, expiresAt }`；`renew(key, token)`；`write(key, token, value)` 只有 token 等于当前锁 token 才允许；过期后可被新锁获取，旧 token 写入被拒。
- 测试（≥7）：获取；续租；过期后被新锁获取；旧 token 写入拒绝；新 token 写入成功；续租过期锁失败；并发获取只有一个成功。
- Python：dict + 时间注入；token 单调递增；异常/返回错误码。
- 常见错误：只比较 key 不比较 token；租约到期不检查；续租不校验持有者；用本地时间做全局排序。

**方案题：LinkHub 分布式失败预案**

- 自检清单：依赖图；超时预算；可重试错误；幂等；锁/fencing；降级；演练；监控；恢复时间。
- 参考要点：统计服务失败不影响跳转；发布器失败可重试；消费者重复只计一次；锁失效用版本号兜底。

**事实清单**：租约与 fencing token；时钟偏移；CAP 是取舍不是三选二；不同 MQ 的顺序保证不同。

**边界**：CRDT/共识算法不在本讲；本讲讲工程陷阱与防线。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 前端缓存与副本 | 读到的可能是旧值 |
| 2 | text | 主从复制 | 同步/异步；延迟；故障切换 |
| 3 | flow | 写主 → 复制 → 读从 | 延迟窗口与用户可见性 |

| 5 | table | 分片键候选 | 用户/租户/链接 ID；热点与跨分片 |

**概念检查**

- C1 单选：用户写完立刻读，读从库可能看不到，怎么解决。
- C2 多选：好的分片键应满足什么。
- C3 单选：分布式 ID 的取舍。

**代码题：一致性哈希环**

- 契约：`createHashRing(nodes, { virtualNodes = 100, hash = defaultHash })`；`getNode(key)`；`addNode(node)`；`removeNode(node)`；返回稳定映射；节点增删后尽量少迁移。`defaultHash` 固定为 FNV-1a 32-bit（与 s4-l4 同一实现），环上位置 = `hash(node + '#' + replicaIndex) % 2^32`，查找用有序数组 + 二分。
- 测试（≥6）：同一 key 多次调用结果一致；用固定 1000 个 key 与 5 个节点断言每个节点分到 10%–30%（确定性夹具，不用随机）；增加节点后仍映射到旧节点的 key 保持不变；删除节点后其 key 迁移到后继；空环抛 `EMPTY_RING`；虚拟节点数从 1 增到 100 时最大份额下降。
- Python：同一 FNV-1a；排序环；`bisect`；返回 dict。
- 常见错误：用 `Math.random`；节点增删重建整个映射；虚拟节点太少导致倾斜；哈希函数不一致。

**方案题：LinkHub 分片方案**

- 自检清单：分片键；热点；跨分片查询；分布式 ID；重分片；读写分离；一致性；运维成本；不分的理由。
- 参考要点：按 tenant/user 分片可避免单链接热点；短链跳转按 code 哈希；统计按 link_id 分片；跨分片聚合放读模型；分片前先优化索引与缓存。

**事实清单**：复制延迟、一致性哈希、Snowflake 类 ID 的结构；不同数据库分片能力不同；不写具体产品限制。

**边界**：B+tree/LSM 内部在 a3；本讲讲数据扩展的取舍与方案。

## 6. 项目 p5：LinkHub 统计服务

**brief**：p3 的 BullMQ 只把慢活挪出请求链路；入队与业务提交仍是两次写，消费者随 API 部署。这一阶段用 Outbox 消除双写窗口，换 RabbitMQ 让发布器与消费者独立部署，形成统计服务。

**steps**

1. 主库加 `click_events` 明细与 `outbox`；点击事件与明细同事务。
2. 独立发布器：`FOR UPDATE SKIP LOCKED` 抢占，投递 RabbitMQ，成功后标记，失败累加 attempts。
3. 独立消费者：按 eventId 幂等，唯一索引兜底，指数退避，死信表与重放工具。
4. 读模型：按天、按链接聚合；查询接口标注一致性级别与延迟上界。
5. 故障演练：消费者 `kill -9`、MQ 不可用、重复投递；记录现象与恢复时间。
6. 验收：主链路延迟不因统计增加；重复投递只累加一次；关掉统计不影响跳转。

**milestones**

| ID | 标题 | 验收 |
| --- | --- | --- |
| p5-m1 | Outbox | 业务与事件同事务；崩溃不丢事件；publisher 可重试 |
| p5-m2 | 独立发布器 | SKIP LOCKED 抢占；失败 attempts；可观测 |
| p5-m3 | 独立消费者 | eventId 幂等；唯一索引兜底；DLQ 可重放 |
| p5-m4 | 读模型 | 按天/链接聚合；查询标注一致性级别与延迟上界 |
| p5-m5 | 故障演练 | 三类故障；恢复时间；跳转不受影响 |

**deliverables**：outbox 迁移、publisher、consumer、读模型、重放工具、演练记录、README。

**checklist**：不重写 p3 的 API；事件与明细同事务；消费者可独立部署；重复只计一次；统计故障不拖垮跳转。

**与 p3 的因果**：p3 的 BullMQ 队列与消费者是「应用内异步」；p5 只替换事件发布与消费的部署方式，业务路径不变。
