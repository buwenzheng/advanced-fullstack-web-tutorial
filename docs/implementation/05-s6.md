# M5：S6 全栈集成内容模块（4 讲 + p6）

> 依赖：G3。产出：把 p2-p5 的后端能力组装成可交付产品；跨层练习通过验证。通过 G4 后进入 M6。

## 1. 模块目标

- S6 回答一个问题：后端已经能跑，为什么用户还是「看不到、等太久、断线就废、出事定位不到」。
- 四讲分别补齐产品层的四块：契约与 BFF、渲染与性能、实时与安全、边缘与可观测性。
- 项目 p6 只做组装与产品层，不重写 p2-p5；统计复用 p5，缓存只讲边缘层，鉴权只讲浏览器会话边界。
- 课程评估要求 S6 至少一道跨层练习。本模块安排三道，分别覆盖「契约 → UI」「传输 → UI 状态」「浏览器 → 服务端 trace」，避免单层代码蒙混过关。

## 3. S6 课时 brief

### s6-l1 契约驱动的全栈开发与 BFF（85 min）

**Objectives**

1. 从 OpenAPI 生成类型安全客户端，并解释生成物为什么不能手改。
2. 设计契约漂移检查，把破坏性变更挡在合并之前。
3. 判断何时需要 BFF、何时直连，并说清 BFF 的收益与代价。
4. 用并发聚合、超时与部分失败降级消除前端请求瀑布。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 手抄菜单与自动生成 | 前端手写接口类型 = 菜单改了靠人传话；契约生成 = 同一份菜单 |
| 2 | text | 契约是唯一事实源 | OpenAPI/JSON Schema；生成客户端；生成物只读；版本与兼容 |
| 3 | code | 从 OpenAPI 片段生成类型 | paths/schema → 请求/响应类型；可选字段；枚举 |
| 4 | flow | 契约 → 生成 → 编译 → 漂移检查 → 发布 | 每一步失败会发生什么 |
| 5 | table | BFF vs 直连 vs 网关聚合 | 控制力、延迟、缓存、团队边界、故障面 |
| 6 | code | BFF 并发聚合 | `Promise.allSettled`；超时；部分失败；错误码映射 |
| 7 | case | 详情页 1.8s：四个串行请求 | 症状/根因/修复/预防/指标 |
| 8 | pitfall | BFF 的五个坑 | 请求瀑布、N+1、把 BFF 做成第二个后端、错误直通 UI、鉴权上下文丢失 |
| 9 | compare | 聚合层放前端 / BFF / 网关 | 各自适合的团队与流量形态 |
| 10 | text（深挖） | 契约兼容性判定 | 新增可选字段、枚举扩展、删除字段、类型收窄、默认值变化 |
| 11 | steps | 设计 LinkHub 详情页 BFF | 输入输出、上游、超时、降级、鉴权、缓存 |
| 12 | note | 面试延伸 | 契约漂移如何进 CI；BFF 挂了前端怎么活 |

**概念检查**

- C1 单选：以下哪种变更属于破坏性契约变更（删除字段 / 可选改必填 / 枚举收窄）。
- C2 多选：BFF 的适用场景与必须接受的代价（多一跳、部署耦合、缓存复杂、团队边界）。
- C3 单选：详情页四个串行请求，正确优化是什么（并发聚合 + 超时降级，而不是把四个请求原样转发）。

**代码题：类型客户端 + BFF 聚合（跨层：契约 → UI 数据）**

- 契约：
  - `buildClient(schema)`：输入简化 OpenAPI（paths + components），返回 `client.get(path, params)`；路径参数替换、查询串稳定排序、响应类型由 schema 决定；未知路径抛 `UNKNOWN_ROUTE`。
  - `createDetailLoader({ fetchMeta, fetchStats, fetchPermission, timeoutMs, scheduler = { setTimeout, clearTimeout } })`：返回 `loadDetail(id)`，并发调用三个上游；meta 失败则整体失败并映射为 `{ code: 'NOT_FOUND' | 'UPSTREAM' }`（错误 `code === 'NOT_FOUND'` 映射 NOT_FOUND，其余含超时映射 UPSTREAM）；stats/permission 失败则降级为 `null`/`false`，并在 `degraded` 数组标记；成功时返回稳定 UI 形状 `{ link, stats, canEdit, degraded }`。
  - 超时语义：`timeoutMs` 是整次聚合的总预算；超时后已完成的字段保留，仍 pending 的 stats/permission 记入 `degraded`，meta 未完成则整体返回 `{ code: 'UPSTREAM' }`；超时后到达的结果必须被忽略，不得二次 resolve。
  - 测试时钟：测试注入假 `scheduler`，手动推进到 `timeoutMs`；禁止依赖真实 `sleep`。
- 测试（≥7）：
  1. 路径参数与查询串编码正确；
  2. 未知路径抛错；
  3. 三个上游并发启动（用受控 Promise 证明两个未决时第三个已启动）；
  4. 全成功时 `degraded` 为空；
  5. stats 失败只降级 stats；
  6. permission 失败只降级 permission；
  7. meta 失败映射错误码，不透传上游原始错误。
- Python：`asyncio.gather(..., return_exceptions=True)`；路径拼接用 `urllib.parse.quote`；返回 dict；测试用 `asyncio` 事件循环。
- 常见错误：顺序 `await`；`Promise.all` 遇错全崩；把上游 500 原样返回 UI；降级不标记；查询参数顺序不稳定导致缓存键漂移。
- 跨层证据：输入是 HTTP 契约，输出是 UI 直接消费的数据形状；测试同时断言「一次聚合」与「形状稳定」。

**方案题：LinkHub 详情页 BFF 契约**

- 自检清单：输入/输出 schema；聚合哪些上游；并发与超时预算；部分失败策略；鉴权透传；错误码映射；缓存边界；与前端类型的同步方式；可观测字段。
- 参考要点：BFF 只做聚合与适配，不承载业务规则；总超时必须小于各上游超时之和；降级必须显式标记；契约变更走生成与漂移检查，不手改客户端。

**事实清单**：OpenAPI 3.1 与 JSON Schema 对齐；不同生成器对 `nullable`/`additionalProperties` 处理不同；HTTP 缓存与 BFF 个性化响应的冲突。

**边界**：不重讲 HTTP 基础（S0）与 API 契约设计（S2）；不讲具体框架（Next/Nest）与 GraphQL 实现；认证细节留给 s6-l3。

### s6-l2 渲染架构与端到端性能（85 min）

**Objectives**

1. 区分 CSR/SSR/SSG/流式渲染的收益与成本，并按页面特征选择。
2. 解释水合成本与可交互时间，避免「首屏很快、点了没反应」。
3. 用 LCP/INP/CLS 与性能预算管理体验，而不是只看加载完成。
4. 区分实验室数据与 RUM，知道各自的盲区。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 外卖到店 vs 到桌 | CSR 像空盒加客户端组装；SSR 像到店即食 |
| 2 | text | 四种渲染模式 | CSR/SSR/SSG/流式；数据新鲜度、成本、缓存、适用页面 |
| 3 | flow | 请求 → HTML → 资源 → 水合 → 可交互 | 每一段的失败现象 |
| 4 | code | 渲染策略决策器 | 页面特征 → 策略；规则可解释、可测试 |
| 5 | table | Core Web Vitals | 测什么、差在哪、常见修复、实验室 vs 现场 |
| 6 | code | 性能预算检查 | p75 分位；预算违规；违规排序 |
| 7 | case | 首屏 1.2s，INP 600ms | SSR 成功但水合长任务；修复与指标 |
| 8 | pitfall | 渲染的五个坑 | 水合不一致、流式被同步阻塞、图片无尺寸、长任务、缓存个性化 HTML |
| 9 | compare | SSR / SSG / ISR / 流式 | 数据新鲜度、部署成本、缓存复杂度 |
| 10 | steps | 为 LinkHub 看板选渲染策略 | 页面分类、数据依赖、预算、降级 |
| 11 | text（深挖） | 关键路径与资源提示 | preload/preconnect/fetchpriority；字体与图片 |
| 12 | note | 面试延伸 | LCP 好但 INP 差说明什么 |

**概念检查**

- C1 单选：登录后个性化看板该选什么策略（SSR/流式 + 客户端补充，而不是全站 SSG）。
- C2 多选：水合成本的来源（组件树规模、序列化数据、客户端重复计算、第三方脚本）。
- C3 单选：LCP 2.1s、INP 480ms，先修哪个、为什么（INP 已严重超标，优先拆长任务）。

**代码题：渲染策略决策 + 性能预算**

- 契约：
  - `chooseRenderStrategy(page)`：输入 `{ requiresAuth, personalization, freshnessSec, seo, interactivity }`；`personalization ∈ {'none','low','high'}`（缺省 `'none'`），`freshnessSec` 为可容忍的内容陈旧秒数（缺省 `Infinity`），其余为 boolean。按固定优先级返回：
    1. `personalization === 'high'` → `stream`；
    2. `seo === true && freshnessSec <= 60` → `ssr`；
    3. `seo === true` → `ssg`；
    4. `requiresAuth === true` → `csr`；
    5. 默认 → `csr`。
  - `checkBudget(samples, budget)`：`samples = { lcp?: number[], inp?: number[], cls?: number[] }`；p75 用最近秩：升序排序后取 `index = ceil(0.75 * n) - 1`（`n === 0` 不取）。返回 `{ pass, violations: [{ metric, p75, budget, ratio, reason? }] }`；`p75 <= budget` 通过；空/缺失样本记 `p75: null, reason: 'NO_DATA'` 并判失败；`ratio = (p75 - budget) / budget`，按 ratio 降序，ratio 相同按 `lcp → inp → cls` 固定顺序。
- 测试（≥7）：营销页 `ssg`；个性化看板 `stream`；登录后工具页 `csr`；新鲜内容 `ssr`；p75 边界等于预算时通过；空样本按 `NO_DATA` 失败；多项违规按 ratio 排序且同 ratio 顺序稳定。
- Python：纯函数 + `statistics` 或手写最近秩；浮点比较；返回 dict。
- 常见错误：把「个性化」误判为不能 SSR；p75 用平均值；预算单位不统一；策略规则顺序冲突。
- 跨层证据：从页面产品特征推导渲染与交付预算，测试覆盖「策略 → 指标门槛」的完整决策。

**方案题：LinkHub 渲染与 CWV 预算**

- 自检清单：页面分类；每类策略与理由；数据获取位置；水合边界；LCP/INP/CLS 预算；资源提示；图片/字体；实验室与 RUM 双数据源；降级。
- 参考要点：预算必须写进 CI；策略按页面而不是全站；流式要定义 shell、错误边界与超时；个性化页面缓存键必须包含用户/租户维度。

**事实清单**：CWV「good」阈值为 p75 下 LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1；阈值会演进；不同框架的水合实现不同。

**边界**：不讲框架语法与组件库；不讲 RUM 采集实现（s6-l4）；不讲 CDN 配置（s6-l4）。

### s6-l3 实时、认证与全栈安全（80 min）

**Objectives**

1. 在 SSE/WebSocket/长轮询之间按方向、基础设施与成本做选择。
2. 设计重连、退避、去重、断点续传与降级轮询。
3. 用 HttpOnly/SameSite/CSRF/CSP 组合建立浏览器会话的安全边界。
4. 识别 XSS/CORS/越权/租户隔离在全栈中的责任分界。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 刷新页面 / 订阅 / 打电话 | 长轮询、SSE、WebSocket 的直觉 |
| 2 | table | 三种实时传输 | 方向、协议、代理兼容、重连成本、适用场景 |
| 3 | code | 重连计划 | 指数退避、上限、jitter、重试耗尽 |
| 4 | flow | 建连 → 鉴权 → 订阅 → 事件 → 断线 → 重连 → 补拉 | 每一步的失败与恢复 |
| 5 | text | 会话 vs Token | 存储位置、过期、刷新、撤销；为什么登录态不放 localStorage |
| 6 | table | 安全头分工 | CSP/HSTS/X-Frame-Options/Referrer-Policy 各防什么 |
| 7 | code | 实时事件归并 | 去重、乱序、缺口标记、UI 状态不重复累加 |
| 8 | case | 重连风暴打挂网关 | 无 jitter、无上限、全员同时重连；修复与指标 |
| 9 | pitfall | 实时与安全的五个坑 | localStorage token、CORS 通配 + credentials、SSE 不鉴权、重复事件、重连风暴 |
| 10 | steps | 实时看板链路设计 | 订阅粒度、扇出、背压、补拉、降级轮询 |
| 11 | compare | OIDC 授权码 + PKCE vs 自建密码登录 | 责任边界、实现成本、适用规模 |
| 12 | note | 面试延伸 | HttpOnly Cookie 为什么仍需要 CSRF 防护 |

**概念检查**

- C1 单选：单向点击通知优先选 SSE 的理由（HTTP 兼容、自动重连、单向足够）。
- C2 多选：重连必须处理的四件事（退避、jitter、去重、补拉/降级）。
- C3 单选：CSP 禁止 inline script 后仍可能被 XSS 的路径（DOM XSS、被允许的第三方脚本）。

**代码题：重连计划 + 实时事件归并（跨层：传输 → UI 状态）**

- 契约：
  - `planReconnect(attempt, { baseMs = 100, maxMs = 1600, jitter = 0.2, random = Math.random })`：返回 `{ delayMs, exhausted }`；指数增长封顶；jitter 由注入的 `random` 决定，测试可复现；attempt 从 0 开始。
  - `applyLiveEvent(state, event)`：`state = { total, perLink, seenIds, lastEventId }`；事件 `{ id, linkId, delta, seq }`；重复 id 忽略；乱序按 id 去重后仍只累加一次；发现 `seq` 缺口时在返回状态标记 `gap: true`；不修改入参。
- 测试（≥8）：退避序列；封顶；jitter 边界（random=0/1）；耗尽标记；重复事件只加一次；两个链接独立累加；乱序事件不重复；缺口标记；入参不可变。
- Python：`min(base * 2 ** attempt, max)`；`random.random()` 注入；dict 拷贝；测试用固定 random。
- 常见错误：无 jitter 导致同步重连；退避无上限；按事件内容而不是 id 去重；直接修改传入 state；缺口当重复丢弃。
- 跨层证据：从传输层事件序列推导 UI 聚合状态；测试覆盖重复、乱序、缺口三种真实网络行为。

**方案题：LinkHub 实时与安全设计**

- 自检清单：传输选择；鉴权方式；订阅粒度；扇出与背压；重连/补拉；去重；降级轮询；会话存储；CSRF；CSP；CORS；租户隔离；审计日志。
- 参考要点：实时链路必须能降级；会话 Cookie 必须 HttpOnly + SameSite + CSRF  token；CORS 不允许 `*` 与 credentials 组合；事件去重放在 UI 状态层而不是只靠服务端。

**事实清单**：SSE 基于 HTTP 长连接；HTTP/2 多路复用改变连接数假设；SameSite 默认值因浏览器与版本而异；CSP 各级别支持不同。

**边界**：不重复 s2-l3 的 API 授权模型；不讲 OIDC 协议完整实现；不讲 WAF/风控产品；本讲只讲浏览器会话、实时链路与全栈安全边界。

### s6-l4 边缘部署、特性开关与全栈可观测性（80 min）

**Objectives**

1. 设计 CDN/边缘缓存策略，理解 stale-while-revalidate 与个性化的冲突。
2. 识别边缘函数的限制：运行时、CPU 时间、状态、一致性、日志。
3. 用特性开关做灰度与即时回滚，并控制开关债。
4. 用 RUM + 前后端 trace 串联定位端到端问题，定义发布健康度。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 前置仓与店内现做 | CDN 缓存 vs 边缘函数 |
| 2 | text | 边缘缓存层级 | 缓存键、Vary、Cookie 污染、个性化 bypass |
| 3 | code | 边缘缓存决策 | TTL、SWR、单飞刷新、过期回源 |
| 4 | table | 边缘函数限制 | 运行时、CPU、内存、状态、日志、冷启动 |
| 5 | code | 特性开关判定 | 白名单、百分比分桶、租户、kill switch |
| 6 | flow | 发布 → 灰度 → 健康度 → 扩量/回滚 | 每步的判定条件 |
| 7 | text | RUM 与服务端 trace | 采集内容、采样、traceparent、端到端分段 |
| 8 | code | RUM 与服务端 trace 合并（跨层） | 按 traceId 对齐；最大缺口；缺失标记 |
| 9 | case | CDN 缓存了个人看板 | 缓存键缺用户维度；修复与预防 |
| 10 | pitfall | 边缘与发布的五个坑 | 缓存 Set-Cookie、Vary 缺失、开关嵌套、RUM 采样偏差、trace 断链 |
| 11 | steps | LinkHub 发布健康度看板 | 指标、阈值、观察窗、回滚条件 |
| 12 | note | 面试延伸 | 用户说「页面慢」，如何用 RUM + trace 定位 |

**概念检查**

- C1 单选：个性化页面能否被 CDN 缓存、正确做法是什么（按用户/租户维度或 bypass，而不是全局缓存）。
- C2 多选：特性开关的治理要求（命名、所有者、过期、默认值、审计、嵌套上限）。
- C3 单选：浏览器有 RUM 但服务端无 trace，先查哪一层（trace 透传/网关采样/跨域头）。

**代码题：边缘缓存 + trace 合并（跨层：浏览器 → 服务端）**

- 契约：
  - `createEdgeCache({ ttlMs, swrMs, now, load, onRefreshError })`：`get(key, { bypass })`；`age = now() - storedAt`；`age <= ttlMs` 返回 `{ value, state: 'fresh' }`；`ttlMs < age <= ttlMs + swrMs` 返回旧值 `{ value, state: 'stale' }` 并触发一次后台刷新（单飞，同一 key 只允许一个在途刷新，期间所有请求都拿到旧值且不再触发）；`age > ttlMs + swrMs` 等待 `load` 并返回 `{ value, state: 'miss' }`；`bypass` 直接回源并更新缓存，返回 `{ value, state: 'bypass' }`；刷新成功替换缓存；刷新失败保留旧值、调用 `onRefreshError(error, key)`，失败落定后下一次 stale 请求可再次触发刷新；miss 的 `load` 失败直接抛出且不写缓存；`now` 可注入。
  - 测试同步：缓存暴露 `whenIdle()`，返回一个在所有在途后台刷新落定后 resolve 的 Promise；测试用可控 `load` Promise + `await whenIdle()` 断言刷新成功/失败，不依赖真实计时器。
  - `joinTrace(rum, server)`：输入浏览器 RUM `{ traceId, lcpMs, inpMs, marks }` 与服务端 `{ traceId, spans: [{ name, startMs, durationMs }] }`；输出 `{ traceId, totalMs, segments, largestGap, incomplete }`；traceId 不匹配或缺失时 `incomplete: true`；span 按开始时间排序。
- 测试（≥8）：新鲜命中；SWR 返回旧值；同一 key 单飞；SWR 过期回源；bypass；刷新失败保留旧值且 `whenIdle` 后可重试；trace 正常合并；trace 缺失标记；span 乱序排序。
- Python：`asyncio.create_task` 表示后台刷新；`whenIdle()` 用 `asyncio.gather`；`now` 注入；测试用可控 Future。
- 常见错误：SWR 期间同步等待；多个并发请求同时回源；缓存键漏掉个性化维度；trace 用本地时间直接相减导致时钟偏移；span 未排序。
- 跨层证据：输入是浏览器 RUM 与服务端 span，输出是端到端分段；测试证明能定位「浏览器等待 vs 服务端处理」的最大缺口。

**方案题：LinkHub 发布健康度与边缘策略**

- 自检清单：缓存键；TTL/SWR；个性化；边缘函数职责；开关层级与所有者；灰度比例；健康指标；回滚阈值；RUM 采样；trace 串联；隐私与脱敏。
- 参考要点：边缘只做可缓存与轻逻辑；个性化必须进入缓存键或 bypass；开关必须有 kill switch 与过期时间；健康度看症状指标，不堆内部指标；RUM 与服务端用同一 traceId。

**事实清单**：SWR 语义来自 RFC 5861 的 `stale-while-revalidate`；边缘运行时能力差异大；`traceparent` 属于 W3C Trace Context；RUM 数据受采样与广告拦截影响。

**边界**：不重复 s3-l1 的 Redis 应用缓存；不重复 s4-l1 的后端日志/指标/追踪三支柱；不讲 CDN 厂商配置教程；只讲边缘层、发布与前端 RUM。

## 5. 项目 p6：LinkHub Web 与 BFF

**brief**：后端能力已经具备，但用户看不到、用不上、出问题也定位不到端到端。本阶段在 p2-p5 之上加产品层：契约生成的类型客户端、BFF 聚合、SSR/流式首屏、安全会话、实时看板、边缘缓存、特性开关与 RUM。不重写后端，不新建第二套 API。

**steps**

1. 从 p2 的 OpenAPI 生成类型安全客户端；CI 增加契约漂移检查，破坏性变更直接失败。
2. BFF 聚合详情页：链接元数据 + 统计摘要 + 权限；并发拉取、总超时、部分失败降级、错误码映射。
3. 首屏 SSR/流式渲染；给出 LCP/INP/CLS 预算并达标；预算写进 CI。
4. 会话：HttpOnly Cookie + SameSite + CSRF；CSP/HSTS；登录态不放 localStorage；越权用例通过。
5. 实时看板：SSE 或 WebSocket；断线指数退避重连；事件按 id 去重；失败后降级轮询。
6. 边缘缓存与特性开关：缓存键包含用户/租户维度或 bypass；开关支持白名单、百分比灰度、kill switch；RUM 上报并与后端 trace 串联。
7. 验收：类型零漂移；CWV 达标；断网/重连可用；开关可灰度可回滚；一个 requestId/traceId 能串起浏览器与服务端。

**milestones**

| ID | 标题 | 验收 |
| --- | --- | --- |
| p6-m1 | 契约客户端与漂移检查 | 客户端由 OpenAPI 生成；手改会被覆盖；破坏性变更在 CI 失败 |
| p6-m2 | BFF 聚合 | 详情页一个 BFF 请求；上游并发；总超时；部分失败有 `degraded` 标记 |
| p6-m3 | 渲染与 CWV | 首屏 SSR/流式；LCP/INP/CLS p75 达预算；预算进 CI |
| p6-m4 | 会话与安全 | HttpOnly/SameSite/CSRF；CSP/HSTS；localStorage 无 token；越权被拒 |
| p6-m5 | 实时看板 | 断线自动重连；指数退避 + jitter；重复事件不重复计数；降级轮询可用 |
| p6-m6 | 边缘、开关与 RUM | 个性化不进公共缓存；开关可灰度/回滚；RUM 与 trace 可串联；发布健康度可读 |

**deliverables**：生成的类型客户端、BFF 聚合层、SSR/流式页面、安全头与会话配置、实时看板、边缘缓存与开关配置、RUM 接入、CWV 报告、端到端 trace 截图/记录、README。

**checklist**：不重写 p2-p5；统计复用 p5；边缘缓存不缓存个性化响应；登录态不在 JS 可读存储；CORS 不通配 credentials；开关有所有者与过期时间；RUM 不含 PII；trace 跨浏览器与服务端可还原。

**与 p2-p5 的因果**：p2 提供 API 与契约，p3 提供异步队列，p4 提供生产化能力，p5 提供独立统计服务；p6 只增加产品层与端到端责任，不重新实现链接、缓存、队列或统计。
