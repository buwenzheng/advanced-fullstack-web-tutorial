# M8：毕业项目 LinkHub（M1-M11 + 答辩）

> 依赖：M5（S6）与 M6（S7）内容完成；a10（ADR）与 a12（故障复盘/表达）是 M8 的必需前置；其余附录不阻塞。产出：可部署、可运营、可答辩的毕业项目与评审材料。通过 G7 后进入 M9。

## 1. 模块目标

- 把 p1-p7 的成果合成一个产品，不重新起仓库、不重写已有服务。
- 11 个里程碑都必须有可观察的验收证据，而不是「做完了」。
- 答辩不是演示 happy path：要讲清三个取舍、两个失败模式，完成一次回滚与一次故障恢复，提交 ADR、容量模型、故障复盘、AI 评估报告与 AI 协作复盘。
- 本站只产出项目说明、模板与验收标准；真实系统由学员在自己的仓库中实现。

## 2. 项目结构

毕业项目沿用 p1-p7 的代码库，按服务与职责分层：

```
linkhub/
  services/api/          # p1-p4：链接、认证、缓存、限流、幂等
  services/stats/        # p5：Outbox、RabbitMQ、读模型
  web/                   # p6：类型客户端、BFF、SSR、实时看板
  ai/                    # p7：网关、RAG、受限工具、评估
  infra/                 # Docker、CI/CD、边缘/开关配置
  docs/
    adr/                 # 3 份 ADR
    reports/             # 容量、故障复盘、AI 评估、CWV
    ai-collaboration-record.md
```

**硬规则**

- 不新建第二套 API、缓存、队列或统计服务；所有能力复用 p1-p7。
- 每个里程碑只在上一个里程碑的代码库上增量演进。
- 所有验收证据必须可复现：命令、报告、截图、trace 或测试输出。

## 3. 里程碑

里程碑 ID 固定为 `m1` … `m11`，与标题 M1-M11 一一对应；进度键为 `p['p-graduation'].m[<id>]`。

### M1 契约与认证

**交付**：OpenAPI、统一错误码表、JWT/Refresh、RBAC、契约测试。

**验收**

- OpenAPI 覆盖所有公开接口；请求/响应 schema 完整；
- 契约测试通过；破坏性变更会让测试失败；
- 未认证返回 401；越权返回 403；越权用例全部被拒；
- Refresh 轮换与撤销可用；token 过期行为明确。

**证据**：`openapi.yaml`、契约测试输出、RBAC 矩阵、越权用例结果。

**关联**：S2/S3；p2。

---

### M2 核心链路

**交付**：创建短链、跳转、管理列表、失效链接处理。

**验收**

- 创建、跳转、列表、删除/失效全链路可用；
- 跳转 P99 达到预设目标（写明口径与压测条件）；
- 失效链接返回 410，未知链接返回 404；
- 输入校验与错误码符合 M1 的契约。

**证据**：集成测试、压测报告、P99 截图、错误码样例。

**关联**：S1/S2/S3；p1/p2。

---

### M3 异步统计

**交付**：复用 p5 统计服务，接入点击事件与读模型。

**验收**

- 重复点击只计一次（eventId 幂等 + 唯一索引兜底）；
- 统计延迟有上界，查询接口标注一致性级别；
- 统计故障不影响跳转；
- 死信可重放，重放不重复累加。

**证据**：幂等测试、延迟指标、故障演练记录、重放记录。

**关联**：S3/S5；p3/p5。

---

### M4 缓存与保护

**交付**：Redis 缓存、限流、幂等键、热点保护。

**验收**

- 热点链接压测不击穿数据库；
- 超限返回 429，带可读的 retry 信息；
- 创建接口支持幂等键，重复提交不重复创建；
- 缓存失效/雪崩有降级策略。

**证据**：压测对比、限流测试、幂等测试、缓存故障演练。

**关联**：S3；p3/p4。

---

### M5 可观测性

**交付**：结构化日志、RED 指标、OpenTelemetry trace、看板与告警。

**验收**

- 任一 requestId 可还原请求经过的服务、数据库与队列；
- 日志无 PII；指标标签低基数；
- 告警有 runbook，且有明确的症状指标；
- 看板能回答「现在是否健康」。

**证据**：trace 截图、日志样例、指标看板、告警 runbook。

**关联**：S4；p4。

---

### M6 交付

**交付**：Docker、CI/CD、灰度与回滚。

**验收**

- 多阶段构建、非 root、健康检查；
- 流水线包含测试、契约检查、构建、部署；
- 完成一次真实回滚，记录时间线与指标恢复时间；
- 灰度可按比例/租户扩量，异常可即时停止。

**证据**：Dockerfile、流水线配置、回滚记录、灰度记录。

**关联**：S4；p4。

---

### M7 Web 与 BFF

**交付**：类型客户端、BFF 聚合、SSR/流式首屏、会话安全、实时看板。

**验收**

- 类型零漂移：客户端由 OpenAPI 生成，CI 检查破坏性变更；
- 详情页一个 BFF 请求完成聚合，有总超时与部分失败降级；
- 首屏 SSR/流式可用；实时看板断线可恢复；
- 登录态 HttpOnly Cookie，localStorage 无 token；CSRF 防护有效。

**证据**：契约漂移检查输出、BFF 测试、SSR 页面、断线重连录屏、Cookie/存储检查。

**关联**：S6；p6。

---

### M8 全栈质量门槛

**交付**：CWV 预算、CSP/安全头、RUM、关键页面可访问性。

**验收**

- LCP/INP/CLS 的 p75 达到预算；
- CSP/HSTS 等安全头齐全，无高危缺失；
- RUM 可上报，并能与后端 trace 串联；
- 键盘可完成核心操作；关键页有可访问名称。

**证据**：CWV 报告、安全头扫描、RUM 看板、可访问性检查清单。

**关联**：S6；p6。

---

### M9 管理后台与多租户

**交付**：登录、链接管理、统计查看、租户隔离。

**验收**

- 管理员可登录、创建/编辑/停用链接、查看统计；
- 跨租户读写全部拒绝，包含直接 URL 与 API 两种路径；
- 权限矩阵与 M1 的 RBAC 一致；
- 关键操作有审计日志。

**证据**：E2E 测试、跨租户用例、权限矩阵、审计日志样例。

**关联**：S2/S3/S6；p2/p6。

---

### M10 AI 功能与评估

**交付**：摘要/标签、语义搜索、自然语言问数、引用与降级。

**验收**

- 摘要/标签走异步链路，失败降级规则提取；
- 语义搜索租户过滤前置，引用精确到文档块；
- 问数只调用 p5 受限工具，不直连生产库、不生成任意 SQL；
- 离线评估集通过；注入用例不越权、不泄漏；
- 单请求与单租户成本有上限；模型不可用时功能降级。

**证据**：评估报告、注入测试报告、引用样例、成本看板、模型故障演练。

**关联**：S7；p7。

---

### M11 故障演练与答辩

**交付**：ADR、容量模型、故障复盘、AI 评估报告、AI 协作复盘、答辩材料。

**验收**

- 讲清三个取舍：至少覆盖数据/异步/全栈或 AI 中的三个；
- 讲清两个失败模式：现象、根因、发现方式、预防；
- 完成一次故障恢复与一次回滚；
- AI 功能可回滚；能讲清哪些任务适合 AI、如何验证与回滚；
- 答辩材料中的数字与报告一致。

**证据**：3 份 ADR、容量模型、故障复盘、AI 评估报告、AI 协作记录、答辩提纲。

**关联**：S4/S5/S6/S7；a10/a12 为必需前置（M8 依赖）。

## 4. 必交材料与模板

### 4.1 ADR（3 份）

建议主题：

1. **数据与租户模型**：为什么选 Postgres、租户隔离方式、索引与分片边界。
2. **异步与统计**：为什么从 BullMQ 升级到 Outbox + RabbitMQ、代价与反悔条件。
3. **AI 接入**：为什么用 RAG + 受限工具而不是 text-to-SQL；模型路由与降级。

每份 ADR 必须包含：

| 字段 | 要求 |
| --- | --- |
| 标题与状态 | 提议/接受/废弃/取代 |
| 背景与问题 | 要解决的具体问题，不是技术名词 |
| 约束 | 团队、成本、合规、时间、现有系统 |
| 备选方案 | 至少两个，写清代价 |
| 决策 | 选了什么、为什么 |
| 后果 | 正面/负面/可逆性 |
| 反悔条件 | 什么信号出现时重新评估 |

### 4.2 容量模型

必须包含：

- 峰值 QPS、读写比、缓存命中率、单实例基线；
- 平均/峰值/故障三场景；
- 实例数、数据库连接、Redis、队列积压、AI token 预算；
- 冗余与增长；
- 成本表（计算/存储/网络/模型）；
- 压测验证与瓶颈迁移。

### 4.3 故障演练

至少两次，其中一次必须是发布回滚。建议从以下选择：

| 演练 | 期望行为 | 记录 |
| --- | --- | --- |
| Redis 不可用/缓存击穿 | 限流 + 数据库保护；跳转降级但不崩 | 发现时间、止损、恢复 |
| 统计消费者 kill -9 / MQ 不可用 | 跳转不受影响；事件可重放；重复只计一次 | 积压、重放、恢复 |
| 模型 provider 超时/429 | AI 功能降级；整站可用 | 降级路径、成本 |
| 坏发布回滚 | 分钟级回滚；指标恢复 | 时间线、指标对比 |

复盘报告模板：

| 字段 | 内容 |
| --- | --- |
| 时间线 | 发现、响应、止损、恢复、复盘 |
| 影响 | 用户、租户、数据、SLO |
| 根因 | 直接原因与系统性原因 |
| 行动项 | owner、截止时间、可验证结果 |
| 预防 | 机制改进，不是「下次注意」 |

### 4.4 AI 评估报告

必须包含：评估集版本与规模、四类用例覆盖、阈值、结果、失败样例、修复、成本、降级演练。五项 AI 质量门槛逐项给证据。

### 4.5 AI 协作复盘

按五层模型记录：

| 层 | 记录 |
| --- | --- |
| 任务 | 分类矩阵位置、为什么交给 AI/为什么不由 AI 主导 |
| 上下文 | 给了什么、缺了什么、如何发现 |
| 执行 | 工具权限、diff 规模、计划与回滚点 |
| 验证 | 独立命令、测试是否被改、运行时证据 |
| 系统 | 度量、review 政策、失败如何复用 |

至少 3 个失败案例，每个包含 taxonomy 分类、发现方式、复现、预防；至少一次因验证发现问题而回滚或重做。

## 5. 答辩评分表

评分 1-5 分；通过条件：平均 ≥ 3.5，且没有任何维度低于 3；所有硬门槛必须通过。

| 维度 | 5 分标准 | 硬门槛 |
| --- | --- | --- |
| 架构与取舍 | 三个取舍均有备选、代价与反悔条件 | 至少三个取舍 |
| 数据与一致性 | 事务、幂等、统计一致性讲得清 | 重复点击只计一次 |
| 可靠性与运维 | SLO、演练、回滚有数据 | 一次回滚 + 一次故障恢复 |
| 全栈与体验 | 契约、渲染、实时、安全形成闭环 | 契约零漂移、CWV、安全头、RUM |
| AI 工程 | 评估、注入、引用、成本、降级有证据 | 五项 AI 质量门槛 |
| AI Coding 系统 | 五层模型、失败 taxonomy、度量可复盘 | 协作记录完整，≥3 失败案例 |
| 表达与追问 | 结构清晰、数字一致、能承认未知 | 讲清两个失败模式 |

**必问问题**

1. 你这个系统最贵的三个取舍是什么？如果重来会改哪个？
2. 统计为什么最终一致？重复/丢失/延迟分别怎么处理？
3. 一次请求从浏览器到数据库，经过哪些层？哪一层最容易出问题？
4. AI 功能答错了，你怎么发现？怎么证明修复没有回归？
5. 哪些任务你绝不会交给 AI？为什么？
6. 如果流量涨 10 倍，先动哪里？瓶颈会迁移到哪里？

**扣分项**

- 只演示 happy path，没有失败模式；
- 数字与报告不一致；
- 说不清 AI 功能的评估与成本；
- 把「AI 说测试过了」当验证；
- 跨租户或注入用例未覆盖。
