## 3. S7 课时 brief

### s7-l1 LLM 应用基础与流式网关（80 min）

**Objectives**

1. 解释 tokens、上下文窗口、消息角色与截断对行为与成本的影响。
2. 用 SSE 实现可增量消费的流式输出，并处理分块边界与结束标记。
3. 设计结构化输出校验、超时/重试/幂等与模型路由。
4. 用 token 计量与成本表控制单请求与单租户预算。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 点餐备注与上下文窗口 | 说得越多不一定越好；窗口有限且按量计费 |
| 2 | text | tokens / 角色 / 窗口 | system/user/assistant/tool；截断策略；输入输出都计费 |
| 3 | table | 结构化输出的三种做法 | JSON mode、function calling、schema 校验；各自失败模式 |
| 4 | code | SSE 解析器 | 分块边界、多行 data、空行派发、`[DONE]`、CRLF |
| 5 | flow | 请求 → 路由 → 模型 → 流式 → 校验 → 计量 | 每步的超时与失败处理 |
| 6 | code | 网关路由与预算 | 按复杂度/风险选模型；预算拒绝；幂等重试；成本计算 |
| 7 | case | 流式断开后重复扣费 | 无幂等键 + 自动重试；修复与指标 |
| 8 | pitfall | 网关的五个坑 | 非幂等重试、忽略 usage、上下文超限、把模型输出当可信、无降级 |
| 9 | compare | 自建网关 / 直连 SDK / 托管网关 | 控制力、成本、合规、运维 |
| 10 | text（深挖） | 模型路由与降级 | 小模型优先、失败升级、熔断、缓存 |
| 11 | steps | 设计 LinkHub 摘要网关 | 输入、输出 schema、预算、超时、降级、计量 |
| 12 | note | 面试延伸 | 如何把单请求成本压到可预测 |

**概念检查**

- C1 单选：上下文超限时最安全的处理（截断 + 摘要 + 明确降级，而不是静默丢消息）。
- C2 多选：哪些操作必须幂等（重试、流式重连、工具调用、计费）。
- C3 单选：结构化输出校验失败后应该做什么（重试一次 + 降级，而不是把坏 JSON 写库）。

**代码题：SSE 解析 + 流式网关**

- 契约：
  - `parseSSE(chunks)`：输入字符串分块数组，输出事件数组 `{ id?, event, data }`；支持多行 `data:` 拼接、空行派发、CRLF、跨块切断；`[DONE]` 输出 `{ event: 'done', data: '' }`；忽略注释行。
  - `createGateway({ providers, pricing, budget, maxRetries = 1 })`：
    - `providers = { cheap, strong }`，均为 `async (request) => ({ text, model, usage: { inputTokens, outputTokens } })`。
    - `pricing = { cheap: { inputPer1k, outputPer1k }, strong: { inputPer1k, outputPer1k } }`，单价为**整数分/千 token**；成本 `cost = ceil((inputTokens * inputPer1k + outputTokens * outputPer1k) / 1000)`，全程整数。
    - `request = { task: { complexity: 'low'|'high', risk: 'low'|'high' }, messages, idempotencyKey? }`；路由：`risk === 'high' || complexity === 'high'` 走 `strong`，否则 `cheap`。
    - `budget` 为本次调用的成本上限（整数分）；计算出的 `cost > budget` 抛 `{ code: 'BUDGET_EXCEEDED' }`，不重试。
    - 可重试错误仅限 `err.retryable === true` 且请求带 `idempotencyKey`；最多重试 `maxRetries` 次（默认 1 次，总尝试 2 次）；非幂等或非可重试错误直接抛出。
    - 返回 `{ text, model, usage, cost, attempts }`；`attempts` 为实际 provider 调用次数；provider 返回缺 `usage` 或负数 token 视为 `INVALID_PROVIDER_RESPONSE`。
- 测试（≥9）：单块 SSE；跨块切断；多行 data；`[DONE]`；低复杂度走 cheap；高风险走 strong；预算拒绝；幂等键重试一次后成功；非幂等失败不重试；成本按输入/输出分别计算且为整数分。
- Python：生成器解析 SSE；`asyncio` 网关；异常映射；成本用 `Decimal` 或整数分。
- 常见错误：按行读取但没缓冲半行；把所有错误都重试；重试不带幂等键；只算输出 token；流式结束才计量导致超预算。
- 安全：测试不访问网络；provider 是注入的假函数；fixture 中不含真实 key。

**方案题：LinkHub 摘要网关设计**

- 自检清单：输入 schema；输出 schema；模型路由；超时；重试与幂等；token 预算；租户配额；降级（规则提取）；计量与 trace；失败告警。
- 参考要点：摘要/标签走异步链路，不阻塞创建短链；结构化输出必须校验；模型失败降级为规则提取；成本按租户与请求双上限。

**事实清单**：不同模型的 token 计算方式不同；上下文窗口与最大输出是两件事；SSE 是 HTTP 上的文本协议；定价会变，课程只教计量方法，不写死价格。

**边界**：不训练/微调模型；不讲推理服务内部（a13）；不讲具体厂商 SDK；不讲提示词大全。

### s7-l2 RAG、向量检索与工具调用（85 min）

**Objectives**

1. 解释 embedding、切分、向量索引与相似度，知道召回失败通常发生在哪一步。
2. 设计关键词 + 向量的混合检索，并在排序前完成权限过滤。
3. 用 rerank、引用与新鲜度让答案可追溯。
4. 区分受限工具调用与 text-to-SQL，守住「不直连生产库、不生成任意 SQL」。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 图书馆找书 | 关键词像索引卡，向量像「意思相近」的书架 |
| 2 | text | embedding 与相似度 | 维度、余弦相似度、归一化、模型一致性 |
| 3 | code | 文档切分 | 最大长度、重叠、段落边界、稳定 chunk id |
| 4 | flow | 文档 → 切分 → 向量 → 索引 → 检索 → rerank → 引用 | 每步的失败现象 |
| 5 | table | pgvector / HNSW / IVF | 召回、延迟、内存、参数；不展开数学推导 |
| 6 | code | 混合检索 | 向量 + 关键词加权；租户过滤前置；引用；新鲜度 tie-break |
| 7 | case | 语义搜索召回了其他租户文档 | 权限后置的后果；修复与测试 |
| 8 | pitfall | RAG 的五个坑 | 切分丢上下文、只看向量、引用编造、权限后置、索引过期 |
| 9 | compare | 受限工具 vs text-to-SQL | 可验证性、权限、注入面、表达力 |
| 10 | code | 受限统计工具 | 指标白名单、时间范围、行数上限、租户隔离 |
| 11 | steps | LinkHub 问数工具设计 | 问题 → 工具选择 → 参数校验 → 查询 → 口径说明 |
| 12 | note | 面试延伸 | RAG 答非所问，按什么顺序排查 |

**概念检查**

- C1 单选：权限过滤应该放在检索的哪个阶段（排序前、进入上下文前）。
- C2 多选：混合检索的必要性来源（关键词精确匹配、语义泛化、新鲜度、权限）。
- C3 单选：问数功能为什么不应生成任意 SQL（不可验证、越权、注入、性能不可控）。

**代码题：切分 + 混合检索 + 受限工具**

- 契约：
  - `chunkDocument(text, { maxChars = 200, overlap = 40 })`：按段落/句子边界切分；块之间有重叠；返回 `[{ index, text, start, end }]`；不产生空块；重叠小于 maxChars。
  - `hybridSearch({ query, docs, embed, keywordScore, tenantId, topK = 3, weights = { vector: 0.7, keyword: 0.3 } })`：
    - `docs = [{ id, docId, chunkIndex, text, tenantId, updatedAt, embedding? }]`；`embed` 为 `async (text) => number[]`，文档缺 `embedding` 时调用 `embed(text)` 补齐；向量维度不一致抛 `DIM_MISMATCH`。
    - 评分前先按 `tenantId` 过滤；对候选集分别计算向量余弦相似度与 `keywordScore(query, text)`；每侧做 min-max 归一化：`max === min` 时归一值为 0；加权分 `score = weights.vector * vecNorm + weights.keyword * kwNorm`。
    - 按 `score` 降序；同分按 `updatedAt` 降序，再按 `id` 升序；`topK` 在排序后截断；返回 `[{ id, score, citation: { docId, chunkIndex } }]`；空查询（trim 后）或 `topK <= 0` 返回空数组；分数保留原始浮点，测试用 `1e-9` 容差比较。
  - `runStatTool(call, { allowedMetrics, query, tenantId, maxLimit = 100, maxRangeDays = 90 })`：
    - `call = { tool: 'topLinks', metric, rangeDays, limit, tenantId? }`；`query` 为注入的 `async ({ metric, rangeDays, limit, tenantId }) => rows`。
    - 校验顺序固定：工具名 → 租户（`call.tenantId` 存在且不等于上下文租户即拒绝）→ 参数类型/范围（`rangeDays` 整数 1..`maxRangeDays`，`limit` 整数 1..`maxLimit`）→ 指标白名单；任一失败抛 `TOOL_DENIED`，`error.reason ∈ { UNKNOWN_TOOL, TENANT_MISMATCH, INVALID_ARGUMENT, RANGE_EXCEEDED, LIMIT_EXCEEDED, METRIC_NOT_ALLOWED }`；校验通过前不得调用 `query`。
    - 返回 `{ rows, basis: metric, rangeDays }`；`rows` 截断到 `limit`；`basis` 取值 `'clicks' | 'unique_visitors'`。
- 测试（≥10）：
  1. 切分不产生空块；
  2. 重叠正确；
  3. 租户过滤在排序前；
  4. 关键词与向量加权；
  5. 分数相同按新鲜度；
  6. `topK` 截断；
  7. 未知指标拒绝；
  8. 超范围拒绝；
  9. 超行数拒绝；
  10. 跨租户拒绝；
  11. 正常调用的口径返回。
- Python：`re` 切分；余弦相似度手写；dict 排序稳定；异常带 `reason`。
- 常见错误：先取 topK 再过滤租户；引用只给文档不给块；切分重叠为 0 导致语义断裂；工具参数不校验就拼查询。
- 安全：fixture 中包含恶意文档、跨租户文档、超限调用；测试证明全部被拒。

**方案题：LinkHub 语义搜索与问数**

- 自检清单：文档来源与切分；embedding 模型与版本；索引类型与参数；混合权重；rerank；引用格式；新鲜度；权限过滤；问数工具白名单；口径说明；降级。
- 参考要点：权限必须在检索前；引用精确到块；问数只调用受限工具，不直连生产库；索引版本与 embedding 版本要一起管。

**事实清单**：pgvector 支持 HNSW/IVF；不同 embedding 模型维度与语义空间不同，不能混用；余弦相似度与内积在归一化后等价；HNSW 参数影响召回与内存。

**边界**：不展开 HNSW/IVF 的数学推导（a13 只讲基础设施素养）；不教模型训练；不做厂商选型评测。

### s7-l3 AI 功能评估、安全与成本（80 min）

**Objectives**

1. 建立离线评估集与回归门槛，覆盖事实性、引用、拒答与注入。
2. 识别 LLM-as-judge 的偏差，知道什么时候必须人工抽检。
3. 区分直接/间接提示注入，建立「不可信内容不进指令层」的边界。
4. 用缓存、批量、路由、预算与降级控制成本。

**内容块大纲**

| # | type | 标题 | 要点 |
| --- | --- | --- | --- |
| 1 | analogy | 考试与评估集 | 没有题库的「感觉良好」不是质量 |
| 2 | text | 离线/在线评估 | 指标、样本、回归门槛、线上分布漂移 |
| 3 | code | 评估结果汇总与门槛 | 通过率、引用率、拒答准确率、注入拦截率 |
| 4 | table | 评估维度 | 事实性、引用、拒答、注入、延迟、成本 |
| 5 | case | 评估集全过、线上却翻车 | 分布漂移 + 评估集泄漏；修复 |
| 6 | text | 提示注入 | 直接注入 vs 间接注入；信任边界；最小权限 |
| 7 | code | 工具授权 | 白名单、租户、参数上限、任意 SQL 拒绝 |
| 8 | flow | 不可信内容 → 隔离 → 工具白名单 → 参数校验 → 输出审查 | 每层的失败兜底 |
| 9 | pitfall | AI 安全的五个坑 | 网页内容当指令、PII 入日志、跨租户缓存、成本无上限、输出直接执行 |
| 10 | table | 成本控制 | 缓存、批量、路由、预算、降级；各自代价 |
| 11 | steps | 设计注入测试集 | 直接、间接、越权、数据外泄、工具滥用 |
| 12 | note | 面试延伸 | 如何证明一次模型/提示变更没有回归 |

**概念检查**

- C1 单选：评估集全部通过但线上效果差，最先怀疑什么（分布漂移/评估集泄漏）。
- C2 多选：间接提示注入的入口（网页正文、文档、邮件、工具返回、用户上传）。
- C3 单选：模型要求调用「删除全部数据」的工具时，正确防线是什么（工具白名单 + 权限 + 参数校验 + 人工确认，而不是只加一句提示词）。

**代码题：评估门槛 + 工具授权**

- 契约：
  - `runEvaluation(cases, runner, thresholds)`：
    - `cases = [{ id, input, expected: { mustCite?, shouldRefuse?, injection? } }]`；`runner = async ({ input }) => ({ answer, citations, refused, toolCalls })`，`toolCalls = [{ name }]`。
    - `thresholds = { passRate, citationRate, refusalAccuracy, injectionBlockRate, allowedTools }`，比率范围 `0..1`，比较用 `>=`。
    - 单 case 判定：调用 `runner` 抛错 → 失败 `RUNNER_ERROR`；调用不在 `allowedTools` 的工具 → 失败 `DISALLOWED_TOOL`；`shouldRefuse === true` 要求 `refused === true`，否则失败 `SHOULD_REFUSE`；`shouldRefuse !== true` 要求 `refused === false`，否则失败 `UNEXPECTED_REFUSAL`；`mustCite === true` 要求 `citations.length > 0`，否则失败 `MISSING_CITATION`；`injection === true` 只额外要求没有 `DISALLOWED_TOOL`（允许安全地用白名单工具回答）。
    - 指标：`passRate = 通过数 / 总数`；`citationRate = 有 mustCite 且带引用的数 / mustCite 数`；`refusalAccuracy = 正确拒答数 / shouldRefuse 数`；`injectionBlockRate = 无越权工具调用的注入用例数 / injection 用例数`；后三项分母为 0 时记为 1（空集不虚增失败）。
    - 输出 `{ pass, metrics: { passRate, citationRate, refusalAccuracy, injectionBlockRate }, failures: [{ caseId, code, detail }] }`；四项全部 `>=` 阈值才 `pass: true`；`cases` 为空时 `pass: false`，`passRate: 0`，failures 为 `[{ caseId: null, code: 'EMPTY_EVALUATION', detail }]`。
  - `authorizeToolCall(call, policy)`：
    - `call = { tool, args }`；`args` 仅允许该工具声明的字段：`topLinks` 允许 `{ metric, rangeDays, limit, tenantId }`。
    - `policy = { allowedTools, tenantId, maxLimit = 100, allowedMetrics }`。
    - 检查顺序固定：工具白名单 → `args.tenantId` 与策略租户一致 → 未知字段（含 `sql`/`query`/`where` 等）→ `limit` 整数且 `<= maxLimit` → `metric` 在白名单；返回 `{ allowed: boolean, reason }`，`reason ∈ { OK, UNKNOWN_TOOL, TENANT_MISMATCH, ARBITRARY_FIELD, LIMIT_EXCEEDED, METRIC_NOT_ALLOWED, INVALID_ARGUMENT }`；任何情况都不抛异常。
- 测试（≥10）：
  1. 全通过；
  2. 缺引用判失败；
  3. 应拒答却回答判失败；
  4. 注入用例调用禁止工具判失败；
  5. 阈值边界；
  6. 空评估集；
  7. 正常工具调用放行；
  8. 未知工具拒绝；
  9. 跨租户拒绝；
  10. 超行数拒绝；
  11. 任意 SQL 字段拒绝。
- Python：dataclass/dict；比率计算；阈值比较；返回结构化失败。
- 常见错误：只算准确率不看引用；注入用例只测直接注入；把授权失败抛异常导致整条链路崩；阈值用平均值掩盖长尾。

**方案题：LinkHub AI 评估与注入测试**

- 自检清单：评估集规模与来源；四类用例；阈值；回归 CI；LLM-as-judge 使用范围；人工抽检；注入入口；工具权限；PII；租户隔离；成本上限；降级。
- 参考要点：评估集要像测试集一样版本化；注入用例必须覆盖间接注入与工具滥用；工具授权是主防线，提示词只是辅助；成本与降级要可观测。

**概念检查**

- C1 单选：架构决策属于任务矩阵的哪个象限（高歧义/低可验证，人主导）。
- C2 多选：最小充分上下文应包含什么（目标、相关文件、契约、验收测试、负向约束）。
- C3 单选：AI 说「测试全部通过」但 CI 没跑，正确做法是什么（独立执行并检查测试是否被改）。

**代码题：AI 变更验证门（跨角色：执行 → 验证）**

- 契约：`reviewAICodeChange(change, policy)`：
  - `change = { files: [{ path, additions, deletions, status }], tests: { total, passed, skipped, deleted, changed }, depsAdded, diffText }`；`tests.changed` 是变更的测试文件数（用于判断是否补了测试）。
  - `policy = { maxFiles, maxChangedLines, allowedPaths, forbiddenPaths, allowNewDeps, requireTests }`；`allowedPaths`/`forbiddenPaths` 按路径前缀匹配，禁止路径优先；`allowedPaths` 为空表示不额外限制。
  - 返回 `{ verdict: 'pass' | 'warn' | 'block', findings: [{ code, severity, detail }] }`；严重度 `block > warn > pass`，findings 按严重度降序、同严重度按 `code` 升序。
  - 规则（固定顺序）：
    - `block`：`tests.deleted > 0` → `TEST_DELETED`；`requireTests && tests.total === 0` → `TESTS_NOT_RUN`；`tests.passed < tests.total - tests.skipped` → `TEST_FAILED`；`depsAdded.length > 0 && !allowNewDeps` → `UNEXPECTED_DEP`；任一文件命中 `forbiddenPaths` → `FORBIDDEN_PATH`；`diffText` 命中密钥模式 → `SECRET_LEAK`。
    - `warn`：`files.length > maxFiles` → `TOO_MANY_FILES`；`sum(additions + deletions) > maxChangedLines` → `DIFF_TOO_LARGE`；`tests.skipped > 0` → `TESTS_SKIPPED`；`requireTests && tests.changed === 0 && 存在行为变更` → `BEHAVIOR_CHANGE_WITHOUT_TESTS`；`files.length === 0 && tests.changed === 0` → `EMPTY_CHANGE`。
    - 无 finding → `pass`。
  - 行为变更定义：存在 `status !== 'deleted'` 且路径不在测试目录（`test/`、`tests/`、`__tests__/`、`*.test.*`、`*.spec.*`）且 `additions + deletions > 0` 的文件。
  - 密钥模式固定为：私钥块 `-----BEGIN [A-Z ]*PRIVATE KEY-----`、`sk-[A-Za-z0-9]{16,}`、AWS `AKIA[0-9A-Z]{16}`、GitHub `ghp_[A-Za-z0-9]{20,}`；不引入熵检测。
  - 空变更明确判 `warn`（可能是流水线异常），不判 `pass`。
- 测试（≥10）：正常变更 pass；删除测试 block；跳过测试 warn；测试失败 block；新依赖未允许 block；修改禁止路径 block；密钥泄漏 block；文件数超限 warn；行数超限 warn；findings 排序稳定；空变更 warn；无测试变更但改了行为 warn。
- Python：纯函数；正则检测密钥；排序；返回 dict。
- 常见错误：只看测试是否通过不看测试是否被删；把「新增依赖」当普通变更；diff 规模无上限；验证门自己调用 AI 解释。
- 说明：这是「验证层」的代码化，不依赖任何模型；练习证明验证必须独立于生成。

**方案题：AI 协作任务卡**

- 自检清单：任务分类；目标与非目标；相关文件与契约；验收测试；负向约束；允许修改的路径；工具权限；回滚方式；失败记录。
- 参考要点：任务卡先写验收再写步骤；上下文只给最小充分；验证由独立命令完成；失败要记录 taxonomy 与改进。

**事实清单**：LLM 生成代码的失败模式与模型版本相关；不同工具的能力边界不同；AI Coding 的度量没有统一行业标准；本讲不评价具体工具。

**边界**：不教模型原理；不做工具评测；不提供「万能提示词」；只讲可验证的协作系统。

## 4. AI 练习的 Mock 与 Fixture 规范

浏览器沙箱不联网，所有 AI 题必须满足：

1. **注入依赖**：provider、embedding、时钟、随机数全部由参数注入；生产代码不直接读 `process.env` 或 `fetch`。
2. **固定 fixture**：放在 `web/scripts/content/fixtures/ai/`，内容稳定、可审查、无真实 key、无真实个人信息。
3. **确定性**：同一输入必须得到同一输出；涉及随机只用于 jitter/分桶，必须注入可复现的随机源。
4. **成本为零**：测试不调用任何付费 API；不在仓库写入 key；README 明确「练习用 mock，真实接入见 p7」。
5. **失败可解释**：mock 的错误要带 `code`（如 `RATE_LIMITED`、`TIMEOUT`、`INVALID_JSON`），便于测试错误路径。

**Fixture 清单**

| 文件 | 内容 | 被谁使用 |
| --- | --- | --- |
| `fixtures/ai/sse-chunks.js` | 分块 SSE 序列（含跨块、多行、CRLF、`[DONE]`） | s7-l1 |
| `fixtures/ai/provider-cases.js` | 低复杂度/高风险/超预算/限流/超时 | s7-l1 |
| `fixtures/ai/rag-docs.js` | 多租户文档、块、mock 向量、更新时间 | s7-l2 |
| `fixtures/ai/tool-cases.js` | 合法/非法指标、跨租户、超限、任意 SQL | s7-l2/l3 |
| `fixtures/ai/eval-set.js` | 事实、引用、拒答、直接/间接注入 | s7-l3 |
| `fixtures/ai/injection-corpus.js` | 网页正文、文档、工具返回中的恶意指令 | s7-l3 |
| `fixtures/ai/ai-diffs.js` | 正常/删测试/越界/新依赖/密钥 diff | s7-l4 |

fixture 总量控制在可审阅范围：eval-set 20-30 条，injection-corpus 10-15 条，rag-docs 8-12 篇；每条都有 `id` 与预期结果。

**评估集最低覆盖**

| 类别 | 最少条数 | 必须包含 |
| --- | --- | --- |
| 事实性 | 6 | 有明确答案、无答案 |

| 成本/降级 | 2 | 超预算、模型不可用 |
